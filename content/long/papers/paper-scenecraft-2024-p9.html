一 · 管线定位：SceneCraft 在真实生产链路中的坐标

把 SceneCraft 放进真实生产管线，第一步不是问“它能不能生成场景”，而是问“它占据哪一段工序”。在典型的 3D 内容生产链路里，上游是需求与设计输入（文字 brief、概念图、参考场景），中游是资产准备与布局搭建，下游是渲染、烘焙、引擎导入、交互逻辑与验收。SceneCraft 的输入是文本描述，输出是可执行的 Blender Python 脚本与渲染图，因此它天然落在“从文字 brief 到可编辑场景工程”的这一段：它不生产资产，不替代建模师，也不负责最终引擎集成，它负责把空间意图翻译成结构化的、可复现的脚本化布局。

这个定位决定了它的接口形态。上游接口是自然语言描述与资产库清单：描述给出物体类别、数量级、空间关系（“沿墙排列”“围绕中央物体”“在另一物体上方”），资产库清单决定哪些类别可被实例化。下游接口是 Blender 工程文件与脚本：脚本里包含物体实例化、变换矩阵、父子关系、材质引用与相机设置，工程文件可被进一步手工精修或被导出到引擎。中间还有一个旁路接口——渲染图，它既是 GPT-V 反馈的输入，也是人工验收的第一道视觉凭证。

关键机制在于“场景图作为中间表示”这一层。文本不直接变成脚本，而是先被 LLM 规划成场景图 $\mathcal{S}=\mathrm{SceneGraph}(t)$，场景图里的节点是物体、边是空间关系，关系再被转成数值约束写进脚本 $\mathrm{Script}=\mathrm{LLM}(\mathcal{S})$，最后由 Blender 执行得到渲染 $\mathcal{I}=\mathrm{Blender}(\mathrm{Script})$。这条三段式链路在生产上的意义是：每一段都可被单独审计、替换与回滚。场景图可以人工审阅，脚本可以 diff，渲染图可以视觉比对。相比“文本直出脚本”的黑箱，这种分层让管线集成方能在任意一段插入检查点。

一个具体例子：某虚拟制片团队需要为一场室内戏快速产出十个布局变体。他们把 brief 写成结构化文本（房间尺寸、家具类别、必须出现的锚点物体、镜头朝向），把工作室资产库的类别清单一并喂给 SceneCraft，得到十份脚本与十张渲染图。美术指导在场景图层面否决两个空间关系错误的变体，在脚本层面微调三个变体的相机参数，剩余五个进入下游引擎导入。整个过程中，SceneCraft 没有被当作“生成器”，而是被当作“布局起草器”，它的产出是待审阅的草稿而非终稿。

系统代价在这里第一次显现：SceneCraft 依赖 Blender 资产库，意味着上游必须提供一份类别覆盖足够、命名规范的资产清单，否则场景图里的节点无法被实例化，脚本会在执行阶段失败。这不是模型能力问题，而是接口契约问题——资产库的类别命名与场景图节点命名必须对齐，否则 LLM 生成的实例化调用会指向不存在的资产。工程上常见的做法是维护一张“类别—资产路径”映射表，并在场景图生成后做一次节点合法性校验，把不合法节点在进入脚本生成前就打回。

二 · 上游接口：文本 brief 与资产库的契约设计

上游接口的设计核心是把“自然语言”收敛成“可被场景图消费的结构”。SceneCraft 的场景图规划模块接受文本，但文本的自由度越高，规划出的场景图越容易偏离资产库的实际能力。工程上的做法是给 brief 加一层轻量 schema：必填字段包括场景类型、空间尺度、锚点物体列表、关系约束列表、镜头参数；可选字段包括风格标签与资产偏好。这层 schema 不是 SceneCraft 论文的一部分，而是集成方为了稳定接口必须补的胶水层。

机制上，场景图节点需要携带三类信息才能被下游脚本消费：类别标识（对应资产库中的可实例化类别）、实例数量、以及与其他节点的关系约束。关系约束被转成数值约束时，常见形式是距离区间、朝向角、包含关系与支撑关系。伪代码思路如下：对每条关系边，取出两端节点的目标位姿变量，写入一个约束项；对“沿墙排列”这类集合关系，展开成对每个实例的墙面距离约束与相邻间距约束；对“在另一物体上方”这类支撑关系，写入高度差与水平投影重叠约束。这些约束不是硬求解，而是作为脚本生成时的提示与渲染后校验的依据。

$$\text{constraint}(a,b)=\{\,\lVert p_a-p_b\rVert\in[d_{\min},d_{\max}],\ \ \theta_{ab}\in[\theta_{\min},\theta_{\max}]\,\}$$

系统代价在上游接口处表现为“描述—资产”的语义鸿沟。文本里说“一张现代风格的沙发”，资产库里可能只有“sofa_A”“sofa_B”两个类别，风格标签无法被实例化。SceneCraft 的应对方式是把风格信息留在场景图节点属性里，由脚本生成阶段选择最接近的资产，但这一步没有视觉语义匹配能力，只能靠命名启发。失败模式是：场景图规划出十个风格化节点，脚本阶段全部落到同一个默认资产上，渲染图看起来“对但不对味”，GPT-V 反馈也无法纠正，因为它看到的是渲染结果而非资产语义。工程判断是：风格类需求不应交给 SceneCraft 闭环，应在资产准备阶段由人选型，SceneCraft 只负责布局。

另一个上游代价是 brief 的歧义放大。文本越短，场景图规划的方差越大；同一个 brief 多次运行会得到不同的空间关系解读。生产上要求可复现，因此集成方通常会固定随机性来源、缓存场景图、并对同一 brief 做多次采样后人工选优。这与“无需训练”的论文设定一致：SceneCraft 用预训练 LLM 加 GPT-V，不做训练，因此稳定性只能靠外部采样与筛选来兜底，而不是靠模型自身的确定性。

具体例子：一个电商团队要为家具目录生成场景图，brief 里写“客厅，三人沙发靠墙，茶几在沙发前方，地毯在茶几下”。场景图规划出四个节点与三条关系边；脚本生成阶段把“前方”转成朝向约束与距离区间；渲染后 GPT-V 检查“茶几是否在沙发与镜头之间”。若资产库里沙发只有两个朝向变体，脚本会选择默认朝向，此时“靠墙”约束可能被违反，GPT-V 在渲染图上看到沙发背面贴墙而正面朝内，触发一轮修正。这一轮修正的代价是一次完整渲染，渲染慢的局限在此处直接转化为迭代成本。

三 · 下游接口：脚本、工程文件与引擎导入

下游接口的第一形态是 Blender Python 脚本。脚本的可审计性是它相对“直接生成网格”的最大优势：每一行实例化、每一次变换都可被 diff、被版本控制、被参数化重跑。工程上应把脚本视为“布局的源代码”，而不是一次性产物。集成方通常会要求脚本满足三条契约：资产引用走统一映射函数而非硬编码路径；变换参数集中在脚本顶部的配置区；相机与灯光作为独立段落可被替换。这三条契约让脚本在下游引擎导入前可被批量改写。

第二形态是 Blender 工程文件。脚本执行后得到 .blend 工程，工程里保留了物体层级、材质引用与修改器栈。这里是人工精修的入口：美术可以在工程里调整材质、替换高模、补充细节，而不必回到文本层。代价是工程文件与脚本之间会失去同步——人工改动不会回写到脚本，下一次脚本重跑会覆盖人工改动。工程判断是：把脚本重跑限制在布局层，把人工精修限制在材质与细节层，两者用命名约定隔离，避免互相覆盖。

第三形态是引擎导入。Blender 到引擎的导出链路会丢失一部分信息：程序化材质、复杂修改器、非标准节点在导出时被烘焙或丢弃。SceneCraft 生成的场景以布局为主，材质通常是简单引用，因此导出损失可控；但如果场景图里包含大量依赖修改器的物体，导出后几何会与渲染图不一致，GPT-V 反馈阶段看到的渲染图不能代表引擎内的最终效果。这是一个接口错位：视觉反馈闭环的终点是 Blender 渲染，而生产验收的终点是引擎内截图，两者之间存在渲染器差异。

系统代价在 downstream 表现为“渲染慢”被放大。SceneCraft 每个场景迭代数轮，每轮都要 Blender 执行渲染再交给 GPT-V 检查。在生产管线里，如果下游还有引擎导入与引擎内验收，那么一次布局迭代的实际周期是“脚本生成 + Blender 渲染 + 视觉检查 + 引擎导入 + 引擎截图”，其中 Blender 渲染与引擎导入都是分钟级操作。含上百资产的复杂场景会进一步拉长这一周期，因为资产加载与几何求交的开销随实例数增长。失败模式是：迭代预算被渲染时间吃光，智能体只跑了少数几轮就被迫收敛，空间关系错误未被修正就进入下游。

具体例子：一个游戏关卡团队用 SceneCraft 生成一个含上百资产的市场场景。脚本执行后 Blender 渲染耗时明显，GPT-V 在第一轮指出“摊位之间的通道被货物堵住”，智能体改写脚本调整间距，第二轮渲染后通道打开但出现两个摊位重叠，第三轮修正重叠。三轮之后团队接受布局，导入引擎后发现引擎内光照与 Blender 渲染差异导致部分区域过暗，但此时已不再回到 SceneCraft 闭环，而是在引擎内手工补光。这说明 SceneCraft 的闭环边界应明确划在“布局正确性”，光照与材质属于下游职责。

四 · 成本结构：算力、人力与迭代预算

成本要分三块算：模型调用成本、渲染算力成本、人力审阅成本。模型调用侧，SceneCraft 无需训练，用预训练 LLM 加 GPT-V，因此没有训练成本，但有推理成本：每个场景要跑场景图规划、脚本生成、多轮视觉检查，每一轮都是一次或多次模型调用。调用次数随迭代轮数线性增长，而迭代轮数由场景复杂度与初始脚本质量决定。含上百资产的场景，场景图节点多、关系边多，脚本更长，模型输出的 token 量更大，单轮成本更高。

渲染算力侧，Blender 执行渲染是成本主项。渲染慢是论文明确列出的局限，工程上它转化为“每轮迭代的固定开销”。成本模型可以写成：总成本正比于迭代轮数乘以单轮渲染时间，再加上模型调用费用。单轮渲染时间随资产数量、几何复杂度、分辨率与采样数增长。生产上控制成本的手段不是减少迭代轮数（那会牺牲布局质量），而是降低单轮渲染成本：用低分辨率、低采样数的预览渲染做 GPT-V 检查，只在最终验收时做高质量渲染。这要求把“检查渲染”与“交付渲染”分开配置。

$$\mathrm{Cost}\ \approx\ N_{\mathrm{iter}}\cdot\bigl(C_{\mathrm{render}}+C_{\mathrm{LLM}}\bigr)+C_{\mathrm{human}}$$

人力审阅侧常被低估。SceneCraft 的产出是场景图、脚本与渲染图三份材料，审阅者需要同时看三者才能判断布局是否符合意图。场景图层面的审阅是结构化的，成本较低；脚本层面的审阅需要懂 Blender API，成本较高；渲染图层面的审阅最直观但最容易漏掉空间关系错误（单视角渲染会遮挡）。工程判断是：把人力集中在场景图审阅与最终渲染验收两端，脚本层面只做契约检查（资产引用合法性、参数区完整性），不做逐行审阅。

失败模式是成本结构失衡：模型调用便宜、渲染贵，团队容易倾向于多跑模型少跑渲染，但 SceneCraft 的修正依赖视觉反馈，减少渲染轮数等于削弱闭环。反过来，渲染便宜、模型贵时，团队容易多跑渲染少做场景图规划，导致脚本在错误的空间关系上反复微调。两种失衡都源于没有把“场景图正确性”作为前置门禁。工程上应在脚本生成前对场景图做一次人工或规则校验，把明显错误挡在渲染之前，这是最便宜的修正点。

具体例子：一个建筑可视化团队估算单场景成本，发现三轮迭代的渲染时间占了总工时的大头，而模型调用费用相对可忽略。他们把检查渲染的分辨率与采样数下调，只保留布局可辨识的最低质量，GPT-V 仍能判断物体是否重叠、通道是否畅通；最终交付渲染单独跑一次高质量。这一调整没有改变 SceneCraft 的算法，只改变了渲染配置，却把迭代预算从“只能跑两轮”扩展到“能跑五轮”，布局质量随之提升。

五 · 合规与风险：资产版权、生成物归属与视觉安全

合规风险的第一层是资产版权。SceneCraft 依赖 Blender 资产库，脚本实例化的是库里已有的资产。若资产库包含第三方版权资产，生成场景的分发就继承该资产的许可约束。工程上必须维护资产许可清单，并在脚本的资产引用映射里标注许可类型，确保导出到下游引擎时不会把受限资产带入分发物。这一层风险与 SceneCraft 的算法无关，但它是管线集成方必须承担的接口责任。

第二层是生成物归属。SceneCraft 的产出是脚本与场景图，脚本由 LLM 生成、经智能体迭代修正，场景图由 LLM 规划。生成物的版权归属在不同法域有不同处理，工程判断是：把脚本视为“工具产出”，把人工审阅与精修视为“创作投入”，在合同层面约定归属，而不是依赖技术手段判定。library learning 沉淀的常用函数是跨场景复用的代码片段，它们可能包含从多个场景中抽象出的布局模式，这部分代码的归属需要在团队内部明确，避免跨项目复用时产生争议。

第三层是视觉安全与内容合规。SceneCraft 用 GPT-V 检查渲染图，GPT-V 的判断标准是“空间关系是否合理”，不是“内容是否合规”。若 brief 包含敏感内容，场景图规划与脚本生成可能产出不合规场景，而视觉反馈闭环不会拦截，因为它只检查布局。工程上需要在 brief 入口加内容过滤，在渲染图出口加人工或独立模型的内容审核，不能把合规责任交给 SceneCraft 的闭环。失败模式是：闭环内所有轮次都“布局正确”，但内容本身不可分发，直到下游验收才发现，此时已浪费全部迭代成本。

第四层是物理交互弱带来的隐性风险。论文明确列出物理弱这一局限：SceneCraft 生成的是布局，不保证物体之间的物理稳定性（支撑、碰撞、重力）。若场景要进入仿真、VR 交互或游戏物理系统，布局正确不等于物理正确。工程判断是：把 SceneCraft 的产出定位为“静态布局草稿”，物理校验交给下游物理引擎或人工检查。具体例子：一个 VR 团队用 SceneCraft 生成室内场景，渲染图看起来合理，但导入物理引擎后发现桌上摆放的物体悬空、书架与墙穿插，这些在单视角渲染图里不可见，GPT-V 也无法从渲染图判断。这类错误必须在物理层拦截，而不是在视觉闭环里反复修正。

六 · 上线检查清单：从试点到产线的门禁

上线检查清单的目标不是罗列功能，而是把 SceneCraft 的已知局限逐条转成可执行的门禁。第一条门禁是资产库覆盖度：场景图规划出的节点类别必须全部能在资产库中找到可实例化资产，覆盖率不足时应在场景图阶段打回，而不是让脚本执行失败。检查方式是跑一批代表性 brief，统计场景图节点与资产映射的命中率，未命中的类别进入资产补充清单。第二条门禁是场景图可审阅性：场景图必须能被人工在合理时间内读懂并否决，节点命名与关系描述要结构化，不能是自由文本。

第三条门禁是脚本契约检查：资产引用走统一映射、变换参数集中、相机灯光独立成段。这三条是下游批量改写与引擎导入的前提，缺失任何一条都会让脚本退化为一次性产物。第四条门禁是渲染配置分离：检查渲染与交付渲染必须使用不同配置，检查渲染以布局可辨识为准，交付渲染以质量为准。第五条门禁是迭代预算：明确每个场景允许的迭代轮数上限，并把场景图前置校验作为减少无效渲染的手段。迭代轮数不是越多越好，渲染慢的局限决定了轮数是稀缺资源。

第六条门禁是视觉反馈的边界：GPT-V 只对布局正确性负责，不对内容合规、物理正确性、引擎内光照负责。检查方式是给 GPT-V 的提示词里明确检查项清单（重叠、比例、通道、朝向、支撑关系），并在闭环外单独设置合规与物理校验。第七条门禁是 library learning 的库治理：沉淀的常用函数要有版本、有测试场景、有许可标注，跨项目复用前必须验证其在目标资产库上的可执行性。库函数是跨场景复用的资产，治理缺失会让错误布局模式在多个项目间传播。

  • 资产覆盖度：场景图节点类别与资产库映射命中率达标，未命中类别进入补充清单。
  • 场景图可审阅：节点命名结构化，关系边可被人快速否决。
  • 脚本契约：统一资产映射、参数集中、相机灯光独立。
  • 渲染分离：检查渲染与交付渲染配置不同，检查渲染以布局可辨识为准。
  • 迭代预算：设定轮数上限，场景图前置校验减少无效渲染。
  • 反馈边界：GPT-V 检查项限定为布局正确性，合规与物理校验在闭环外。
  • 库治理：library learning 函数有版本、测试与许可标注，复用前验证可执行性。

第八条门禁是可复现性：同一 brief 多次运行应能产出可比较的场景图与脚本，随机性来源要固定并记录，采样多次后人工选优的流程要写进作业规范。SceneCraft 无需训练，稳定性不来自模型确定性，因此复现性只能靠外部流程保证。第九条门禁是回滚路径：脚本重跑会覆盖人工精修，必须约定布局层与细节层的隔离命名，确保回滚只影响布局层。第十条门禁是验收断言：把“空间关系合理”拆成可判定的断言，例如锚点物体存在、通道宽度大于阈值、物体间无穿插、朝向符合 brief，这些断言在场景图与渲染图两个层面各跑一遍。

最后一条门禁落在工程判断上：SceneCraft 适合作为“布局起草器”进入管线，不适合作为“端到端场景生成器”承担交付责任。它的三段式链路——场景图、脚本、渲染——每一段都可被审计与替换，这正是它相对黑箱生成的优势；但它的局限——资产库依赖、渲染慢、物理弱——决定了它必须被夹在人工审阅与下游校验之间。上线检查清单的本质，是把这些局限转成管线上的检查点，让智能体的迭代闭环只负责它擅长的那一段：把文本意图翻译成结构化的、可编辑的布局脚本。
