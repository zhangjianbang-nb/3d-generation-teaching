一 · 复现边界：把论文拆成可执行的契约

CraftsMan3D 的复现难点不在单个模块，而在两段式管线的接口契约。粗生成模型输出的是网格序列或潜变量解码后的三角网格，精修器接收的是同一网格的顶点数组与面索引，并在可微渲染下反复求梯度。复现时第一件事不是找权重，而是把两段之间的数据契约写死：顶点坐标必须为 float32、面索引必须为 int64 且满足逆时针朝向约定、法线由面法线按面积加权平均得到、每个网格必须携带相机外参和内参的规范化副本。契约不写死，后面所有崩溃都会以“渲染图全黑”或“梯度为 NaN”的形式出现，排查成本极高。

论文给出的目标函数是两段式验收的数学表达：

$$\mathcal{M}_{\mathrm{coarse}}=\mathrm{Gen}_\theta(c),\qquad \mathcal{M}^{*}=\arg\min_{\mathcal{M}}\sum_v\|\hat{I}_v-I_v\|^2+\lambda\mathcal{L}_{\mathrm{reg}}$$

第一项是多视图图像重建误差，第二项是正则项。复现时要把这个式子翻译成两个独立可测的断言：粗生成阶段只验网格合法性（流形性、面数上限、退化面比例），精修阶段只验多视图误差是否单调下降。两段混在一起调，一旦 loss 不降，无法判断是粗网格拓扑坏还是渲染管线错。

一个具体的失败模式：粗生成模型输出的网格存在大量非流形边，精修器用可微渲染求顶点梯度时，光栅化对非流形面片的遮挡关系不确定，导致同一顶点在不同视图下收到矛盾梯度，loss 震荡。复现者常误以为是学习率问题，实际是契约层没有做流形清洗。工程判断是：在粗生成与精修之间插入一个纯 CPU 的网格清洗步骤，代价是数十毫秒到数百毫秒，但能消除大部分 NaN 梯度。

二 · 目录结构与最小可跑版本

最小可跑版本应把管线切成四个可独立启动的进程边界，而不是一个巨型脚本。推荐目录如下：

  • data/：存放 Objaverse 子集与内部资产的原始网格、渲染多视图、相机参数；每个资产一个目录，内含 mesh.obj、views/、cameras.json。
  • coarse/：粗生成模型的定义、tokenizer（网格序列化）、解码器与采样脚本；输出统一为 coarse_mesh.npz。
  • refine/：可微渲染器封装、多视图监督、正则项、优化循环；输入 coarse_mesh.npz 与 views/，输出 refined_mesh.npz。
  • interact/：人工交互接口，接收顶点拖拽或面片删除事件，转成精修器的额外约束。
  • asserts/：验收断言集合，每个断言一个函数，返回布尔与诊断信息。

最小可跑版本的判定标准是：给定一个 Objaverse 资产的条件输入（文本或图像），粗生成产出面数在预设上限内的闭合网格，精修在固定迭代次数内使多视图误差下降，最终网格通过全部断言。这个版本不需要训练粗生成模型，可以先用论文同类的预训练权重或小规模过拟合验证管线连通性。论文的推理时间是数十秒到数分钟，复现时要把这个区间当作性能预算：粗生成占小头，精修迭代占大头，交互接口的响应必须与精修循环解耦。

一个具体机制：粗生成的网格序列化把面片按邻接顺序排成 token 流，解码时按 token 顺序重建面片。复现者若直接复用 MeshGPT 类 tokenizer，要注意 token 词表与面片朝向的绑定关系；朝向约定不一致会让精修器的法线监督符号翻转，表现为渲染图整体偏暗。这是最常见的“看起来能跑但结果错”的崩溃点。

三 · 数据准备与多视图监督的构造

数据准备的核心是把每个 3D 资产转成“网格 + 多视图 + 相机”的三元组。Objaverse 资产数量大但质量参差，内部资产质量高但规模小，复现时应先用内部资产做小规模闭环，再用 Objaverse 子集扩规模。每个资产渲染多视图时，相机分布要覆盖上半球，避免只渲染正面导致背面拓扑无监督。相机参数必须与精修器使用的可微渲染器坐标系一致，这是数据准备阶段最容易埋雷的地方。

多视图监督的构造有一个具体机制：对每个视图渲染法线图和深度图，法线图用于约束表面朝向，深度图用于约束轮廓与遮挡。精修器的损失是图像重建误差加上正则项，正则项通常约束顶点位移幅度与面片面积变化，防止优化过程中网格自交或塌缩。伪代码思路如下：

  • 对粗网格做流形清洗与退化面删除；
  • 对每个视图用可微渲染器前向得到渲染图、法线图、深度图；
  • 计算与真值的误差，反传得到顶点梯度；
  • 按正则项惩罚顶点位移与面片形变；
  • 更新顶点，拓扑变更（边分裂、边折叠）由交互或启发式触发。

系统代价：多视图数量直接决定精修单步成本。视图数翻倍，光栅化与反传的显存和时间近似线性增长。复现时要在视图数与迭代次数之间做取舍，论文的“数十秒到数分钟”区间对应的是有限视图加有限迭代。一个具体失败模式：视图太少导致背面无监督，精修后网格背面出现孔洞或翻面；视图太多导致单步显存溢出，尤其在消费级显卡上。工程判断是先用少量视图跑通，再按显存预算增加视图，而不是一开始就堆满。

另一个崩溃点：Objaverse 资产的尺度不统一，有的以米为单位，有的以厘米为单位。精修器的正则项若按绝对位移惩罚，尺度大的资产几乎不动，尺度小的资产被过度平滑。复现时必须在数据准备阶段做尺度归一化，把每个资产缩放到单位包围盒，并在输出时记录缩放因子以便还原。

四 · 超参与验收断言

超参分两组：粗生成组与精修组。粗生成组的关键超参是采样温度、token 序列最大长度、面数上限；精修组的关键超参是学习率、迭代次数、视图数、正则权重 λ。论文没有给出具体数值，复现时只能定性设定并靠断言收敛。一个可操作的配方是：精修学习率取粗生成学习率的十分之一量级，迭代次数以多视图误差连续若干步不降为停止条件，λ 取使正则项与重建项量级相当的値。这些不是论文数字，是复现者必须自己扫的参数。

验收断言应写成可执行的检查，而不是人工目测。建议的最小断言集：

断言检查内容失败含义
网格合法性闭合、无退化面、面数不超上限粗生成解码或清洗出错
法线一致性面法线与顶点法线朝向一致朝向约定或 tokenizer 绑定错
多视图误差单调精修 loss 总体下降梯度矛盾或学习率过大
正则项有界顶点位移与面片形变不超阈值λ 过小或视图监督不足
交互可回放人工编辑事件能复现同一结果交互接口与精修循环未解耦

一个具体机制：多视图误差单调断言不能只看总 loss，要分视图看。若某一视图误差持续上升而其他下降，说明该视图相机参数错或该区域无监督，总 loss 的下降是假象。复现者常被总 loss 迷惑，最终网格在特定视角下明显破损。工程判断是把分视图误差纳入断言，任何单视图误差上升超过阈值即中止并输出诊断。

系统代价：断言集本身有运行成本，网格合法性检查在大面数网格上是 O(面数) 的邻接遍历，多视图误差检查需要额外前向。复现时把断言放在精修循环的检查点而非每步执行，避免拖慢迭代。一个具体失败模式：交互接口的事件若在精修循环中途注入，会破坏优化器的动量状态，导致回放不一致；正确做法是把交互事件转成约束项，在下一轮迭代开始时合并。

五 · 常见崩溃点与工程判断

崩溃点一：可微渲染器的光栅化对薄面片和自交面片梯度不稳定。粗网格若存在自交，精修会在自交处产生爆炸梯度。复现时要在清洗阶段做自交检测，代价是较慢的几何求交，但比调试 NaN 便宜。崩溃点二：多视图真值与渲染图的颜色空间不一致，导致重建误差有系统偏置，精修把网格往错误方向拉。复现时统一到线性颜色空间再算误差。

崩溃点三：粗生成模型的条件输入与精修器的多视图真值不是同一资产，数据准备时索引错位。这类错误表现为 loss 不降但无 NaN，极难排查。工程判断是给每个资产生成唯一哈希，粗生成输出与多视图目录都携带哈希，断言层校验哈希一致。崩溃点四：精修迭代中拓扑变更与顶点优化交替进行，若拓扑变更后没有重置优化器状态，动量会作用在已删除的顶点上。复现时在拓扑变更后重建优化器。

一个具体例子：复现者用内部资产跑通管线后换到 Objaverse 子集，发现精修时间从数十秒涨到数分钟且部分资产失败。排查发现 Objaverse 资产面数分布更宽，粗生成的面数上限对高面数资产截断过度，精修需要更多迭代补细节。工程判断是按面数分桶设定迭代预算，而不是全局固定迭代次数。这也对应论文局限中“管线复杂、慢”的定性描述：慢不是单一环节慢，而是面数分布与视图预算不匹配导致的迭代膨胀。

最后落在具体机制上：复现 CraftsMan3D 的验收核心是“分视图误差 + 网格合法性 + 哈希一致”三条断言同时成立，任何一条不成立都说明两段式管线的接口契约被破坏，此时调超参无效，必须回到契约层修数据或修清洗步骤。
