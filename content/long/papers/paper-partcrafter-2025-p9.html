一 · 管线定位：它到底插在哪一段

把 PartCrafter 放进真实生产管线，第一件事不是评估它的生成质量，而是确定它的插入点。工业资产管线通常分成五段：概念设定（原画/参考图）、建模（整体或部件级）、UV 与材质、绑定与动画、引擎集成。PartCrafter 的输入是单张图，输出是多个语义部件网格的集合 $\{\mathcal{M}_k\}_{k=1}^{K}$，因此它天然占据“概念设定 → 建模”之间的位置，替代的是原本由建模师从参考图手工拆分部件、逐个建中模的环节。它不解决 UV、材质、绑定，也不解决拓扑优化，这一点必须在管线设计时就写死，否则下游会把不可用的网格当成可用资产。

具体机制上，它的输出契约是“部件集合 + 部件语义标签”，而不是“一个整体网格”。这意味着管线接口必须从单网格流改成集合流：下游的每个处理节点都要能接受 $K$ 个网格及其索引，并保留部件边界。工程上常见的做法是给每个部件分配稳定的 part id，把 $\mathbf{z}^{(k)}$ 与 part id 绑定写入资产元数据，这样后续编辑、替换、重新生成单个部件时不会打乱整体结构。系统代价在于，原本为整体网格设计的批处理工具（自动 UV 展开、减面、碰撞体生成）大多假设输入是单一流形，遇到多部件集合时需要逐个调用并额外做一次合并或分组，管线节点数量与调度复杂度都会上升。

一个具体例子：某资产团队的原管线是“参考图 → 建模师手工拆 6 个部件 → 逐个中模 → 合并 → UV”。接入 PartCrafter 后变成“参考图 → PartCrafter 一次出 6 个部件网格 → 建模师只做拓扑清理与 UV”。中间那一步的工时被压缩，但新增了一个“部件数校验”节点：因为论文明确指出部件数预测易错，管线必须在生成后核对 $K$ 是否与参考图的语义部件数一致，不一致就退回重采样或人工指定 $K$。这个校验节点是新增的系统代价，不能省略。

二 · 上下游接口：输入契约与输出契约

上游接口的关键是图像条件 $I$。PartCrafter 不需要预分割输入，这是它相对两阶段方案的核心优势，但工程上仍要对 $I$ 做约束：单主体、背景干净、视角明确。若输入图包含多个物体或遮挡严重，全局注意力会把不同物体的部件混在一起，输出集合的语义标签就会失配。上游应当提供一个“单主体裁剪 + 视角标注”的前置节点，把 $I$ 规范化为单物体视图，并把视角信息作为条件元数据一并传入，供后续一致性检查使用。

下游接口的核心是逐部件解码的结果 $\mathcal{M}=\bigcup_{k=1}^{K}\mathrm{Dec}(\mathbf{z}^{(k)})$。这个并集在几何上不是流形合并，而是部件集合，因此下游第一个节点必须是“部件边界检测”：判断相邻部件之间是贴合、缝隙还是穿插。论文把缝隙/穿插列为局限，说明解码器逐部件出网格时并不保证接触面严格对齐。工程上可以用包围盒相交测试加最近点距离做粗筛：对每对相邻部件计算最小间距 $d_{ij}=\min_{p\in\mathcal{M}_i,q\in\mathcal{M}_j}\|p-q\|$，当 $d_{ij}$ 超过阈值判为缝隙，当包围盒重叠且表面穿透判为穿插。这个检查是纯几何的，不依赖模型内部，因此可以做成独立的后处理节点。

接口设计还要处理“部件可编辑”这一承诺。可编辑意味着每个部件是独立网格，下游的替换、缩放、旋转不能破坏其他部件。工程上应把部件集合写成场景图节点：根节点持有整体变换，子节点各自持有 $\mathcal{M}_k$ 与局部变换。这样铰接动画的骨骼可以直接绑定到子节点，而不需要先把整体网格切开。系统代价是场景图序列化格式要支持多网格引用，原本的单文件资产格式需要扩展，资产库的索引结构也要从“一个资产一个网格”改成“一个资产多个部件网格”。

一个具体例子：引擎集成节点接收部件集合后，按 part id 生成碰撞体。若某部件被判为缝隙过大，碰撞体之间会出现可穿越的空洞；若被判为穿插，碰撞体会互相嵌入导致物理抖动。因此边界检测节点的输出必须作为引擎集成的门禁，而不是可选的质检项。

三 · 成本结构：训练侧与推理侧的分账

成本要分两笔账。训练侧，PartCrafter 继承预训练网格 DiT 权重，在带部件标注的 3D 数据上做组合式去噪训练，论文给出的量级是“数天”。这笔成本主要落在数据上：部件标注数据是稀缺资源，论文使用的数据集是 Objaverse 部件标注与内部资产，说明公开部件标注的覆盖有限，内部资产标注是必需补充。工程判断是，训练侧的成本不在算力而在标注管线：要建立“整体资产 → 语义部件拆分 → 部件标签”的标注规范，并保证标注粒度与推理时的部件数 $K$ 一致。标注粒度不一致会直接表现为部件数预测偏差。

推理侧，论文给出的量级是“数十秒”。这个数字决定了它在管线中的角色：它不是实时交互组件，而是离线或准离线的资产生成节点。数十秒意味着单次生成可以放进批处理队列，但不适合放在建模师的交互循环里等待。工程上应把它做成异步任务：提交参考图与部件数提示，后台生成，完成后推送部件集合与质检报告。系统代价是任务队列与结果缓存的基础设施，以及失败重试策略——部件数错误与缝隙/穿插是两类不同的失败，前者应重采样，后者应进入几何修复而非盲目重试。

$$\text{cost}_{\text{total}} = N_{\text{train}}\cdot c_{\text{label}} + N_{\text{infer}}\cdot\left(t_{\text{gen}}\cdot c_{\text{gpu}} + c_{\text{qc}}\right)$$

这个式子把成本拆成标注、生成、质检三项。质检项 $c_{\text{qc}}$ 常被低估：部件数校验、边界检测、拓扑清理都是人工或半自动环节，在部件级生成里它们不可省略，因为模型本身不保证这些性质。一个具体例子：批量生成 100 个资产，若部件数错误率为可观水平，重采样会放大生成成本；若缝隙/穿插需要人工修复，质检成本会超过生成成本。因此上线前必须测出这两个失败率，用它们反推队列容量与人力配置，而不是只看单次生成耗时。

四 · 合规与数据风险：部件标注的来源问题

合规风险集中在训练数据。部件标注数据要求对 3D 资产做语义拆分，这类标注往往来自内部资产库或第三方资产，其许可条款决定了生成模型能否商用。工程上要建立数据血缘：每个训练样本记录来源、许可类型、是否允许衍生生成。论文使用 Objaverse 部件标注与内部资产，说明数据来源是混合的，混合来源意味着许可条款不一致，上线前必须按来源分层审计，不能把“公开数据集 + 内部资产”当成同质数据。

第二个风险是生成结果的衍生性。PartCrafter 的输出是部件网格，若训练数据中包含受保护的设计（例如特定品牌的产品结构），模型可能复现其部件划分与几何特征。工程判断是，在管线中加一个“相似度筛查”节点：把生成部件与训练集中受保护资产做几何特征比对，命中则标记为需人工复核。这个节点不依赖模型内部，属于资产合规流程的一部分。

第三个风险是部件语义标签的歧义。同一个几何拆分可以对应不同语义命名（例如“外壳”与“上盖”），若下游绑定或动画依赖语义标签，标签不一致会导致绑定错误。工程上应把语义标签做成受控词表，生成时由上游指定候选标签集，而不是让模型自由命名。系统代价是词表维护与标签映射，但它把“可编辑”从几何层面提升到语义层面，是部件级资产真正可用的前提。

五 · 上线检查清单

以下清单按管线顺序排列，每项都对应一个可验证的断言，而不是笼统的“质量检查”。

  • 输入规范化：$I$ 为单主体、背景干净、视角标注存在；断言为“输入图只含一个语义主体”。
  • 部件数契约：上游给出期望 $K$ 或候选范围；断言为“输出部件数落在给定范围内”，否则重采样。
  • 语义标签受控：每个部件标签来自受控词表；断言为“无词表外标签”。
  • 边界检测：对相邻部件计算最小间距与包围盒重叠；断言为“无超阈值缝隙、无表面穿透”。
  • 拓扑清理：逐部件检查流形性、退化面、自交；断言为“每个部件可被下游 UV 工具接受”。
  • 场景图序列化：部件集合写成根节点 + 子节点结构，part id 稳定；断言为“单部件替换不改变其他部件索引”。
  • 数据血缘：训练样本来源与许可可追溯；断言为“商用生成可回溯到许可允许的来源”。
  • 相似度筛查：生成部件与受保护资产比对；断言为“命中项进入人工复核队列”。
  • 成本核算：记录生成耗时、重采样次数、质检工时；断言为“单资产总成本不超过预算阈值”。

这份清单的工程含义是：PartCrafter 把“生成”这一步变简单了，但把“校验”这一步变复杂了。部件级生成的价值在于可编辑与结构化，而这两点恰恰依赖生成之后的部件数、边界、语义、序列化四项检查。上线判断不应落在“生成质量是否足够好”，而应落在“校验节点是否把模型的已知失效模式全部拦住”。论文明确列出的失效模式是部件数易错、缝隙/穿插、数据需求，检查清单的前四项正是对这三条的工程回应。

最后一个具体机制层面的判断：逐部件解码意味着每个 $\mathrm{Dec}(\mathbf{z}^{(k)})$ 是独立调用，部件之间没有共享拓扑。若下游需要水密整体网格，必须在部件集合之上再做一次布尔合并或缝合，而这一步会引入新的几何误差，且合并后的网格不再可独立编辑。因此管线设计要在“可编辑集合”与“水密整体”之间二选一，不能既要求部件独立又要求整体水密而不付缝合代价。这个取舍应写进资产规范，而不是留到集成阶段才发现。
