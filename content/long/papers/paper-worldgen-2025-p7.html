一 · 对照基线：三个方法各自的“表示承诺”

把 WorldGen 与 Text2Room、WonderWorld、SceneCraft 放在一起比较，第一步不是比分数，而是比“表示承诺”——每个方法在生成开始前就押注了一种场景表示，这个押注决定了它后面能做什么、不能做什么。Text2Room 的表示承诺是“单目图像加深度外扩”：它以一张或多张图像为种子，用深度估计把像素反投影成点云/网格，再向外扩生成新视角。它的世界是一层“壳”，房间级尺度内视觉连续性好，但壳之外没有实体，也没有物体身份。WonderWorld 的承诺是“单图外扩加可交互高斯”：从一张图出发扩展出可探索的场景，用高斯泼溅承载外观，并允许用户在场景里“走进去”产生局部交互。它的强项是快速、视觉讨喜、单图入口门槛低，但世界尺度受限于外扩的视野半径，且缺少显式的物体级结构。SceneCraft 的承诺是“LLM 写脚本驱动 3D 资产摆放”：让大模型输出一段程序，调用资产库把物体摆到场景里。它的世界是“符号化摆放”的，布局可控、可编辑性强，但资产来自库而非生成，风格与几何多样性受库容量约束，且地形/大尺度结构不是它的重点。

WorldGen 的表示承诺是四层复合：LLM 场景图（符号层）、程序化地形（结构层）、扩散物体（资产层）、object-aware 分解（组合层）。这个承诺的代价是系统复杂度，收益是“可穿越、可交互、可进引擎”三个属性同时成立。对照时要把这个差异讲清楚：前三个方法各自只覆盖了 WorldGen 四层中的一到两层，所以它们不是“更弱的 WorldGen”，而是“不同承诺下的不同系统”。

方法核心表示覆盖的世界层尺度上限的决定因素
Text2Room图像+深度反投影的壳层外观层（弱结构）外扩视野与深度一致性
WonderWorld单图外扩+可交互高斯外观层+局部交互单图入口与外扩半径
SceneCraftLLM 脚本+资产库摆放符号层（弱地形）资产库容量与脚本正确性
WorldGenLLM 布局+程序化+扩散+分解符号/结构/资产/组合四层布局推理质量与资产生成吞吐

这张表本身就是一个工程判断工具：如果你的需求是“从一个房间照片快速得到可看可走的空间”，WonderWorld 或 Text2Room 的表示承诺更匹配；如果你的需求是“布局必须精确可控、物体必须可替换”，SceneCraft 的符号承诺更匹配；只有当需求同时包含“大尺度地形、物体级交互、引擎导出”时，WorldGen 的四层复合才成为必要而非过度设计。

二 · 监督信号：谁在“教”系统什么是合理的世界

四个方法的监督结构差异极大，这直接决定了它们的失败模式形状。Text2Room 的监督来自预训练深度估计与图像生成模型的先验，没有显式的 3D 真值监督；它的“合理”是视觉上的合理，深度尺度漂移和几何穿插是它的典型病。WonderWorld 同样依赖单图先验与外扩过程中的一致性约束，交互性来自用户触发的局部编辑而非全局物理规则，所以它的“合理”是局部视觉合理加局部响应合理。SceneCraft 的监督主要是 LLM 的常识与脚本执行的成功率：布局合理性由语言模型的世界知识兜底，几何合理性由资产库兜底，二者之间没有联合优化，脚本写错或资产尺寸不匹配就会暴露。WorldGen 的监督是分层的：LLM 布局由语言先验与场景图约束监督，程序化地形由规则与参数监督，扩散物体由 3D 生成模型的预训练分布监督，object-aware 分解则提供一个组合阶段的一致性/可分解性约束。它不是端到端训练，而是“各自预训练 + 系统级组合”，这一点在对照时必须强调：WorldGen 的监督不是单一损失，而是一组异构监督在组合层的拼接。

$$\mathcal{W}=\mathrm{Compose}\!\left(\mathrm{Layout}_{\mathrm{LLM}}(t),\mathrm{Terrain}_{\mathrm{proc}},\{\mathrm{Gen}(o_i)\}\right)$$

这个组合式目标意味着：当最终世界出现问题时，归因必须逐层做。布局错了是 LLM 场景图的问题；地形穿模是程序化参数与布局尺度不匹配；物体悬空或比例失调是扩散资产与放置变换的问题；组合缝隙是 object-aware 分解的优化不足。对照实验里，Text2Room 的失败几乎总能归因到深度尺度，WonderWorld 的失败几乎总能归因到外扩一致性，SceneCraft 的失败几乎总能归因到脚本或资产库，而 WorldGen 的失败是“多层可归因”的——这既是它的诊断优势，也是它的运维负担。一个具体例子：文本要求“山谷里有一座桥连接两岸”，WorldGen 需要 LLM 先给出桥与两岸的相对位置和尺度，程序化地形要保证两岸高度差在桥的可跨越范围内，扩散要生成桥体资产，分解要把桥两端对齐到岸沿；任何一层偏差都会让桥悬空或插入地面。而在 SceneCraft 里，同样的需求会退化成“从库里挑一座桥放到坐标上”，地形不存在，所以“对齐”问题根本不会出现，但“世界感”也不会出现。

监督差异还带来一个工程代价：WorldGen 的每一层都需要独立的验收断言。布局层要断言场景图的对象数量、类别覆盖与相对位置约束；地形层要断言高度场范围与坡度分布；资产层要断言网格水密性、面数与包围盒比例；组合层要断言物体与地形的接触关系与无穿插。对照方法只需要一到两条断言，WorldGen 需要四条以上，这就是“系统复杂”的具体含义，而不是一句定性描述。

三 · 速度与显存：组合式管线的吞吐账

速度对比不能只看“生成一个世界要多久”，而要看“瓶颈在哪一层、能否并行、失败重试的成本”。Text2Room 的耗时主要在外扩循环：每扩一个视角就要跑一次图像生成加深度估计，耗时随视角数线性增长，显存峰值由图像生成模型与点云/网格缓存共同决定。WonderWorld 的单图入口使其首帧响应快，但外扩与高斯优化会随探索范围增加而累积显存，交互编辑还会引入额外的优化步。SceneCraft 的耗时主要是 LLM 脚本生成与资产加载，脚本一次生成、执行快，显存占用低，但脚本失败需要重写，重试成本落在语言模型调用上。WorldGen 的耗时是四段串联：LLM 布局推理（一次调用，可缓存）、程序化地形（CPU 侧为主，快且确定）、扩散物体生成（按物体数量线性增长，是主要瓶颈）、object-aware 分解与放置（优化迭代，随物体数与场景复杂度增长）。显存峰值通常出现在扩散资产生成与分解优化同时驻留的阶段。

方法速度瓶颈并行性显存主要占用重试成本
Text2Room外扩视角循环视角间弱并行图像生成模型+几何缓存局部重扩，较低
WonderWorld外扩+高斯优化探索区域可分批高斯表示随范围增长局部编辑，较低
SceneCraftLLM 脚本生成脚本内资产加载可并行资产库加载，低重写脚本，中
WorldGen扩散物体生成物体级可并行扩散模型+分解优化驻留单物体重生成，中高

这里有一个具体的工程判断：WorldGen 的物体级并行是它相对前三个方法的结构性优势。因为物体是独立生成的，{Gen(o_i)} 可以在物体粒度上批处理或分布式生成，吞吐随 GPU 数近似线性提升；而 Text2Room 的外扩是顺序依赖的，WonderWorld 的外扩也受已探索区域约束，SceneCraft 的瓶颈在单次 LLM 调用上无法并行。代价是 WorldGen 的显存峰值更难压：扩散模型与分解优化器同时在场，且物体越多、分解优化的迭代矩阵越大。一个可操作的缓解手段是把“生成”和“组合”分成两个阶段，生成阶段只保留资产与元数据，组合阶段再加载场景，用磁盘换显存；但这会引入资产落盘的 I/O 开销与版本一致性问题。对照方法没有这个两阶段问题，因为它们的表示本身就是流式的。

四 · 失败模式逐项对照

失败模式的对照要落到“可观测现象 + 归因层 + 修复路径”三件事上，否则只是罗列。Text2Room 的典型失败是深度尺度漂移导致的外扩几何扭曲、以及大角度转身后的“壳层断裂”——现象是墙面错位或出现空洞，归因在深度估计的先验误差，修复路径是限制外扩角度或引入多视图一致性，但根本上是表示承诺的天花板。WonderWorld 的典型失败是外扩边界处的视觉退化与交互编辑后的局部不一致——现象是远处模糊、编辑区域与周围风格脱节，归因在单图先验的覆盖不足与高斯优化的局部性，修复路径是增加入口视图或约束编辑范围。SceneCraft 的典型失败是脚本语义错误与资产尺寸/朝向不匹配——现象是物体悬空、穿墙、比例荒谬，归因在 LLM 空间推理的不可靠与资产库元数据的不完整，修复路径是加后处理碰撞检查或人工修正脚本。

WorldGen 的失败模式是前三者的“分层版本”，且每一层都有独立的可观测现象。布局层：LLM 场景图可能给出物理上不成立的布局（比如把建筑放在陡坡上、把水体放在山脊），现象是后续地形与放置冲突，归因在语言先验缺乏几何可行性约束。地形层：程序化参数与布局尺度不匹配会导致地形起伏超出物体放置的容差，现象是物体半埋或悬空。资产层：扩散生成的物体质量参差，现象是网格不水密、面数异常、纹理拉伸，归因在 3D 生成模型的分布覆盖与采样随机性。组合层：object-aware 分解的优化可能收敛到局部最优，现象是物体之间的接触关系错误或缝隙可见。这四类失败在对照实验里必须分开统计，否则“WorldGen 失败率高”这个结论没有工程意义——因为它的失败可以定点修复，而 Text2Room 的壳层断裂是表示层的，修复成本高得多。

  • 布局失败：场景图对象关系违反几何可行性，需在 LLM 输出后加规则校验器。
  • 地形失败：高度场与放置容差冲突，需把地形参数暴露为布局的可查询约束。
  • 资产失败：单物体质量不达标，可重采样或替换，不影响全局。
  • 组合失败：接触与穿插错误，需在分解优化里加接触约束与迭代上限。

一个具体例子能说明这种分层归因的价值：文本“雪山上有一座小屋，屋前有篝火”。若小屋半埋进雪坡，问题在地形层（坡度与放置点高度不匹配），修复是调整程序化地形参数或移动放置点；若篝火悬空，问题在组合层（接触约束缺失），修复是加地面吸附；若小屋本身破面，问题在资产层，重生成即可。而在 Text2Room 里，同样的场景只能靠外扩图像“看起来对”，一旦视角偏离就露馅，且没有可定点修复的层。

下面这张决策表把前面的对照压缩成工程选择规则。读法是：先确定你的第一优先级需求，再看对应方法的表示承诺是否覆盖它，最后看失败模式是否可接受。表中不写“最好”，只写“匹配”。

决策表里有两个容易被忽略的判断。第一，“可进游戏引擎”是一个硬门槛：Text2Room 与 WonderWorld 的输出是视觉表示（网格/高斯），进引擎需要额外的碰撞体、材质与 LOD 处理，且壳层没有实体语义，交互逻辑无从挂载；SceneCraft 的输出是摆放好的资产，进引擎相对直接但地形与大规模结构缺失；WorldGen 的输出从设计上就面向引擎导出，布局、地形、物体都带语义与变换，这是它区别于前两者的结构性差异，而不是“导出格式多几种”。第二，“可编辑”的粒度不同：SceneCraft 的编辑是替换库中资产与改脚本，粒度粗但确定；WorldGen 的编辑可以到单物体重生成与布局重推理，粒度细但每次编辑都可能触发组合层重优化，编辑成本随场景规模上升。工程上要按编辑频率选：低频编辑选 WorldGen 的细粒度，高频编辑选 SceneCraft 的确定性。

六 · 对照实验的设计要点与工程结论

做这四个方法的对照实验，最容易犯的错误是“用同一个文本提示、同一个评测脚本”就宣布公平。实际上，四个方法的输入契约不同：Text2Room 与 WonderWorld 更适合图像入口，SceneCraft 与 WorldGen 是文本入口；把它们放在同一文本提示下，前两者需要额外的文生图步骤，这一步的误差会污染对比结论。正确的对照设计是“按入口契约分组”：图像入口组比 Text2Room 与 WonderWorld 的视觉连续性与外扩稳定性；文本入口组比 SceneCraft 与 WorldGen 的布局可控性与世界尺度；跨组只比“是否可穿越、是否可进引擎”这类二元属性，不比连续分数。此外，WorldGen 的评测必须分层报告，把布局、地形、资产、组合四类的成功率分开，否则一个总分会掩盖“资产层差但布局层好”这种可修复的结构。

还有一个系统代价必须写进对照结论：WorldGen 的复现门槛是四个预训练组件加一个组合优化器，任一组件版本变化都会改变最终世界分布，所以它的对照实验需要固定组件版本并记录组合参数；而 Text2Room 与 WonderWorld 的复现门槛主要是图像/深度模型版本，SceneCraft 的门槛是 LLM 与资产库版本。这意味着 WorldGen 的实验可复现性成本最高，但它的失败可定点修复性也最好。工程判断落在具体机制上：如果你的团队没有能力维护四层组件与分层验收断言，WorldGen 的组合式路线会把“生成失败”变成“运维失败”；反过来，如果你的产品需求确实要求大尺度、可交互、可进引擎，那么前三个方法的表示承诺在结构上就无法覆盖，此时 WorldGen 的系统复杂度不是可选成本，而是需求本身的映射。对照实验的最终产出不应是一张排名表，而应是一张“需求—表示承诺—失败模式—修复路径”的映射表，决策表只是它的压缩形式。
