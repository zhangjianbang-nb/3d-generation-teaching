一 · 管线定位：WorldGen 在生产栈中的真实坐标

把 WorldGen 放进真实生产管线，第一件事不是问它“能不能生成一个世界”，而是问它“替代了管线里的哪一段”。论文给出的组合式结构决定了它不是一个可以塞进任意位置的通用黑盒，而是一个横跨三段的复合体：布局推理段、地形与建筑段、资产生成段。它上游接的是文本或结构化需求，下游接的是引擎可加载的场景描述与资产包。中间它自己承担了从语义到空间、从空间到几何、从几何到可交互实体的全部转换。这意味着在工程上它更像一条“世界装配线”，而不是一个“世界生成器函数”。装配线的每一段都有独立的失败模式和独立的成本曲线，任何一段出问题都会让整条线的产出不可用，而不是像单模型那样只影响局部质量。

具体机制上，WorldGen 的输出可以拆成三类交付物：布局层（LLM 产出的场景图与尺度约束）、地形层（程序化生成的高度场与建筑体块）、资产层（扩散模型生成的物体网格及其 object-aware 分解结果）。这三类交付物在引擎里的生命周期完全不同。布局层是数据，可以版本化、可以 diff、可以人工审阅；地形层是确定性程序化产物，同一个种子可以复现；资产层是概率性产物，同一个 prompt 每次采样都可能不同。工程判断的关键在于：不要把这三层混成一个“生成结果”来管理，否则回滚、审计、增量更新全部失效。一个具体例子是，当美术团队要替换某个建筑风格时，如果资产层与布局层耦合在一起，就必须重跑整条管线；如果分层管理，只需替换资产层的风格 prompt 并保留布局与地形，重生成成本下降一个量级。

系统代价在这里体现为接口复杂度。论文的公式把世界定义为布局、地形、资产生成的组合：

$$\mathcal{W}=\mathrm{Compose}\!\left(\mathrm{Layout}_{\mathrm{LLM}}(t),\mathrm{Terrain}_{\mathrm{proc}},\{\mathrm{Gen}(o_i)\}\right)$$

这个 Compose 不是一次函数调用，而是一个需要定义坐标系约定、尺度单位、资产锚点、碰撞体映射的装配协议。工程上最常见的失败模式是坐标系与尺度不一致：LLM 布局给出的可能是抽象网格坐标，程序化地形给出的是米制高度场，扩散资产给出的是归一化包围盒。三者没有统一的单位约定时，Compose 会在引擎里表现为物体悬浮、穿地、比例失真。这不是模型能力问题，是接口契约问题，必须在管线设计阶段用显式 schema 固定下来。

二 · 上下游接口：输入契约与导出契约

上游接口的核心是文本到布局的契约。WorldGen 用 LLM 做布局推理，但生产管线不能接受“一段自由文本进、一个世界出”的松散接口。可用的输入契约至少要包含：世界类型与尺度范围、必须出现的功能区域、风格约束、可穿越性要求（哪些区域必须连通）、交互实体清单。这些约束不是给 LLM 的提示词装饰，而是下游验收断言的来源。例如“必须连通”这一条，在布局阶段就决定了场景图必须是连通图，程序化地形阶段必须保证路径不被水体或陡坡切断，资产阶段必须保证门洞尺寸可通过。三个阶段的约束是同一条语义在不同表示上的投影，接口设计要把这条投影链显式化。

下游导出契约的核心是引擎可加载性。论文强调输出“可进游戏引擎”，工程上这意味着至少四类数据必须齐备：网格与材质、碰撞体、实体语义标签、光照与导航信息。扩散生成的物体网格通常不带碰撞体，object-aware 分解给出的是部件级语义，但部件到碰撞体的映射需要额外规则。一个具体机制是：对每个分解出的 object，按其语义标签查表决定碰撞体类型——建筑体块用凸包或盒体，植被用简化胶囊，可交互道具用精确网格。这个查表规则是工程资产，不是论文内容，但它决定了导出是否可用。失败模式很直接：如果碰撞体生成被跳过，世界在引擎里“看起来能穿越”，实际角色会穿墙或卡在几何缝隙里，可穿越性断言失败。

接口层还需要一个中间表示来承载 object-aware 分解的结果。论文的组合式路线依赖把世界拆成 object 再组合，这个“拆”的粒度必须在接口里固定。粒度过粗，资产替换不灵活；粒度过细，装配协议爆炸。工程上的折中是三层粒度：区域级（地形块与建筑群）、实体级（建筑、道具、植被）、部件级（门窗、屋顶、装饰）。导出时区域级用于流式加载，实体级用于碰撞与交互，部件级用于资产替换与 LOD。这个三层结构不是论文给出的，而是把论文的分解思想落到管线后的必然产物。

下表给出接口契约的最小字段集，用于在管线设计评审时逐项确认：

接口方向字段缺失后果
上游输入尺度范围与单位布局与地形尺度失配，物体悬浮或穿地
上游输入连通性要求可穿越断言无法验收，路径被地形切断
上游输入交互实体清单引擎侧交互逻辑缺锚点
下游导出碰撞体映射规则角色穿墙，可穿越性名存实亡
下游导出实体语义标签交互与导航无法按语义查询
下游导出区域级流式边界大尺度世界无法分块加载

三 · 成本结构：三段各自的账单

成本必须按三段分开算，因为三段的成本驱动因子完全不同。布局段的成本主要是 LLM 推理的 token 成本与重试成本。LLM 布局推理的输出是场景图，场景图的规模随世界尺度增长，token 消耗随之增长；更关键的是布局失败的重试成本——当 LLM 给出的布局违反连通性或尺度约束时，需要重新推理，而每次重试都是一次完整的长上下文调用。工程上的控制手段是把布局推理拆成“全局骨架 + 局部填充”两级：全局骨架只决定区域划分与连通关系，token 量可控；局部填充按区域并行，失败只重试局部。这个拆分不改变论文的方法，但改变了成本曲线，把线性增长的长上下文成本转成可控的分块成本。

地形段的成本是程序化生成的算力与确定性复现的存储成本。程序化地形本身算力不高，但它是确定性的，意味着同一个种子必须能复现同一地形。工程上必须把种子与参数一起版本化，否则布局调整后地形无法复现，整条管线失去可回滚性。失败模式是种子漂移：布局阶段微调了区域边界，地形阶段用了新种子，结果地形与布局对不上，路径被切断。这不是算力问题，是版本管理问题。

资产段的成本是大头，且是概率性的。扩散模型生成物体，每个 object 一次采样，采样次数随实体数量线性增长。成本驱动因子有三个：实体数量、单实体采样次数（用于筛选）、以及失败重采样率。工程上的控制手段是分级采样：对视觉焦点区域的高重要性实体用多次采样加筛选，对背景实体用单次采样加后处理。这个分级不是论文内容，但它把资产成本从“实体数量 × 固定采样数”变成“重要性加权采样预算”。系统代价是筛选环节需要人工或自动质量评估，而论文明确指出资产质量参差、评测缺标准，这意味着自动筛选本身就是一个未解决的工程问题。一个具体例子是：生成一片森林，树木作为背景实体可以单次采样，但若某棵树恰好位于玩家必经路径的视觉焦点，单次采样的低质量会直接暴露，分级策略必须能识别这种位置重要性。

三段成本叠加后，整条管线的成本不是三段之和，而是三段之积的失败率放大。任何一段的失败都会触发上游重跑：资产质量不合格可能触发资产重采样，也可能触发布局调整（因为某个区域实体太密集导致采样预算不够）。工程判断是：必须为每段设置独立的验收门，门不过则只重跑该段，禁止跨段级联重跑。这是控制成本爆炸的唯一结构性手段。

四 · 合规风险：资产来源、文本来源与可审计性

合规风险的第一层是资产来源。扩散模型生成的物体网格，其训练数据来源决定了产出是否可商用。论文没有给出训练数据的授权细节，工程上不能假设生成资产天然干净。可用的控制手段是资产溯源标签：每个生成资产记录模型版本、prompt、采样种子、后处理链。这个标签不解决授权问题，但它让审计成为可能——当某个资产被质疑时，可以回溯到生成路径而不是面对一个无来源的二进制网格。失败模式是标签缺失导致整批资产无法举证，只能全部弃用，成本按整批计。

第二层是文本来源。上游输入文本可能来自用户、来自策划文档、来自第三方 IP。LLM 布局推理会把文本语义投影到空间结构，如果文本包含受保护的世界观设定，布局层可能间接复制了受保护的空间关系。这不是模型侵权，是管线把侵权文本转化成了可用产出。工程上的控制是在上游接口加文本来源标记，并对标记为第三方的文本走人工审阅门，而不是自动放行。这个门不是技术问题，是流程问题，但它必须被写进上线检查清单，否则技术团队会默认“文本是输入，责任在输入方”，而产出已经进入了资产库。

第三层是可审计性，这一层最容易被忽略。WorldGen 是组合式系统，产出是布局、地形、资产三层的组合。审计要求能回答“这个世界的这个部分是怎么来的”。如果三层没有独立的版本标识与装配日志，审计无法进行。具体机制是装配日志：每次 Compose 记录三层各自的版本哈希、装配参数、以及被替换的实体清单。这个日志的成本是存储与写入开销，但它是合规的底线。失败模式是产出被质疑时无法定位责任段，只能整世界下架。工程判断是：装配日志的粒度必须到实体级，区域级太粗，无法定位单个争议资产。

五 · 上线检查清单：从管线门到验收断言

上线检查清单必须按管线段组织，每段有独立的门与断言，禁止用“整体看起来不错”作为通过标准。以下清单把论文的方法落到可执行的工程门上，每一条都对应一个具体失败模式。

  • 布局门：场景图必须是连通图，连通性断言在布局输出上直接跑图算法验证，不通过则重跑布局段，不进入地形段。
  • 尺度门：布局坐标、地形高度场、资产包围盒三者单位统一，用一组标定实体（门、台阶、角色身高）做交叉验证，任一实体比例失真则阻断。
  • 地形门：种子与参数版本化，同一版本必须复现同一地形；路径连通性在地形上重验，防止布局连通但地形切断。
  • 资产门：每个实体有溯源标签；碰撞体映射规则已应用；焦点区域实体经过多次采样筛选，背景实体经过后处理；资产质量抽检不通过则只重跑资产段。
  • 装配门：装配日志到实体级；三层版本哈希齐全；被替换实体清单可查。
  • 引擎门：导出包在目标引擎版本上加载成功；可穿越性用自动寻路跑通至少一条从入口到出口的路径；交互实体锚点可被引擎逻辑查询到。
  • 合规门：上游文本来源标记齐全；第三方文本走人工审阅；资产溯源标签可导出供审计。
  • 回滚门：任一段失败可独立回滚到上一版本，不触发跨段级联重跑；回滚后装配日志更新。

这份清单的关键不是条目多，而是每条都绑定了“失败时只重跑哪一段”。论文明确指出系统复杂是主要局限，复杂性在工程上的表现就是失败会级联。清单的作用是把级联切断，让每一段成为可独立验收、可独立回滚的单元。一个具体例子是引擎门里的寻路断言：它不检查视觉质量，只检查拓扑可穿越性，这样即使资产质量参差，只要拓扑通过，世界就可用，资产质量问题被隔离在资产门里单独处理。这种隔离是组合式系统能在生产管线里存活的前提。

最后落在装配协议上：WorldGen 的生产价值不在于它生成了多好看的世界，而在于它把世界拆成了可分别验收、分别回滚、分别审计的三层。上线检查清单的本质是把这三层的接口契约写成可执行的断言。工程判断是：如果团队无法为每一层写出独立的验收断言，就不具备把 WorldGen 放进生产管线的条件，因为系统复杂性会以级联失败的形式吞掉所有局部收益。装配协议里的坐标系约定、尺度单位、碰撞体映射规则、装配日志粒度，这四项是管线能否运转的最小充分条件，缺任何一项，可穿越与可交互就退化成不可验收的口号。
