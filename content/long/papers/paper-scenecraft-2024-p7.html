一 · 对照坐标：把“同期/后继”拆成可比的四个轴

把 SceneCraft 放进对照实验，先要拒绝“谁更强”这种笼统问法。SceneCraft 的输入是文本、输出是 Blender Python 脚本，中间强制经过场景图与渲染回看；这决定了它与另外两类方法根本不在同一坐标系里。第一类是“直接 LLM 写脚本”的朴素基线，它同样落在 Blender 代码空间，但没有显式场景图，也没有视觉回环；第二类是 Text2Room 这类以房间为单位的生成方法，它输出的是带纹理的几何/网格，而不是可编辑的脚本与资产引用；第三类是同期的 LLM 布局路线（以 WorldGen 为代表），它把 LLM 用在空间布局推理上，产出的是布局参数而非完整可执行程序。因此本部分的对比必须固定四个轴：表示（场景被编码成什么）、监督（靠什么信号纠错）、速度（一次成品的端到端时延构成）、显存（峰值占用来自哪里），再外加一个失败模式轴。只有把轴钉死，逐项对比才有工程意义；否则“SceneCraft 能生成上百资产”与“Text2Room 能生成可漫游房间”就是两句无法互相证伪的话。

表示轴的差异最直接。SceneCraft 的中间表示是场景图：节点是物体，边是空间关系（在……之上、贴墙、面向……），随后由 LLM 把关系翻译成数值约束写进脚本。直接写脚本的基线没有这层，LLM 在一次前向里同时承担“想清楚布局”和“写对 API”两件事，错误无法定位到具体环节。Text2Room 的表示是逐视角生成的深度/纹理场，最终融成网格，物体身份是隐式的，改一个椅子的位置意味着重生成一片区域。WorldGen 的表示是布局参数（位置、朝向、尺寸），它天然可编辑，但不含材质、不含渲染管线。四种表示对应四种“可修改的最小单元”：场景图节点、脚本语句、网格面片、布局框。工程上判断一个方法是否适合你的管线，本质上是问“我的迭代单位是什么”，而不是问它的 demo 好不好看。

监督轴决定迭代成本。SceneCraft 的监督信号是 GPT-V 对渲染图的视觉检查，属于“渲染—看图—改代码”的闭环，每一轮都要真实跑一次 Blender 渲染，代价高但信号直接对应最终观感。直接写脚本的基线通常没有闭环，或只有语法/运行时异常检查，属于“编译通过即交付”，物体重叠和比例错误这类语义缺陷完全漏检。Text2Room 的监督来自生成模型自身的先验与视角一致性约束，没有外部符号检查，因此它不会报“这把椅子穿墙了”，只会把穿墙画得看起来合理。WorldGen 的监督主要是 LLM 对布局约束的自洽性推理，缺少像素级验证。四者的监督强度排序不是单调的：SceneCraft 信号最贴近成品但最贵，WorldGen 最便宜但最不接地，Text2Room 居中但不可符号化纠错。

$$\text{Cost}_{\text{iter}}=\underbrace{C_{\text{plan}}}_{\text{LLM 规划}}+\underbrace{C_{\text{code}}}_{\text{脚本生成}}+\underbrace{C_{\text{render}}}_{\text{Blender 渲染}}+\underbrace{C_{\text{vlm}}}_{\text{GPT-V 检查}}$$

上式把一次迭代的成本拆成四项，是后面速度与显存对比的共同底座。SceneCraft 的迭代成本里 C_render 与 C_vlm 占主导，因为每个场景要迭代数轮，每轮都要出图再送视觉模型；直接写脚本的基线通常只有 C_code（外加一次渲染用于展示），所以它的“快”是以放弃语义纠错换来的。Text2Room 的成本结构完全不同：它没有 C_code，但生成过程本身是多次前向的扩散/生成采样，成本随视角数增长。WorldGen 的成本几乎只有 C_plan，所以它在速度轴上占优，却在表示轴上丢失了可执行性。把成本拆开之后，“SceneCraft 渲染慢”这句局限就不再是模糊抱怨，而是可定位的：慢在 C_render 乘以迭代轮数，且这一项无法用更快的 LLM 抵消。

二 · 表示与监督的逐项对照

先看表示维度上的具体机制差异。SceneCraft 的场景图不是装饰性的中间产物，它承担了“把自然语言的空间谓词离散化”的职责：文本里的“靠墙”“在桌子左边”被转成场景图里的边，再由脚本生成阶段转成坐标与旋转约束。这一步使得 LLM 的两次调用各司其职——第一次只做关系推理，第二次只做代码合成，错误可以被归因。直接写脚本的基线把两步压成一步，LLM 必须在生成 `bpy.ops.mesh.primitive_cube_add(location=...)` 的同时心算布局，结果是物体重叠与比例错误高发，且渲染崩（脚本异常）与语义错（布局不合理）混在一起，调试时无法区分是 API 用错还是空间想错。这是表示选择带来的可调试性差异，而不是模型能力差异。

Text2Room 的表示是视角中心的，它的“物体”是生成出来的像素与深度，没有符号身份。这带来一个具体后果：它无法响应“把这把椅子换成另一把”这种指令，因为不存在“这把椅子”这个可寻址实体；而 SceneCraft 的场景图节点天然可寻址，改一个节点只需重生成对应脚本片段。代价是 SceneCraft 被资产库绑死——场景图节点必须映射到 Blender 资产库中存在的物体，库里没有的东西就表达不了。Text2Room 不受资产库限制，但也不提供资产级编辑。WorldGen 的布局框同样可寻址，但框里没有几何与材质，需要下游补齐。三者在“可寻址性”与“资产自由度”上构成明确的取舍三角，没有一项能同时占两头。

监督维度上，SceneCraft 的 GPT-V 回环有一个容易被忽略的机制细节：视觉检查的输入是渲染图，输出是对场景的语义判断，再由 LLM 把判断翻译回脚本修改。这意味着监督信号经过了一次“图像→语言→代码”的两次转译，每次转译都可能丢信息。工程上的失败模式是：GPT-V 指出“物体太挤”，LLM 改了一个坐标但改错了轴，下一轮渲染仍然挤，迭代在原地打转。这类振荡是 SceneCraft 迭代数轮的隐性成本来源，也是它必须靠 library learning 沉淀常用函数来降低每次修改的自由度的原因——函数库把“移动物体到某关系位”这类操作固化成可复用的正确实现，缩小了 LLM 改错的空间。直接写脚本的基线没有这个机制，它的错误一次性固化在产物里；Text2Room 的监督不产生符号修改，因此不存在振荡，但也无法定向修正。

这张表要读的是列间耦合，而不是逐格打分。SceneCraft 的“场景图 + 脚本”表示与“GPT-V 回环”监督是配套的：图给了监督一个可归因的修改入口，脚本给了监督一个可执行的落点。把其中任何一个单独拿掉，另一项就失去意义——消融里场景图、GPT-V 反馈、library learning 三项各自被移除后性能下降，正说明这三者是耦合件而非可插拔装饰。工程复现时若只抄场景图不抄视觉回环，得到的是一个“布局看起来合理但渲染出来穿模”的系统；若只抄回环不抄图，得到的是一个“每轮都在盲改坐标”的系统。对照实验的价值就在于暴露这种耦合，防止把某个模块当成可单独采购的组件。

三 · 速度与显存：成本结构的逐项拆解

速度轴上，SceneCraft 的端到端时延由“迭代轮数 × 单轮四项成本”决定。单轮里 C_render 是 Blender 真实渲染，C_vlm 是一次视觉模型调用，两者都无法用更快的采样或更小的模型随意压缩而不损监督质量。因此它的速度劣势是结构性的：只要保留视觉回环，就必须为每一轮付渲染与看图的钱。直接写脚本的基线在速度上占优，因为它通常只渲染一次用于展示，甚至不渲染；但它的产物质量方差大，物体重叠与比例错误不会被发现，返工成本被推给了人。Text2Room 的速度取决于视角数与生成采样步数，与场景资产数量弱相关而与分辨率/视角覆盖强相关；SceneCraft 的速度则与资产数量强相关，因为上百资产的脚本生成本身就长，渲染也更重。这是两种不同的伸缩方向：一个随视角伸缩，一个随资产伸缩。

显存轴上，四者的峰值来源完全不同。SceneCraft 的显存峰值不在 LLM 侧（预训练 LLM 与 GPT-V 都是推理调用，可分批），而在 Blender 侧：上百资产的场景在渲染时要把网格、材质、纹理全部驻留，纹理分辨率与资产数量共同决定峰值。这意味着它的显存瓶颈是“场景规模 × 纹理预算”，而不是模型参数。Text2Room 的峰值在生成模型侧，随分辨率与视角缓冲增长。WorldGen 的峰值最低，因为布局参数是轻量结构。直接写脚本的基线显存峰值同样在 Blender 侧，但因为布局失控，常出现资产堆叠导致渲染崩，峰值反而不可预测。工程判断是：如果你的部署环境 GPU 显存紧张而 CPU/磁盘充裕，SceneCraft 的渲染可以外置到离线渲染节点，把显存压力从服务侧移走；但迭代回环要求渲染结果及时返回给 GPT-V，外置会引入网络往返，抵消部分速度收益。

$$M_{\text{peak}}\approx \sum_{i=1}^{N}\left(m_{\text{mesh},i}+m_{\text{tex},i}\right)+m_{\text{render buffer}}$$

上式给出 SceneCraft 侧显存的加性结构：N 为资产数，网格与纹理逐项累加，再加渲染缓冲。它解释了为什么“上百资产”既是能力指标也是成本指标——资产数是线性进入显存的，没有共享机制时峰值随 N 线性上升。library learning 在这里有一个间接的工程价值：它把常用函数沉淀成库，减少了重复资产生成的脚本冗余，但对显存无直接帮助，因为渲染仍要实例化每个资产。真正能压峰值的手段是资产复用（同一网格多实例）与纹理图集，这两者在 SceneCraft 的框架里没有被显式处理，属于复现时需要自己补的工程层。对照之下，Text2Room 的显存不随“资产数”增长，因为它根本没有资产概念，这是表示差异在资源轴上的投影。

速度与显存的联合失败模式是“迭代不收敛导致的资源放大”。SceneCraft 每个场景迭代数轮，若 GPT-V 的判断与 LLM 的修改形成振荡，轮数会超出预期，渲染与视觉调用成本成倍增加，显存峰值也因反复加载场景而反复冲高。直接写脚本的基线没有这个放大机制，它的成本是一次性的，失败也是一次性的。Text2Room 的失败模式是视角间不一致导致的接缝，成本不随迭代放大但随视角数放大。把这三条放在一起，可以看出一个反直觉的判断：SceneCraft 的资源效率不能只看单轮，而要看“收敛轮数的分布”；一个平均轮数低但方差大的系统，其尾部成本可能高于一个轮数稳定偏高的系统。工程验收时应断言轮数上界，而不是只断言单轮时延。

四 · 失败模式的逐项归因

SceneCraft 的失败模式可以按四个轴归因，而不是笼统说“物理弱”。第一类来自表示：场景图节点必须映射到资产库，库里没有的物体无法表达，于是文本里的稀有物件被替换成近似资产，语义漂移。第二类来自监督转译：GPT-V 的语义判断经“图像→语言→代码”两次转译，坐标轴改错、关系词理解偏差都会导致振荡，表现为迭代数轮后布局仍不合理。第三类来自渲染：上百资产的场景渲染慢且在资产堆叠时可能崩，崩了就没有图可看，回环中断。第四类来自物理：脚本只写静态布局，没有刚体/碰撞求解，物体可以悬空或互穿，视觉上未必立刻可见，但在下游仿真或交互中暴露。这四类失败模式的修复成本递增：表示类要扩资产库，监督类要改提示与校验规则，渲染类要优化场景组织，物理类要引入求解器，已超出“写脚本”的范畴。

直接写脚本的基线的失败模式更集中：物体重叠、比例错误、渲染崩。这三者同源——缺少显式布局推理。它的失败是“一次性且不可归因”的，因为产物里没有中间表示可供回查。Text2Room 的失败模式是几何接缝与纹理拉伸，以及“看起来合理但不可符号编辑”；它不会崩，但也不会告诉你哪里错了。WorldGen 的失败模式是布局自洽但下游无法落地——布局框合理，但补齐几何时穿模，因为布局阶段没有考虑资产的实际包围盒。把四种失败模式并列，可以看出 SceneCraft 的独特性在于它是唯一一个“失败可归因到具体模块”的方法：场景图错、脚本错、渲染错、视觉判断错，四者可以被分别观测。这个可归因性本身是工程价值，代价是模块多、耦合紧、复现面广。

五 · 决策表：按工程约束选型

把四个轴与失败模式压成一张决策表，前提是承认没有全能方法。表的每一行是一个工程约束，每一列是一个方法，格子里写“适配/不适配/需补件”，并注明补件是什么。这样读表的人不会问“哪个最好”，而会问“我的约束落在哪一行”。需要强调的是，SceneCraft 在“可编辑性”“失败可归因”“空间关系合理”三行上占优，在“速度”“显存”“资产自由度”“物理”四行上需补件或不适配；这不是它的缺陷清单，而是它的适用边界。把它用在需要资产级编辑与可归因调试的管线里，它的慢是可以被迭代收益抵消的；把它用在需要实时或低显存的场景，它的渲染回环就是硬伤。

需要上百资产复杂场景适配（论文主张的能力）不适配（布局失控）部分（视角覆盖受限）部分（布局可扩，几何待补）

读表时要区分“不适配”与“需补件”。不适配是表示层决定的、补不回来的：SceneCraft 的资产自由度受 Blender 库约束，这是场景图节点必须映射到实体的直接后果，换提示词或换 LLM 都改不了；Text2Room 的资产级编辑不可能，因为它的表示里没有实体。需补件是工程层可以加的：SceneCraft 的低显存峰值可以通过资产复用与纹理图集压下来，物理交互可以外接求解器，但这些补件会引入新的耦合——外接求解器要求脚本输出可被求解器解析的碰撞体，而 SceneCraft 的脚本默认只写静态变换，补件意味着改写脚本生成阶段的模板。决策表的作用不是给答案，而是把“补件的代价”提前暴露，避免在集成到一半时才发现表示层不支持。

一个具体的选型例子：假设管线要求“文本→可编辑场景→下游物理仿真”，且允许离线批处理。按表走，SceneCraft 在可编辑、可归因、上百资产三行适配，在物理行需补件，在时延行不适配但离线批处理消解了时延约束。补件方案是：在脚本生成阶段强制每个资产生成碰撞体并写入统一命名，供求解器读取；同时用资产复用压显存峰值。这个组合的失败模式是求解器与渲染器的包围盒定义不一致导致穿模误报，需要在验收断言里加一条“渲染包围盒与碰撞包围盒一致”。对照之下，若管线要求实时交互，SceneCraft 的渲染回环直接出局，应转向 WorldGen 的布局路线加轻量几何补齐，代价是失去资产级材质与视觉回环。决策表的每一行都在逼你回答“我愿意为哪一项付补件成本”，而不是“哪个方法分数高”。

六 · 对照实验的设计要点与可复现断言

做这组对照实验时，最容易犯的错是让四个方法跑在不同的输入分布上。SceneCraft 的输入是自建场景描述，Text2Room 的输入通常是房间级描述，WorldGen 的输入是布局导向的描述；若不加控制，比较就退化成“各自在擅长的输入上得分”。可复现的做法是固定一组描述，按“是否含空间关系谓词”“是否含稀有物件”“资产数量档位”分层，每层内四方法同输入。评价也要分层：表示层看可寻址单元是否与描述中的指称对齐（说“那把椅子”能否定位到具体节点），监督层看错误是否在迭代内被检出并修复，速度层看端到端时延与轮数分布，显存层看峰值与资产数的关系曲线。分层评价的好处是每一层的失败都能归因到具体轴，而不是一个总分掩盖结构差异。

可复现断言应写成可执行的检查，而不是定性描述。针对 SceneCraft，至少四条：其一，场景图节点数应等于脚本中实例化的资产数（防止图与脚本脱节）；其二，迭代轮数应有上界，超过上界即判振荡失败（对应监督转译的失败模式）；其三，渲染峰值显存应随资产数呈可解释的增长，若出现非线性跃升则查资产堆叠；其四，脚本产出的静态布局应通过包围盒互斥检查，未通过则标记为物理补件前的已知缺陷。这四条断言分别对应表示、监督、显存、物理四个轴，构成一个最小验收集。对直接写脚本的基线，断言简化为“语法通过 + 包围盒互斥”，因为它没有回环可查；对 Text2Room，断言转向视角接缝与纹理一致性；对 WorldGen，断言转向布局框与下游几何的包围盒一致。

$$\text{Pass}=\bigwedge_{k\in\{\text{graph},\text{iter},\text{mem},\text{bbox}\}}\text{Assert}_k(\text{run})$$

把四条断言取合取，得到一个二值通过判据，这是对照实验里唯一不依赖主观打分的部分。它的工程意义在于：当 SceneCraft 在某层失败时，合取式会指出是哪一项 Assert 失败，从而直接映射回第 4 节的失败模式表。例如 iter 断言失败对应监督振荡，bbox 断言失败对应物理缺失，graph 断言失败对应图与脚本脱节（通常是 library learning 复用函数时参数未对齐）。这种“断言—失败模式”的一一映射，比任何总分都更适合工程验收，因为它给出的是修复入口而不是排名。对照实验的最终产出不应是“SceneCraft 优于 X”，而应是这张断言表加上每个方法在各层的通过/失败分布，让读者按自己的约束去查表。

最后落到一个具体机制上：SceneCraft 的 library learning 在对照实验里有一个容易被误读的作用。它沉淀的是跨场景复用的常用函数，降低的是脚本生成的自由度与重复错误，但它不改变渲染成本、不扩大资产库、不引入物理。因此它在速度与显存轴上几乎无贡献，在表示与监督轴上贡献的是“减少 LLM 改错的空间”。对照实验若把 library learning 当成性能加速项来测，会得到误导性的结论；正确的测法是看它在“迭代轮数分布”上的作用——函数库越厚，单轮修改越受限，振荡越少，轮数上界越容易满足。这也解释了为什么消融里移除 library learning 会掉性能：掉的不是单轮质量，而是收敛稳定性。工程复现时，library learning 应被当作“收敛控制器”而非“加速器”来验收，断言应落在轮数分布而非时延上。
