一 · 数据从哪来：自建描述与 Blender 场景的配对结构

SceneCraft 的数据侧没有走大规模预训练那条路，它的“训练数据”实际上是评测与迭代所依赖的配对样本：一端是自建的自然语言场景描述，另一端是对应的 Blender 场景。理解这一点很关键，因为很多读者看到“LLM 智能体”会默认存在一个微调阶段，而这篇论文的配方是零训练——预训练 LLM 与 GPT-V 直接上岗，数据的作用是提供任务实例和验证信号，而不是梯度来源。配对结构决定了评测协议的形状：给定一条描述文本 t，系统应当产出一个可执行的 Blender Python 脚本，脚本经 Blender 执行后得到渲染图 I，再由视觉模型与人工/规则共同判断 I 是否兑现了 t 中的物体清单与空间关系。

具体机制上，描述文本并非自由散文，而是被组织成可核对的断言集合：出现了哪些物体、各自的大致类别、彼此之间的方位与包含关系（例如“桌子在沙发前方”“书架靠墙”）。这些断言正是场景图 S 的监督信号来源。场景图作为中间表示，把文本中的关系转成数值约束写进脚本，于是“数据”在流水线中扮演了双重角色：既是任务的输入，也是回环修正时的比对基准。工程上这意味着数据标注的粒度直接决定了评测能查多细——如果描述只写“一个客厅”，那么重叠、比例、朝向这些失败模式就无法被归责。

系统代价出现在配对数据的构建环节。Blender 场景不是随手可得的语料，它需要人工搭建或从既有工程中抽取，并且要与描述逐条对齐；资产库依赖使得场景的可用物体集合受限于本地资产，描述里提到的类别若资产库缺失，配对就失效。这是一个数据层面的失败模式：描述与资产的可实现性不匹配，会让智能体在迭代中反复尝试不存在的资产，渲染循环空转。举例来说，一条描述要求“上百个资产的复杂场景”，若其中若干类别在资产库中没有对应网格，规划阶段生成的场景图节点就无法落地成脚本调用，视觉反馈看到的缺失会被误判为布局错误，从而触发无效修正。

另一个容易被忽略的点是配对数据的规模与多样性并不构成统计意义上的训练集。论文的评测建立在自建描述与 Blender 场景之上，样本量级服务于定性展示与消融，而不是拟合。因此读者不应把“能生成含上百资产的复杂场景”理解为在某个大语料上泛化出的统计结论，它更像是在受控实例上的能力演示。这个区分直接影响后文对指标口径的解读：当样本是自建的、任务是开放的，任何单一数字都携带了任务构造的偏差。

二 · 评测协议：脚本可执行性、渲染可见性与关系核验三层

SceneCraft 的评测协议可以拆成三层递进的检查，每层的通过条件不同，失败归因也不同。第一层是脚本层：生成的 Python 是否能在 Blender 中无异常执行。这一层是硬门槛，直接让 LLM 写脚本的基线经常在此折戟——物体重叠、比例错误、渲染崩，本质上都是脚本执行阶段或执行后渲染阶段的崩溃。第二层是渲染层：执行后是否产出了可用的渲染图，且图中能辨认出描述所要求的物体。第三层是关系层：物体之间的空间关系是否符合描述中的断言。三层不是并列的评分项，而是串联的门控：脚本跑不起来，后两层无从谈起。

用伪代码表达这套协议的判定逻辑，大致是：对每条描述 t，取场景图 S 与脚本，执行 I=Blender(Script)；若执行抛异常则记为脚本失败；否则把 I 与 t 的断言集合一起送入 GPT-V 做视觉核验，输出逐条关系的满足情况；最后由人工或规则汇总。这里的公式化表达与论文给出的三段式一致：

$$\mathcal{S}=\mathrm{SceneGraph}(t),\qquad \mathrm{Script}=\mathrm{LLM}(\mathcal{S}),\qquad \mathcal{I}=\mathrm{Blender}(\mathrm{Script})$$

注意这个式子里没有损失函数，也没有梯度项——它描述的是数据流而非训练目标，这正是评测协议与训练配方分离的体现。协议的关键在于 GPT-V 反馈既是生成时的迭代信号，也是评测时的核验工具，二者共用同一视觉模型，这带来一个结构性风险：生成阶段用来修正的判据，与评测阶段用来打分的判据同源。若视觉模型对某类空间关系系统性失明（例如深度方向的前后遮挡判断），生成端会停止修正，评测端也会给出通过，误差被闭环掩盖而非暴露。

系统代价体现在渲染慢这一已知局限上。三层协议中第二、三层都依赖渲染产物，而 Blender 渲染是流水线中最重的一环；每个场景迭代数轮意味着渲染次数随迭代线性增长，评测吞吐因此受限于渲染而非 LLM 推理。工程复现时若想扩大评测规模，瓶颈不在采样也不在解码，而在渲染队列。失败模式还包括渲染崩：脚本语法正确但运行时触发几何或材质异常，导致进程中断，这类失败在协议里被归入第一层，但根因往往在场景图的数值约束不合理，例如比例约束给出退化的尺度。

具体例子可以取一个含多件家具与装饰物的房间描述：协议要求脚本执行成功、渲染图中主要家具可辨认、且“沙发在桌子后方”这类关系被 GPT-V 确认。若智能体把沙发与桌子放在同一深度平面上，渲染图从默认视角看可能仍然“像”对的，关系层核验就会放过一个实际错误的布局。这说明协议对视角与遮挡的敏感性没有显式控制，评测结论的强度依赖于渲染视角的选择，而视角选择本身未被纳入指标口径。

三 · 指标口径：通过率背后的分母与判据归属

论文在结果层面给出的表述是“能生成含上百资产的复杂场景、空间关系更合理”，并与直接 LLM 写脚本、Text2Room 两个基线对比。这里没有给出具体的通过率数字，读者需要理解的是口径而非数值。指标的分母是什么？是自建描述集合中的场景实例数，而不是资产数、也不是关系断言数。分子是什么？是通过三层协议的实例数。这个口径下，“上百资产”是单个实例内部的复杂度描述，不进入分母，也不按资产计分。误读常发生在这里：把“上百资产”当成规模指标去与基线的资产数比较，实际上它描述的是单场景容量，而非评测样本量。

判据归属是第二个口径问题。关系层的核验由 GPT-V 完成，这意味着指标的判据来自一个视觉语言模型的主观判断，而非几何真值。若场景图在规划阶段已经写入了数值约束，理论上可以用脚本中的坐标直接计算关系是否成立，但论文的协议走的是渲染后视觉核验这条路。两种判据的差别在于：几何判据可复现、可审计，但对“看起来是否合理”不敏感；视觉判据贴近人类感知，却引入模型偏差且难以复算。指标口径若不声明判据归属，跨论文比较就失去意义——同样叫“空间关系合理”，一个用坐标算、一个用视觉模型看，结论不可通约。

消融实验的口径也值得拆开看。场景图、GPT-V 反馈、library learning 三个组件被分别移除，观察性能变化。这里的指标变化不能简单读成“组件贡献”，因为移除场景图会同时改变脚本生成阶段的输入结构，移除 GPT-V 反馈会同时取消生成端的迭代与评测端的核验，两个作用混在一个数字里。工程判断上，消融的口径应当区分“生成能力下降”与“评测判据变化”，否则会把评测工具的缺失误读成生成器的退化。library learning 的消融尤其如此：它沉淀常用函数供跨场景复用，移除后脚本更长、更易出错，但评测协议并不直接度量代码质量，只能通过脚本层失败率间接反映。

系统代价在这里表现为评测的可比性成本。要让指标有意义，必须固定描述集合、固定渲染视角、固定视觉模型版本、固定迭代轮数上限；任何一项漂移都会改变分子。论文声明每个场景迭代数轮，但轮数上限本身是超参，放宽轮数会提高通过率同时拉高渲染成本，指标与成本因此耦合。一个具体的失败模式是：在有限渲染预算下，迭代被截断，部分实例以“未收敛”状态计入失败，指标低估了系统在充足预算下的能力；反之若预算充足而基线未获同等预算，比较就不公平。这类口径问题在零训练的智能体系统里尤其突出，因为没有训练集与测试集的自然划分来约束预算分配。

四 · 作弊风险：同源判据、资产泄漏与描述回填

零训练配方带来一类特有的作弊风险：生成端与评测端共享组件。GPT-V 既在迭代中告诉智能体“哪里不对”，又在评测中判断“是否通过”。若智能体学会迎合视觉模型的偏好而非真实几何，例如把物体摆在视觉模型容易确认的视角正面、用高对比材质让物体更易被识别，那么通过率会上升而场景质量未必提升。这不是恶意作弊，而是优化压力下的判据对齐——智能体优化的是“让 GPT-V 说对”，不是“让场景符合描述”。工程上缓释的办法是评测端换用独立判据，例如从脚本坐标直接核验关系断言，或引入人工抽检，代价是评测吞吐下降与人力成本上升。

资产泄漏是第二类风险。SceneCraft 依赖 Blender 资产库，描述中的物体类别若与资产库高度重合，智能体的任务就退化为“在已知资产集合里做布局”，难度被系统性低估。若描述文本在构造时参考了资产库的清单，配对数据就带有选择偏差：凡是资产库没有的类别不会被写进描述，评测因此避开了最难的泛化情形。这种偏差不会体现在任何单一数字上，但会让“能生成复杂场景”的结论限定在资产库覆盖范围内。复现时应显式报告描述集合与资产库的交集比例，作为口径的一部分。

第三类风险是描述回填，即用生成结果反向修订描述以匹配产出。由于描述是自建的，存在一种诱惑：当某个场景的关系核验失败时，调整描述措辞使其“成立”，从而提高通过率。这在数据侧是隐蔽的作弊，因为分母没变、分子变了，而变更发生在标注而非系统。防止的办法是把描述集合在评测前冻结，并保留版本记录；工程验收断言里应当包含“描述文本在评测期间不可变”这一条。

系统代价方面，作弊风险的缓释都要花钱：独立判据要写几何核验器，人工抽检要人力，冻结描述要流程管理。这些成本在论文的定性表述中不可见，但在复现清单里必须计入。一个具体例子是关系核验的几何化：把“沙发在桌子后方”转成脚本坐标上的深度比较，需要定义坐标系与容差，容差过松则放过错误布局，过紧则误杀合理近似，容差的选取本身就是一个口径决策，且必须与视觉判据的宽松度对齐，否则两套判据会给出互相矛盾的结论。

五 · 那个容易误读的数字：上百资产不是规模指标

最容易被误读的表述是“能生成含上百资产的复杂场景”。读者常把它读成两项含义之一：其一是系统的容量指标，仿佛资产数越多系统越强；其二是评测规模，仿佛在上百资产的场景上做了统计。两种读法都不对。这个数字描述的是单个场景内部的资产数量级，用来说明系统能处理的空间规划复杂度——物体越多，场景图节点越多，数值约束越密，脚本越长，重叠与比例错误的概率越高。它是一个能力边界的定性锚点，不是分母，不是均值，也不是与基线比较的公平刻度。

为什么容易误读？因为资产数是一个直观的复杂度代理，而论文的其他结果表述是定性的（“空间关系更合理”），读者会本能地抓住唯一出现的数量级当作量化证据。但口径上，资产数不进入通过率的计算：一个含上百资产的场景与一个含十来个资产的场景，在协议里都只算一个实例，权重相同。若基线的场景资产数较少，比较的是“能否处理”而非“处理得多好”，前者是布尔门槛，后者才涉及质量。把门槛当成刻度，就会得出系统在规模上大幅领先的错误结论。

正确读法是把它放进三层协议里定位：上百资产主要压在第一层与第二层——脚本更长更易崩，渲染图中物体更多更难辨认；第三层的关系核验则随资产数增加而断言数增加，GPT-V 的核验负担上升，漏判概率随之上升。也就是说，资产数增加同时提高了任务难度与评测的不可靠性，二者方向相反地影响通过率。这个数字因此不能被单独引用为性能证据，必须与判据归属、渲染视角、迭代预算一起声明。工程判断上，复现时应把资产数分布作为协变量报告，而不是把它压缩成一个上限值。

具体机制上，资产数如何转化为脚本复杂度可以这样看：场景图每个节点对应至少一次资产加载与一次变换设置，节点间的空间关系对应约束求解或坐标计算，脚本长度大致随节点数与关系数线性增长，而 LLM 生成的长脚本在一致性上更脆弱——后段代码容易遗忘前段定义的变量或坐标系约定。失败模式因此不是均匀分布的，而是集中在脚本后段与关系密集的子图。一个含上百资产的场景若关系断言集中在少数几对物体上，评测可能只核验了局部，剩余大量物体的布局错误不被计入，指标因此偏乐观。这正是把资产数当规模指标会掩盖的口径漏洞。

六 · 工程复现的验收断言：把口径写进检查项

复现这套数据与评测体系时，验收断言应当围绕口径而非结果展开。第一，描述集合冻结且版本可追溯，评测期间不可修改，防止描述回填。第二，资产库与描述集合的交集比例被显式记录，作为能力结论的适用范围。第三，渲染视角与视觉模型版本固定，任何变更都触发指标重算而非直接比较。第四，迭代轮数上限与渲染预算作为超参记录，通过率必须与预算成对报告，避免预算不对称的比较。第五，关系核验的判据归属声明清楚：是几何坐标核验还是视觉模型核验，容差与宽松度如何设定。

这些断言的系统代价是流程开销，但换来的是指标的可比性。一个具体的失败模式是版本漂移：视觉模型升级后对遮挡的判断变化，导致同一批场景的通过率跳变，若没有版本记录，会被误读为系统改进或退化。另一个失败模式是资产库更新引入新类别，描述集合未变但可实现性变了，交集比例漂移，能力边界随之移动。工程上应把资产库版本与描述集合版本绑定为一次评测单元，任何一方变更都视为新单元。

消融的验收也需要断言：移除某组件时，必须区分生成端变化与评测端变化。例如移除 GPT-V 反馈会同时取消迭代修正与视觉核验，此时若仍用视觉核验打分，等于用被削弱的判据评价被削弱的系统，结论不可解释。正确做法是在消融时固定判据，或至少报告判据是否随组件变化。library learning 的消融应额外报告脚本长度与脚本层失败率，因为它的作用机制是代码复用而非直接提升视觉质量，指标口径必须能捕捉这条路径。

最后落在具体机制上：SceneCraft 的数据与评测体系本质上是“配对描述—场景图—脚本—渲染—视觉核验”的闭环，闭环的每一环都可能成为口径泄漏点，而零训练配方意味着没有训练/测试划分来天然隔离这些泄漏。工程判断因此是：把评测协议当作系统的一部分来设计和验收，而不是事后附加的度量；把“上百资产”这类数量级表述还原为任务复杂度锚点而非性能刻度；把判据归属、预算、版本三项写进每一次指标报告的头部。做到这三点，跨论文比较才有意义，复现结论才不会建立在同源判据与资产泄漏的沙地上。
