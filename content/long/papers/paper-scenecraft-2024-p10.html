一 · 45 分钟排课：把论文拆成五个可讲透的模块

给一位有工程背景、但没读过 SceneCraft 的新工程师讲这篇论文，45 分钟不能按论文的章节顺序平铺，而要按“他听完能自己复现哪一步”来排。建议的时间切分是：8 分钟讲问题与动机，10 分钟讲场景图到脚本的转换，10 分钟讲渲染回环与视觉反馈，8 分钟讲 library learning，7 分钟讲边界与复现判断，最后 2 分钟留给五道自测题的口头提问。这个切分的依据是：论文的贡献重心不在“LLM 会写代码”这一层，而在“把空间关系变成可执行数值约束、再用渲染图闭环纠错”这一层，所以中段必须占掉一半以上时间。

开场 8 分钟只讲一件事：直接让 LLM 写 Blender 脚本会怎么坏。给工程师看三个具体失败模式就够了——物体重叠（两个物体的包围盒在数值上相交，脚本能跑但场景穿模）、比例错误（桌子和杯子的尺寸关系不符合常识，因为 LLM 只从文本里猜尺度）、渲染崩（脚本语法正确但 API 调用顺序错，Blender 直接抛异常）。这三个失败模式正好对应论文要解决的三个子问题：空间规划、资产布局、视觉反馈。讲到这里要明确一句：论文的解法不是让 LLM 一次写对，而是把“一次写对”拆成“先规划、再生成、再检查、再修”。

接下来的 10 分钟讲核心数据流。用论文给出的三段式公式做骨架：

$$\mathcal{S}=\mathrm{SceneGraph}(t),\qquad \mathrm{Script}=\mathrm{LLM}(\mathcal{S}),\qquad \mathcal{I}=\mathrm{Blender}(\mathrm{Script})$$

讲这个公式时不要停在符号层面，要把它翻译成工程师能落地的三步。第一步，文本 $t$ 进 LLM，输出的是场景图 $\mathcal{S}$，图里的节点是物体、边是空间关系（在……上方、在……左侧、贴着……）。第二步，场景图再进 LLM，输出的是 Blender Python 脚本，脚本里每个物体的位置、旋转、缩放都是具体数值。第三步，脚本进 Blender 执行，得到渲染图 $\mathcal{I}$。这三步的关键工程含义是：LLM 在第一步只做符号推理，不做数值计算；数值约束是在第二步由 LLM 根据场景图“翻译”出来的。这个分工决定了后面所有失败模式的归因方式——场景穿模多半是第二步的数值翻译错了，而不是第一步的关系判断错了。

中段 10 分钟讲渲染回环。这里要讲清一个机制：渲染图 $\mathcal{I}$ 不是给人看的，是给 GPT-V 看的。GPT-V 拿到渲染图后做视觉检查，判断场景是否满足文本描述，不满足就生成修正指令，回到脚本生成环节再迭代。这个回环的系统代价必须讲透：每一轮迭代都要跑一次 Blender 渲染，而渲染是整条流水线里最慢的一环。论文明确把“渲染慢”列为局限，所以工程上讲这个回环时，听众要意识到迭代轮数不是免费的——每多一轮就多一次渲染开销。一个具体例子：如果场景含上百个资产，单次渲染的耗时随资产数和材质复杂度上升，迭代数轮意味着渲染开销成倍叠加。这也是为什么论文要用 library learning 来减少重复劳动，而不是单纯靠增加迭代轮数来提升质量。

8 分钟讲 library learning。机制是：跨场景迭代过程中，那些反复出现的常用函数（比如“把一组物体沿某轴等距排列”“给物体加某类材质”）被沉淀进一个函数库，后续场景生成时直接复用。这个机制的工程价值在于它把“每个场景从零写脚本”变成“每个场景从库出发写脚本”，降低了脚本生成的搜索空间。代价是库的维护问题：库里的函数是 LLM 生成的，函数本身的正确性没有形式化保证，复用错误函数会把错误跨场景传播。这一点在讲的时候要提醒听众：library learning 是加速器，不是正确性保证。

最后 7 分钟讲边界。三个局限要逐个落到工程判断上：资产库依赖意味着场景的视觉丰富度上限由 Blender 资产库决定，文本里描述的东西如果库里没有，就只能用近似资产替代；渲染慢意味着这条流水线不适合实时交互场景；物理弱意味着生成的场景是“看起来合理”而不是“物理上可交互”，物体之间的碰撞、重力、材质响应都没有建模。讲完这三个局限，听众应该能自己判断：SceneCraft 适合离线生成静态场景，不适合做游戏运行时或机器人仿真环境。

二 · 三个类比：让抽象机制在工程师脑子里有落点

第一个类比：场景图之于脚本，相当于编译器的中间表示（IR）之于目标代码。LLM 直接从文本写 Blender 脚本，相当于让一个程序员跳过 IR 直接手写汇编——能写，但一出错就难定位。SceneCraft 插入场景图这一层，等于把“文本到脚本”拆成“文本到 IR”和“IR 到脚本”两段，每段都可以单独检查。场景图错了，是关系理解错了；脚本错了，是数值翻译错了。这个类比的教学价值在于：它让工程师立刻明白为什么要多这一层，以及为什么消融实验里去掉场景图会掉性能——去掉 IR，错误归因就失去了抓手。

第二个类比：GPT-V 的渲染检查，相当于 CI 流水线里的截图回归测试。传统前端工程里，改完代码跑一遍无头浏览器截图，和基准图比对，不一致就报错。SceneCraft 的回环是同一个思路的视觉版本：渲染图就是截图，GPT-V 就是那个比对器，只不过比对标准不是像素级 diff，而是“这张图是否符合文本描述”的语义判断。这个类比的工程含义是：回环的有效性取决于检查器的判断质量。像素 diff 是确定性的，GPT-V 的判断是概率性的，所以这个回环会漏检——有些错误 GPT-V 看不出来，迭代就停在一个错误但“看起来还行”的场景上。这是讲课时必须点明的失败模式。

第三个类比：library learning 相当于把项目里反复出现的工具函数抽成公共库。任何工程师都做过这件事：三个地方都写了同样的排序逻辑，第四处再写之前先抽成函数。SceneCraft 把这个动作自动化了，让 LLM 在跨场景迭代中识别重复模式并沉淀。类比的边界也要讲清：人手抽库时会写单元测试，SceneCraft 的库函数没有测试，只有“在已生成场景里跑通过”这一条弱证据。所以这个类比能帮听众理解机制，但不能帮听众理解可靠性。

三个类比讲完，可以做一个交叉检查：问听众“如果去掉场景图这一层，哪个类比会失效”。正确答案是第一个——没有 IR，就没有错误归因的抓手，第二个类比里的“检查”也会退化成对最终脚本的黑盒检查，定位成本大幅上升。这个提问的作用是让听众把三个类比串成一条因果链，而不是记三个孤立的故事。

三 · 两个常见误解：讲课时必须主动拆掉

误解一：以为 SceneCraft 是“端到端训练出来的 3D 生成模型”。这个误解在工程听众里很常见，因为他们习惯了“输入文本、输出 3D 资产”的生成模型叙事。事实是论文明确写了无需训练，用的是预训练 LLM 加 GPT-V。整条流水线里没有任何针对 3D 场景的梯度更新，所有“学习”都发生在推理时的迭代和 library learning 的函数沉淀上。拆这个误解时要讲清后果：如果听众以为它是训练出来的模型，就会误判它的泛化边界——它不会因为见过更多场景而变强，它的上限由预训练 LLM 的代码能力和 GPT-V 的视觉判断能力共同决定。工程上这意味着，换一个更强的 LLM 或更强的视觉模型，整条流水线的表现会跟着变，但流水线本身没有“训练配方”可调。

误解二：以为“能生成上百个资产”等于“能生成任意复杂的场景”。论文的结果是能生成含上百资产的复杂场景、空间关系更合理，但这是在一个有边界的设定下成立的：资产来自 Blender 资产库，场景是静态的，物理交互弱。拆这个误解的关键是把“数量”和“复杂度”分开：上百个资产是数量指标，空间关系合理是质量指标，而物理可交互性是另一个维度，论文没有覆盖。讲课时可以给一个具体反例：一个含上百资产的场景，如果文本要求“杯子被碰倒后水洒在桌上”，SceneCraft 生成的是静态摆放，不会模拟这个动态过程。所以“上百资产”不能外推成“任意动态场景”。

这两个误解的共同根源是把论文的贡献范围读宽了。论文的贡献是“LLM 智能体把文本转成可执行 Blender 脚本并用视觉反馈修正”，这个贡献是真实的，但它的边界是资产库、静态场景、弱物理。讲课时把这两个误解拆掉，听众才能准确判断这条路线能接到自己项目的哪一段。

四 · 五道自测题：检验听众是否真的理解了机制

第一题：给定文本“一张桌子，桌上左边一个杯子、右边一个盘子”，请写出场景图里至少三个节点和两条边，并说明这两条边在脚本生成阶段会被翻译成什么样的数值约束。这道题考的是“场景图到数值约束”的转换机制。合格的回答应该能说出：节点是桌子、杯子、盘子；边是“杯子在桌上”“杯子在盘子左侧”；数值约束是杯子和盘子的 z 坐标对齐桌面高度、杯子的 x 坐标小于盘子的 x 坐标。不合格的回答通常会把边直接写成“杯子在盘子左边”的自然语言，而说不出数值形式——这说明听众没理解第二步 LLM 做的是数值翻译。

第二题：如果渲染图里两个物体明显重叠，但 GPT-V 没有报错，迭代会怎么走？这道题考的是回环的失败模式。合格回答：迭代会停在当前脚本，因为检查器没给出修正信号，场景带着穿模错误被接受。进一步追问“怎么发现这种漏检”，合格回答会指向人工抽检或换更强的视觉检查器，而不是指望回环自己纠错。

第三题：library learning 沉淀下来的函数如果本身有 bug，会发生什么？这道题考的是库的跨场景传播风险。合格回答：bug 会随着函数复用传播到后续所有调用它的场景，而且因为函数已经“沉淀”，后续迭代不会重新生成它，错误被固化。这道题的工程含义是：库需要版本管理和回归检查，不能只沉淀不验证。

第四题：论文说无需训练，那“迭代数轮”和“训练”的区别在哪？这道题考的是对“学习”一词的精确理解。合格回答：迭代是推理时的搜索，不改变模型参数；library learning 改变的是外部函数库，不是模型权重。两者都不产生梯度更新。不合格回答会把迭代说成“在线学习”，这是概念混淆。

第五题：如果要让 SceneCraft 生成的场景支持物理交互，需要补哪一层？这道题考的是边界判断。合格回答会指出：需要在脚本里加入物理属性（质量、摩擦、碰撞体）并接入物理引擎，而论文的流水线只做静态摆放和视觉检查，没有这一层。这道题的作用是让听众把“能生成”和“能仿真”分开，避免把 SceneCraft 直接当成仿真环境生成器。

五道题讲完，可以留一个口头追问作为收尾：如果只允许改一个模块来提升场景质量，改哪个？合理的工程判断是改视觉检查器——因为回环的上限由检查器的判断质量决定，检查器漏检，迭代再多轮也修不对。这个判断把整堂课的重心落回到“渲染回环的有效性取决于检查器”这一机制上，而不是落在“LLM 更强就能生成更好场景”这种笼统的说法上。
