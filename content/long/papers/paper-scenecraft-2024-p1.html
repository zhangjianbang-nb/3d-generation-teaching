一 · 从一句描述到一个可渲染场景：任务链条的真实长度

设想一个具体的输入：用户写下“一间临街咖啡馆，靠窗三张双人桌，吧台在右后方，吧台上方挂四盏吊灯，门口有一块立式菜单牌，窗外能看到人行道和两棵树”。这句话对人来说是一个可想象的画面，对机器来说则是一串需要被逐层兑现的承诺。SceneCraft 面对的正是这条从自然语言到 Blender 可执行脚本的链路：文本先被抽象为场景图，场景图再被翻译成带数值约束的 Python 代码，代码在 Blender 里执行并渲染出图像，图像被视觉模型检查后回流成修正指令，修正后的脚本再次执行。这条链路上任何一环松动，最终画面就会失真——桌子穿进墙里、吊灯悬在半空、菜单牌比例像一扇门。

把这条链路写成形式化的三段，论文给出的核心表达式是：

$$\mathcal{S}=\mathrm{SceneGraph}(t),\qquad \mathrm{Script}=\mathrm{LLM}(\mathcal{S}),\qquad \mathcal{I}=\mathrm{Blender}(\mathrm{Script})$$

这里 $t$ 是文本描述，$\mathcal{S}$ 是场景图（物体集合加空间关系），$\mathrm{Script}$ 是 Blender Python 脚本，$\mathcal{I}$ 是渲染出的图像。公式看似简洁，但它把三类异质能力压进同一条流水线：语言模型的空间规划能力、代码模型对 3D API 的精确操控能力、以及视觉模型对渲染结果的判读能力。三者中任何一个缺席，链路就断。这正是这篇论文之前的主流做法没能解决的问题现场。

二 · 论文之前的两条主流路线及其结构性缺陷

在 SceneCraft 之前，文本到 3D 场景的生成大致沿着两条路线推进。第一条是“直接让 LLM 写脚本”：把文本描述连同 Blender Python 的 API 说明一起塞进提示词，让语言模型一次性吐出完整脚本，执行、渲染、结束。第二条是端到端的场景生成模型，以 Text2Room 为代表：用图像或深度生成模型在已有几何上逐步“长”出房间，靠 2D 生成先验补全三维结构。两条路线各有各的失效方式，而失效方式恰好互补，构成了这篇论文非改不可的理由。

直接写脚本路线的机制是“一次性代码生成”。它把空间规划隐式地压在语言模型的 token 预测里：模型在生成 `bpy.ops.mesh.primitive_cube_add(location=(x,y,z))` 这样的语句时，同时要决定这个立方体代表什么家具、它该放在哪、它和邻居是否冲突。问题在于，语言模型对数值的把握是概率性的，而 3D 布局对数值的容错极低。两个物体中心点相距 0.3 米还是 0.5 米，在 token 层面几乎无差别，在渲染层面却是“穿模”与“正常摆放”的分界。更麻烦的是脚本是单体式的：一旦第 40 行的坐标写错，前面 39 行建立的物体全部作废，模型没有局部回退的机制。这条路线在简单场景（三五个物体）上能跑通，物体数量一多，重叠、比例错误、渲染崩溃三类失败同时出现。

Text2Room 路线的机制是“逐视角生成加几何融合”。它不写脚本，而是从一个初始视角出发，用 2D 生成模型补全当前视角看不到的区域，再把新生成的深度图反投影成三维点云或网格，移动到下一个视角继续。这条路线擅长生成连续、有机的室内表面，纹理和光照有生成模型的先验支撑。但它的结构性缺陷在于：场景的“物件性”被消解了。它产出的是融合后的几何壳，而不是一组有名字、有层级、可单独选中和替换的资产。用户说“把靠窗第二张桌子换成圆桌”，Text2Room 没有“桌子”这个可寻址的对象，只有一片网格。空间关系的可控性也随之丧失——模型无法被要求“吧台必须在右后方”，因为布局是生成过程涌现出来的，不是被约束出来的。

把两条路线的缺陷并置，问题现场就清楚了：一条路线有代码的可控性但缺空间规划与视觉校验，另一条路线有视觉真实感但缺对象级可控性与显式空间约束。SceneCraft 要做的，是把前者的可控性和后者的视觉反馈接起来，同时补上中间缺失的那一层——显式的场景图。

三 · 为什么“直接写脚本”必然失败：三个可复现的失效模式

把直接写脚本的失败拆开看，可以归纳为三类，每一类都能在具体场景里定位。

  • 重叠与穿插。语言模型生成坐标时倾向于“各自独立地放”，缺少全局的占位检查。咖啡馆例子里，模型可能给三张桌子分别写 `location=(1.0, 2.0, 0)`、`location=(1.2, 2.1, 0)`、`location=(0.9, 1.9, 0)`，三个中心点彼此相距不到 0.3 米，桌面的包围盒直接相交。渲染出来是一坨叠在一起的几何体，视觉上无法辨认。
  • 比例失配。模型对“米”这个单位缺乏身体感。吊灯被写成半径 0.8 米的球体，挂在 2.5 米高处，视觉上像一颗悬着的行星；菜单牌被写成高 2 米的板子，比门还高。这类错误不是坐标错，而是尺度错，且往往在整份脚本里系统性出现——模型一旦选定某个量级，会把所有物体都往那个量级上靠。
  • 渲染崩溃。Blender Python 的 API 有大量隐式前置条件：材质节点要先建、物体要先 link 到 collection、修改器顺序有讲究。一次性生成的脚本经常在中间某步触发异常，整个渲染流程中断，且错误信息对语言模型来说是不可读的堆栈，模型无法据此自我修复。

这三类失败的共同根源是：脚本是一维的 token 序列，而场景是三维的约束系统。把三维约束压进一维序列，等于要求模型在写第 $i$ 个 token 时已经精确预判第 $i+k$ 个 token 造成的空间后果。这不是提示词工程能补的，是表示层的错配。用伪代码描述直接路线的控制流，其脆弱性一目了然：

$$\mathrm{Script}\sim p(\cdot\mid t),\quad \mathrm{exec}(\mathrm{Script})\rightarrow \mathcal{I}\ \text{或}\ \bot$$

执行结果要么是一张图，要么是一个异常 $\bot$，中间没有“部分成功”的状态可供修正。模型拿不到“第 12 个物体位置偏了”这样的局部信号，只能整段重写。这就是为什么非改不可：不是模型不够强，而是接口设计让反馈无处落脚。

四 · 场景图作为中间表示：把空间关系从隐式变成可约束

SceneCraft 的第一个结构性改动，是在文本和脚本之间插入场景图 $\mathcal{S}$。场景图不是简单的物体清单，它把场景拆成两层：节点层是带类别与属性的物体（“双人桌”“吊灯”“菜单牌”），边层是物体之间的空间关系（“靠窗”“在……上方”“在……右后方”“相邻”）。这个表示的关键作用是让空间关系从“语言模型生成坐标时的隐式直觉”变成“可以被单独检查、单独修正的显式命题”。

一旦关系是显式的，它就能被翻译成数值约束写进脚本。比如“吊灯在吧台上方”这条边，在脚本里落成一组约束：吊灯的 $x,y$ 坐标继承吧台的 $x,y$ 范围，吊灯的 $z$ 坐标等于吧台台面高度加一个悬挂偏移。用约束的形式写，就是：

$$\mathbf{p}_{\text{light}}=(x_b+\delta_x,\ y_b+\delta_y,\ z_b+h),\qquad \delta_x,\delta_y\in[-w_b/2,w_b/2]$$

其中 $(x_b,y_b,z_b)$ 是吧台参考点，$w_b$ 是台面宽度，$h$ 是悬挂高度。这条公式的意义不在于它多复杂，而在于它把“上方”这个模糊的方位词兑现成了一个可执行的算术关系。脚本生成不再需要模型凭空猜坐标，而是按约束求解。重叠问题也同理：任意两个物体的包围盒在 $xy$ 平面上不相交，可以写成一条全局约束，在脚本里以占位检查的形式落地。

场景图还带来一个工程上的好处：它是可寻址的。用户说“把靠窗第二张桌子换成圆桌”，在场景图里就是定位到“桌子”节点、筛选“靠窗”边、取第二个实例、改类别属性，然后只重新生成与该节点相关的脚本片段。这与 Text2Room 的网格壳形成鲜明对比——后者没有节点，改动只能靠重新生成整片区域。代价是场景图的质量直接决定下游一切：如果 LLM 在规划阶段漏掉了“菜单牌”这个节点，后面的脚本再精确也不会把它变出来。这是这条路线新增的失败面，也是消融实验里场景图被单独拿掉后性能下降的原因。

五 · 视觉反馈回路：渲染图作为不可绕过的裁判

即便有了场景图和约束，脚本仍会在细节上出错——约束是局部的，而视觉一致性是全局的。SceneCraft 的第二个结构性改动，是把渲染出的图像 $\mathcal{I}$ 送回给 GPT-V 做检查，让视觉模型充当裁判，把“看起来不对”翻译成“哪条约束需要改”。这个回路的机制是：Blender 执行脚本产出渲染图，GPT-V 对照原始文本描述与场景图逐项核对（物体是否齐全、方位是否相符、比例是否合理、有无明显穿插），输出修正指令，指令回流到脚本生成环节，形成下一轮迭代。

这个回路的价值在于它捕捉的是约束语言捕捉不到的东西。约束能保证“吊灯在吧台上方”，但保证不了“吊灯看起来像吊灯而不是像球”。视觉模型看的是像素，它能指出“吊灯太大”“桌子腿悬空”“窗外树的位置挡住了招牌”这类语义级偏差，而这些偏差很难事先写成数值约束。用伪代码表示迭代控制流：

$$\mathrm{for}\ k=1\ldots K:\ \mathcal{I}_k=\mathrm{Blender}(\mathrm{Script}_k);\ \ \mathrm{Script}_{k+1}=\mathrm{Script}_k\oplus\mathrm{LLM}_{\text{vis}}(\mathcal{I}_k,t)$$

其中 $\oplus$ 表示把视觉模型给出的修正补丁合并进脚本。这里的系统代价非常具体：每一轮迭代都要真实渲染，渲染是整条流水线里最慢的一环，场景资产上百时单帧渲染耗时显著，迭代数轮意味着时间成本成倍叠加。这是论文自述的局限之一——渲染慢。另一个代价是视觉模型的判读本身可能出错：GPT-V 对遮挡关系和小尺寸物体的判断并不稳定，它可能把“被桌子挡住的椅子”误判为“椅子缺失”，触发一次错误的修正。回路因此不是单调收敛的，存在震荡的可能。消融实验去掉 GPT-V 反馈后性能下降，说明这个裁判尽管不完美，仍是链路里不可省的一环。

六 · 资产库与物理：两条被论文明确承认的边界

SceneCraft 生成的场景不是从零造几何，而是从 Blender 资产库里取用现成模型，再由脚本摆放。这个设计选择决定了它的能力上限与失败模式。资产库依赖意味着：文本里描述的物体如果在库里没有对应资产，场景图规划得再准也落不了地，智能体只能退而求其次用近似资产替代，视觉上就出现“说的是藤椅，渲染出的是木凳”的偏差。上百个资产的复杂场景之所以能生成，恰恰是因为资产是现成的、脚本只负责布局；一旦要求生成库里没有的物件，这条流水线的优势立刻转为劣势。

物理交互弱是第二条边界。脚本摆放的是静态变换，物体之间没有碰撞求解、没有重力沉降、没有支撑关系验证。约束能保证包围盒不相交，但保证不了“桌子腿接触地面”“吊灯被绳索悬挂而非悬浮”。在咖啡馆例子里，如果约束只写了吊灯 $z$ 坐标，没写悬挂连接件，渲染出的吊灯就是凭空浮着的——视觉上细看能发现，但约束层不会报错。这条边界不是实现疏漏，而是“场景图加脚本”这一表示路线的固有代价：它描述的是布局，不是物理。

把这两条边界和前面的机制放在一起看，这篇论文的问题现场就完整了：它要解决的是“直接写脚本缺规划与反馈、端到端生成缺对象级可控性”这个双重缺口，用的手段是场景图加视觉回路加库学习。而它付出的代价——资产库依赖、渲染慢、物理弱——恰好标出了这条路线在工程上需要继续补的位置。判断这条路线是否值得跟进，关键不在于它能否生成上百个资产，而在于场景图这一层中间表示是否真的把空间关系变成了可修正的对象；从消融结果看，拿掉场景图后性能下降，说明这一层不是装饰，是承重结构。
