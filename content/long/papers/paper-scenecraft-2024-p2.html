一 · 从文本到场景图：规划模块的输入与输出

SceneCraft 的数据流起点不是 Blender，而是一张场景图。给定一段场景描述文本 t，规划模块调用预训练 LLM 产出结构化的场景图 S，这一步在论文的公式中被写作 S = SceneGraph(t)。场景图不是渲染数据，而是一份中间契约：节点是物体实例，边上挂的是空间关系（左/右、前/后、上/下、相邻、包含、朝向等）以及少量属性（类别、数量、尺度量级）。规划模块的职责因此被限定得很窄——它不做几何计算，不做坐标求解，只负责把自然语言里的名词和方位词抽成一张可被下游消费的关系图。

具体机制上，规划模块的提示词要求 LLM 输出固定 schema 的 JSON：物体列表带唯一 id 与类别名，关系列表以 (subject, relation, object) 三元组表达，并对成组物体（如“一排椅子”“围绕桌子的四把椅子”）显式标注基数。这一步的关键设计是把“数量”和“关系”从自由文本里剥离出来，因为下游脚本生成器无法从“几把椅子散落四周”这类表述里稳定推出循环次数和角度分布。场景图因此承担了自然语言到数值约束之间的第一道降熵。

这里存在一个明确的失败模式：LLM 在规划阶段会漏物体或凭空加物体。漏物体通常发生在长描述的后半段，因为上下文里前面的物体占用了注意力；加物体则常见于 LLM 把描述中的修饰语误读为独立实体（例如把“带抽屉的柜子”拆成柜子和抽屉两个节点）。系统代价是下游无法自行发现这类错误——脚本生成器会忠实执行一张错误的图，渲染结果看起来“合理但不对”，只有视觉反馈模块才可能捕捉到缺失。工程上的缓解手段是在规划输出后加一道 schema 校验：检查 id 唯一性、关系两端是否存在、基数是否为正整数，把结构性错误挡在脚本生成之前，而不是留给渲染去暴露。

一个具体例子：描述“一间客厅，沙发靠墙，沙发前有一张茶几，茶几两侧各有一把单人椅，右墙上挂一幅画”。规划模块应产出 5 个节点（沙发、茶几、单人椅×2、画）与 4 条关系（沙发—靠—墙、茶几—前于—沙发、单人椅—侧于—茶几、画—挂于—右墙），其中“各有一把”被展开为基数为 1 的两个独立实例，而不是一个“单人椅组”节点。这个展开动作决定了后续脚本里是写两次放置调用还是写一个循环——SceneCraft 选择展开成独立实例，换取布局约束可以逐物体求解。

二 · 关系到数值约束：脚本生成模块的翻译职责

脚本生成模块接收场景图 S，输出一段可执行的 Blender Python 脚本，即公式中的 Script = LLM(S)。它的核心工作是把定性关系翻译成定量约束。以“茶几在沙发前”为例，翻译不是简单地把茶几放到沙发坐标减一个固定偏移，而是要引入朝向：沙发的局部前向决定茶几的落点方向，偏移量由两个物体的包围盒尺寸共同决定，保证不重叠且留有通道。脚本生成器因此在每个放置语句里同时写入位置、旋转与尺度三类参数，并把“不重叠”作为硬约束体现在偏移量的下界上。

可以用一个伪代码思路概括单个物体的放置逻辑：对场景图中的每个节点，先查其父关系（若有包含关系则继承父物体坐标系），再按关系类型选择约束模板——相邻类关系解一个一维偏移，环绕类关系解角度均分加半径，堆叠类关系解高度累加。约束模板的输出是一组候选位姿，脚本里再对这些候选做包围盒相交测试，取第一个通过测试的位姿。这个流程把 LLM 的自由生成压缩成“选模板、填参数”，显著降低了脚本出现物体重叠的概率，代价是布局的多样性受模板库限制。

$$\mathrm{pose}(o)=\arg\min_{p\in\mathcal{P}(o)}\ \mathrm{overlap}(p,\mathcal{O}_{\mathrm{placed}})\quad \mathrm{s.t.}\ \mathrm{dist}(p,\mathrm{anchor}(o))\in[\ell,u]$$

公式表达的是：在候选位姿集合中选一个与已放置物体集合重叠最小、且与锚点距离落在区间内的位姿。区间下界来自包围盒尺寸之和，上界来自关系语义（“前”不能远到变成“远处”）。这里的系统代价是脚本生成器必须持有已放置物体的状态，因此它不能一次性无状态地生成整段脚本，而要在生成过程中维护一个放置账本；论文的实现把账本编码进提示词的上下文，让 LLM 在写第 k 个物体时能看到前 k−1 个物体的位姿摘要。

失败模式在这一层很典型：比例错误。LLM 对真实世界尺度的先验不可靠，容易把椅子写得和沙发一样高，或把画写得比墙还宽。SceneCraft 的应对是在脚本里使用资产库中资产的真实尺寸，而不是让 LLM 凭空写尺度数值——LLM 只选资产类别，尺寸从资产元数据读取。这直接把“比例”问题从生成问题转成了检索问题，但也埋下了资产库依赖：资产库里没有的类别，脚本只能退化到程序化几何，视觉质量随之下降。一个具体例子是“上百个资产”的复杂场景：当物体数量上升，放置账本的上下文长度线性增长，LLM 在长上下文里对早期物体的位姿记忆变弱，重叠检测的可靠性下降，这是脚本生成模块在规模上的真实瓶颈。

三 · 执行与渲染：Blender 作为确定性后端

脚本进入 Blender 执行，产出渲染图 I，即 I = Blender(Script)。这一层是整个系统里唯一确定性的部分：给定脚本与资产库，渲染结果可复现。它的职责不是智能，而是把符号层的约束变成像素层的证据。渲染配置（相机位姿、光照、分辨率）本身也是脚本的一部分，因此“从哪个角度看场景”是生成出来的，而不是人工设定的——这带来一个副作用：LLM 可能选一个恰好遮住错误的视角，让视觉反馈失效。

系统代价在这里最直观：渲染慢。每个场景要迭代数轮，每轮至少一次渲染，而含上百资产的场景在 Blender 里完成几何构建、材质绑定与光线计算的时间远高于纯文本 LLM 调用。迭代轮数与场景复杂度相乘，构成了整个 agent 循环的主要时延。工程上的权衡是降低单轮渲染成本——降分辨率、减采样、用工作台视图代替最终渲染——但降分辨率会削弱 GPT-V 对比例错误和穿插错误的判读能力，这是一个无法同时满足的两难。

失败模式是渲染崩：脚本语法正确但语义非法，例如对不存在的资产名调用、对空对象设置父级、在布尔修改器上叠加不兼容的几何。Blender 的报错信息对 LLM 并不友好，堆栈里混杂着 C 层与 Python 层的调用，脚本生成器很难从报错反推该改哪一行。SceneCraft 的处理方式是把执行失败也当作一种反馈信号回灌给 LLM，让它依据报错重写脚本片段，而不是让整个 agent 崩溃。这与视觉反馈构成两条并行的修正通道：一条修语法与 API 误用，一条修空间与外观。

具体例子：一个“餐桌周围六把椅子”的场景，脚本用角度均分放置六把椅子，但其中一把的朝向被写成面向桌心之外，渲染图上表现为椅背对着桌子。这个错误在符号层完全合法（位置正确、无重叠），只有渲染图能暴露。这说明 Blender 层的价值不在于计算，而在于提供符号层无法自检的几何证据——符号层能保证“不重叠”，但保证不了“朝向语义正确”。

四 · 视觉反馈：GPT-V 作为判别器而非生成器

渲染图交给 GPT-V 检查，产出的不是新场景，而是针对当前渲染的缺陷清单与修正建议。这个模块的定位必须说清楚：它是判别器，不是生成器。它看的是像素，回答的是“哪里不对”，然后把判断交回给脚本生成模块去改代码。这种分工让视觉模型不必具备写 Blender 脚本的能力，也让脚本修改始终发生在符号层，避免像素级的盲目试错。

具体机制上，反馈被组织成结构化的缺陷条目：物体缺失、物体重叠、比例失调、朝向错误、关系不满足。每条缺陷关联到场景图中的节点 id，从而让脚本生成器知道该改哪个物体的哪条约束。这个 id 关联是设计上的关键——没有它，GPT-V 的反馈只是一段自然语言评论，LLM 需要自己猜测对应关系，修正的命中率会下降。有了 id，修正就变成对特定约束模板的参数调整，而不是重写整段脚本。

失败模式是视觉模型的误判与漏判。GPT-V 对遮挡关系和小尺寸物体的判读不稳定：一个被沙发部分遮住的茶几可能被判为缺失，一个实际存在的轻微穿插可能被忽略。更麻烦的是反馈的稳定性——同一张图在不同轮次可能得到不同的缺陷清单，导致 agent 在两次互相矛盾的修正之间振荡。系统代价因此体现为迭代轮数的不可预测：有的场景两轮收敛，有的场景在“改好了又改坏了”之间循环。工程上的缓解是限制每轮只采纳高置信度的缺陷条目，并保留历史修正记录以防回退。

一个具体例子：描述要求“画挂在右墙”，渲染图里画出现在左墙。GPT-V 指出方位错误并关联到画的节点 id，脚本生成器据此把该节点的锚定墙从右墙改为左墙，重算墙面坐标系下的偏移。若没有 id 关联，LLM 可能去改沙发的朝向，因为它在文本里离“右”字更近。这个例子说明反馈模块的产出质量取决于它能否把像素观察锚定回符号节点。

五 · library learning：跨场景的函数沉淀

library learning 模块的输入是历次迭代中被验证有效的脚本片段，输出是一个可复用的函数库。它的作用不是加速单场景收敛，而是降低后续场景的生成成本：当“环绕放置”“沿墙排列”“堆叠”这类模式被反复写出并修正正确后，它们被抽象成带参数的函数，后续脚本直接调用，LLM 只需填参数而不必重写循环与约束求解逻辑。

具体机制可以概括为三步：识别重复出现的代码模式，把模式中的具体数值抽成形参，把函数签名与用途写入库的索引供 LLM 检索。索引的存在让库不是一堆死代码，而是可以被提示词召回的候选工具集。跨场景复用的判定标准是函数在至少两个不同场景中被调用且未引发执行错误——这个标准把“偶然写对”与“稳定可用”区分开，代价是库的增长速度受限于场景多样性。

失败模式是库的污染与过拟合。一个在特定资产库版本下有效的函数，可能在资产更新后失效；一个针对“四把椅子”写死的角度均分函数，被复用到“三把椅子”时若形参没抽干净就会出错。更隐蔽的问题是 LLM 倾向于过度调用库函数，把本可以用简单语句表达的放置也塞进复杂函数，导致脚本可读性下降、调试困难。系统代价体现在库的维护上：库越大，检索与提示词注入的上下文开销越大，而错误函数的传播范围也越广。

一个具体例子：第一个场景里 LLM 手写了“沿墙等距放置书架”的循环，经过两轮修正后正确；第二个场景描述“沿后墙放三个柜子”，library learning 把该循环抽象为 place_along_wall(objects, wall, spacing) 并入库；第三个场景直接调用该函数，省去了重写与调试。这个链条展示了 library learning 的真实收益：它把一次性的修正成果转化为跨场景的资产，但也把一次性的错误风险转化为跨场景的风险。

六 · 模块分工与数据流的整体形状

把五个模块放在一条数据流上看，SceneCraft 的形状是一个带两条反馈回路的闭环。前向路径是：文本 → 场景图 → 脚本 → 渲染图。第一条回路从渲染图回到脚本生成（视觉反馈，修空间与外观），第二条回路从执行报错回到脚本生成（修语法与 API）。library learning 不在这两条回路上，它是旁路的沉淀器，把回路中稳定下来的片段抽走，供下一次前向路径使用。

这张表暴露了分工的核心张力：每个模块都把一类问题挡在自己这一层，但每一层挡问题的手段都引入新的代价。规划层用结构化 schema 挡自由文本的歧义，代价是 LLM 在 schema 约束下仍会漏项；脚本层用约束模板挡几何错误，代价是布局多样性受限；执行层用确定性渲染提供证据，代价是时延；反馈层用 id 关联挡盲目修正，代价是判别的不稳定；库层用复用挡重复劳动，代价是错误传播。SceneCraft 的方法论价值不在于某个模块特别强，而在于它把“文本到 3D”拆成了一条每层都可检查、可回灌的流水线，让错误在符号层被尽量拦截，而不是全部堆到像素层去碰运气。

从工程判断的角度看，这条流水线的瓶颈位置随场景规模移动。小场景里瓶颈在视觉反馈的判别质量，因为符号层几乎不出错；上百资产的大场景里瓶颈移到脚本生成的放置账本与渲染时延，因为上下文长度和几何复杂度同时上升。这也解释了论文消融里场景图、GPT-V 反馈、library learning 三项各自被移除后性能下降的原因：它们分别守住了规划、修正、复用三个不同的失效面，缺一个就有一个失效面失守。而资产库依赖与物理弱这两条局限，恰好落在这条流水线之外——前者是执行层的输入约束，后者是整条流水线根本没有物理求解模块，脚本只写位姿不写动力学，所以场景看起来对但推不动。
