一 · 失效条件：场景图规划器在什么输入上崩掉

SceneCraft 的整条链路可以写成三段复合映射：文本先经 LLM 规划为场景图，场景图再经 LLM 转成 Blender Python 脚本，脚本在 Blender 里执行并渲染出图像，图像交给 GPT-V 做视觉反馈。失效不是均匀分布在三段上的，而是集中在第一段与第三段的接口处——场景图既要有足够的语义自由度容纳文本描述，又要有足够的数值确定性让脚本生成器不产生歧义。这个双重身份就是它的脆弱点。

具体机制上，场景图节点承载物体类别、实例标识与属性，边承载空间关系（在……之上、贴着、围绕、朝向）。规划器把关系翻译成约束时，必须把定性谓词映射为数值区间，例如“贴着墙”被写成沿墙法向的偏移量落在某个容差内。问题在于这个映射是 LLM 在无显式监督下自行选择的：同一句描述在不同轮次可能得到不同的容差量级，导致脚本生成器拿到的约束时而过紧（求解器无解，物体互相穿插）时而过松（关系名义满足但视觉上不成立）。形式化地，设关系集合为 $R$，每个关系 $r\in R$ 被赋予约束函数 $c_r(\mathbf{x})\le \tau_r$，其中 $\mathbf{x}$ 是场景中全部实例的位姿与尺度拼接向量。规划器的输出实际上是 $(\mathcal{S}, \{\tau_r\})$，而 $\{\tau_r\}$ 不在任何显式校验环节里被检查。当 $R$ 中关系数量增长，可行域 $\bigcap_r\{c_r\le\tau_r\}$ 的体积随维度指数收缩，容差稍有偏差就落入空集。

$$\mathcal{F}=\{\mathbf{x}\mid c_r(\mathbf{x})\le \tau_r,\ \forall r\in R\},\qquad \text{feasible}\iff \mathcal{F}\neq\varnothing$$

失败模式表现为两类。第一类是硬失败：Blender 执行脚本时物体包围盒相交、比例失真到渲染崩，或脚本本身因 API 调用顺序错误抛异常。第二类是软失败：脚本跑通、渲染出图，但 GPT-V 看不出问题——因为渲染视角恰好掩盖了重叠，或者光照让穿插处不可辨。软失败更危险，它让迭代循环提前收敛到一个错误解。系统代价在这里体现为迭代预算的浪费：每一轮都要付一次完整渲染的代价，而渲染是这条链路里最慢的一环，资产数量上百时单帧渲染时间随多边形数与材质复杂度上升，迭代轮数被渲染吞吐直接卡死。

具体例子：描述“一张长桌周围摆十把椅子，桌上散落餐具”。规划器给出“围绕”关系，容差按角度均匀分布设定。若容差过紧，十把椅子在圆周上等距排布时相邻包围盒相切，脚本求解失败；若容差过松，椅子被放到桌腿投影范围内，渲染图里桌腿与椅面穿插，但俯视角看不出来。前者触发重试，后者静默通过。这就是不能照搬的第一处：容差不是超参，是语义的一部分，必须在场景图里显式携带并被下游校验，而不是留给 LLM 隐式决定。

二 · 资产库依赖：library learning 的复用边界

library learning 是 SceneCraft 里最容易被误读为“通用能力”的模块。它的机制是把跨场景反复出现的脚本片段抽象成带参数的函数，沉淀进一个库，后续场景生成时优先调用库函数而非从零写代码。抽象的依据是语法结构与调用频次：当某个子图（例如“沿墙排列一组同类别物体”或“在平面上做环形布局”）在多个场景的脚本中出现，系统把它提升为函数，参数化其中的实例数量、间距、朝向。这确实降低了长脚本的生成难度，也让 LLM 的上下文预算从“每次重写全部布局逻辑”变成“调用库函数 + 填写参数”。

但库的复用边界由资产库决定，不由代码结构决定。SceneCraft 的脚本必须引用 Blender 资产库中真实存在的网格与材质，库函数一旦把某个资产名硬编码进参数默认值，跨场景复用就会失效——目标场景里没有那个资产，函数调用直接失败。更隐蔽的是尺度耦合：库函数里“间距”参数的合理量级取决于资产的实际尺寸，而不同资产库的尺寸约定不一致，同一函数在另一个资产集上产生视觉上过密或过疏的布局。系统代价是库的维护成本随资产库异构性上升，函数数量增长并不单调带来收益，反而增加 LLM 选择函数的决策负担。

复用层级可跨场景复用的条件失效表现
布局逻辑（环形、沿墙、网格）资产类别语义一致，尺寸量级可比间距参数失配，视觉密度错误
资产引用目标资产库含同名或同类别资产脚本引用缺失资产，执行报错
材质与光照设置渲染器版本与材质节点兼容节点类型不识别，渲染退化为默认材质

具体例子：某场景沉淀出“书架沿墙排布”函数，参数含层数与每层书本数量。换到一个资产库中书本网格是合并单体而非分层组件，函数仍能跑，但每层书本被压成一块板，GPT-V 反馈“书本不像书”，迭代循环于是反复调整参数却无法修复——因为问题在资产结构而非参数。这暴露了 library learning 的一个结构性局限：它抽象的是代码，不是几何语义。工程复现时若把库当作跨数据集的可移植资产，会在换库时付出成倍的调试代价。可照搬的是“沉淀高频子图”的思路，不可照搬的是“库函数默认参数可跨库复用”的假设。

三 · 视觉反馈回路的盲区与物理缺位

GPT-V 反馈是闭环的关键，但它是一个二维判别器，作用在单张或少量渲染图上。机制上，系统把渲染图与文本描述一起送入 GPT-V，让其判断空间关系是否合理、物体是否重叠、比例是否协调，输出自然语言批评，再由 LLM 把批评翻译成脚本修改。这条回路的能力上限由渲染视角决定：判别器只能看到被渲染出来的部分，遮挡、背面、场景内部的关系不在其观测范围内。于是反馈回路对“可见性”有隐式依赖——关系越是被遮挡，越难被纠正。

更根本的缺位是物理。SceneCraft 生成的是静态场景脚本，物体位姿由约束求解与 LLM 写入，没有刚体动力学、没有接触力、没有稳定性检验。一个视觉上合理的布局可能物理上不可站立：细高物体重心偏移、堆叠物体接触面不足、悬挂物体无支撑。系统对此没有任何校验环节，因为渲染管线不模拟物理。代价在后续使用阶段显现：若场景被导入仿真或游戏引擎，物理引擎会在第一帧就把这些物体弹开或穿透，此时修复成本远高于生成阶段。

$$\text{accept}=\mathrm{GPTV}(\mathcal{I},t)\ \wedge\ \text{physics}(\mathbf{x})=\text{true}$$

上式是工程上应当补上的验收条件，而原文的接受判据只有左半部分。具体例子：描述“桌上叠放三层盘子”。脚本按高度递增放置，包围盒不相交，渲染图看起来整齐，GPT-V 通过。但盘子之间接触面积极小、质心偏移，导入物理引擎后整摞倒塌。这不是 LLM 规划的错误，是验收断言缺失的错误。可照搬的是“渲染—判别—修正”的回路结构，不可照搬的是“视觉合理即场景合理”的判据。复现时必须在回路末端加一层轻量物理检查（至少是支撑关系与质心投影的几何检验），否则回路收敛的是图像，不是场景。

四 · 被谁继承、被谁替代：路线定位

SceneCraft 在路线图上占据的位置是“LLM 代码生成 + 视觉闭环”这一支。它与 WorldGen 的 LLM 布局路线呼应：两者都把场景生成拆成“先规划结构、再落地为可执行表示”，差别在于落地表示——SceneCraft 落地为 Blender Python 脚本，WorldGen 落地为布局参数。这个差别决定了它们的继承关系不同。脚本表示的优势是可表达任意程序化构造（循环、条件、参数化组合），劣势是与具体渲染器绑定；布局参数表示的优势是引擎无关，劣势是表达力受限于预定义的布局原语。

被继承的部分是“场景图作为中间表示”与“视觉反馈作为修正信号”这两个设计。后续工作若要做可控场景生成，几乎必然保留一个显式的结构化中间层，因为纯端到端的文本到图像或文本到三维模型无法提供实例级的可编辑性。被替代的部分是脚本作为最终产物这一选择：当目标引擎不是 Blender，或当场景需要实时交互与物理仿真时，脚本层会被更抽象的表示替代，SceneCraft 的脚本生成器则退化为一个后端插件。library learning 的沉淀机制也被继承，但继承者通常把它改成与资产库解耦的形式——库函数只接收抽象几何参数，资产绑定推迟到执行期。

系统代价在于耦合度。脚本与 Blender 的绑定让整条链路无法在不装 Blender 的环境里运行，渲染慢的代价也无法通过换渲染器缓解，因为脚本里的 API 调用是 Blender 专有的。具体例子：若要把 SceneCraft 的思路搬到 Web 端三维展示，脚本层必须整体重写为引擎无关的场景描述格式，此时 library learning 沉淀的函数全部作废——它们抽象的是 Blender API 调用序列，不是布局语义。这说明复现时应把“布局语义”与“引擎调用”分成两层，前者沉淀、后者生成，而不是像原文那样把两者混在同一层脚本里。

五 · 工程复现清单与验收断言

复现 SceneCraft 不是复现一篇论文的数字，而是复现一条能稳定跑通的流水线。清单按依赖顺序排列，每一项都对应一个可观测的失败模式，缺一项就会在某个环节静默退化。

  • 场景图 schema 必须显式携带数值约束与容差，而不是只存定性关系字符串；否则脚本生成器无从判断约束松紧，失败模式是可行域为空或关系名义满足。
  • 资产库必须做尺寸与类别的规范化索引，脚本生成前校验引用的资产存在且尺度可比；否则失败模式是执行期报错或视觉密度错误。
  • 渲染必须固定视角集合与分辨率，GPT-V 反馈基于多视角而非单视角；否则失败模式是遮挡关系漏检，回路提前收敛。
  • 迭代循环必须有轮数上限与失败分类（硬失败重试、软失败换视角复查）；否则失败模式是渲染预算被无界消耗。
  • library learning 的函数签名必须只含抽象几何参数，资产绑定在执行期解析；否则失败模式是换库即失效。
  • 验收阶段必须有物理或几何的支撑性检验，独立于 GPT-V 判据；否则失败模式是视觉通过、物理崩溃。

验收断言应当写成可执行的谓词，而不是人工目检。最小集合包括：实例包围盒两两不相交（或相交体积占比低于阈值）、每个关系的约束残差 $c_r(\mathbf{x})-\tau_r$ 在容差内、每个非地面实例存在支撑链回溯到地面、渲染图中目标物体的可见像素占比高于阈值（保证反馈回路能看到它）。这些断言把“空间关系合理”从主观判断变成可计算量，也让迭代循环的终止条件从“GPT-V 说可以了”变成“断言全部通过”。

$$\text{pass}=\bigwedge_{i}\text{bbox-disjoint}(i)\ \wedge\ \bigwedge_{r}\left(c_r(\mathbf{x})\le\tau_r\right)\ \wedge\ \bigwedge_{o}\text{supported}(o)\ \wedge\ \bigwedge_{o}\text{visible}(o)$$

具体例子：一个含上百资产的室内场景，断言检查发现三处包围盒相交、一处支撑链断裂。相交处对应脚本里两个循环的间距参数在边界条件下退化，支撑链断裂对应一个被放到桌面边缘外的花瓶。这两类问题在单视角渲染图里都不明显，但断言直接定位到实例与关系，修复只需改参数而非重跑整条链路。这就是复现时最该照搬的工程判断：把 LLM 的自由度限制在规划层，把正确性交给确定性断言，视觉反馈只作为软信号的补充而非唯一判据。SceneCraft 原文的回路把 GPT-V 放在判据位置，复现时应把它降级为提示器，判据交给断言——这是照搬其架构、但不照搬其验收方式的具体落点。
