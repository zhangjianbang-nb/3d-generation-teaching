一 · 复现边界：哪些能照搬，哪些必须自建

SceneCraft 的复现难点不在模型权重，而在系统边界。论文本身不训练任何网络，整条链路是「预训练 LLM 写场景图 → LLM 写 Blender Python → Blender 无头渲染 → GPT-V 读图打分 → 反馈回注 → library learning 沉淀函数」。这意味着复现者拿不到任何 checkpoint，必须自己拼装四类外部依赖：一个能稳定输出结构化场景图的文本 LLM、一个能读图的视觉模型、一个可脚本化调用的 Blender 运行时、以及一套资产库。四者中任何一个版本漂移，整条链路的失败模式都会变，所以复现的第一步不是写代码，而是把「不可控项」显式列成配置，并在验收断言里对它们做版本钉死。

需要强调的是，论文的贡献是智能体编排与 library learning 机制，不是某个模型的精度。因此复现的目标应是「机制可跑通、失败可定位」，而不是「复刻论文里的场景外观」。资产库尤其如此：论文明确依赖 Blender 资产库，资产的名字、层级、缩放约定在不同 Blender 版本与不同资产包之间并不一致，LLM 生成的 bpy.ops.mesh.primitive_* 或资产 append 调用一旦指向不存在的资产名，脚本会在执行期而非生成期崩溃。复现者必须把资产清单做成可查询的注册表，让 LLM 在写脚本前先看到合法资产名，这是最小可跑版本能否成立的分水岭。

另一个不能照搬的点是渲染预算。论文的迭代修正依赖「渲染—看图—改脚本」的闭环，每一轮都要真实出图，渲染慢是论文自己承认的代价。复现时若把迭代轮数照抄成「数轮」而不设超时与分辨率上限，单场景耗时会被渲染吞掉，调试周期被拉长到不可接受。工程判断是：把渲染分辨率、采样数、迭代上限三者做成显式超参，并在第一轮就用低分辨率跑通闭环，再逐级抬高，而不是一上来就追求论文级画质。

二 · 目录结构：把智能体、执行器、资产与验收分离

最小可跑版本的目录应围绕「一次场景生成 = 一次可重放的作业」来组织。核心原则是：LLM 侧的一切（提示词、场景图 schema、脚本模板）与 Blender 侧的一切（执行器、资产注册表、渲染配置）物理分离，中间只通过序列化文件交接。这样任何一次失败都能定位到「是图错了、脚本错了、还是执行环境错了」，而不是在一坨耦合代码里猜。

  • agent/：场景图规划器、脚本生成器、视觉反馈解析器、library learning 管理器。每个模块只吃 JSON、只吐 JSON。
  • schema/：场景图的 JSON Schema 与脚本 AST 的约束定义，用于在 LLM 输出后做结构校验，校验失败即重试而非直接送进 Blender。
  • executor/：Blender 无头调用的封装，负责拼命令行、注入资产路径、捕获 stdout/stderr、超时杀进程、收集渲染产物。
  • assets/：资产注册表（资产名 → 文件路径 → 包围盒尺寸 → 默认朝向），以及一份「合法资产名清单」供提示词注入。
  • library/：library learning 沉淀下来的函数库，按「函数名 + 签名 + 适用场景标签」索引，跨场景复用时按标签检索注入提示词。
  • runs/：每次作业的落盘目录，含输入文本、每轮场景图、每轮脚本、每轮渲染图、每轮视觉反馈、最终产物与耗时日志。
  • asserts/：验收断言的实现，分「结构断言」「执行断言」「视觉断言」三层，可独立对 runs/ 下的历史作业重放。

这个结构的关键在于 runs/ 的可重放性。SceneCraft 的迭代修正本质是一个带反馈的搜索过程，若不留存每一轮的中间态，就无法回答「第几轮开始崩、崩在场景图还是脚本」。工程上应把每轮的场景图与脚本都当作一等产物落盘，视觉反馈只存结构化结论（例如「物体 A 与 B 重叠」「比例失真」）加原始图像路径，而不是把整段自然语言回复塞进日志。

一个具体例子：当 LLM 生成的脚本在 bpy.ops.wm.append 处因资产名拼写失败时，执行器应把 stderr 原文与退出码写入该轮目录，并把「资产名不在注册表」这一结构化原因回注给脚本生成器，让它下一轮从合法清单里选，而不是让 LLM 自由发挥再撞一次墙。这个回注路径必须在目录结构里有明确归属，否则反馈会散落在各模块的临时变量里。

三 · 数据准备：场景描述、资产注册表与提示词契约

论文的数据集是自建场景描述加 Blender 场景，复现时不需要复刻其规模，但需要复刻其「输入形态」。最小可跑版本准备三类数据：一是若干条文本场景描述，每条要含物体清单、数量级与空间关系词（例如「在……左侧」「围绕……排列」「位于……之上」），因为场景图规划器正是要把这些关系词转成数值约束；二是资产注册表，每条记录资产名、文件路径、包围盒三维尺寸、默认朝向与单位缩放，这是把「关系」落成「坐标」的唯一依据；三是提示词契约，即场景图 JSON 的字段定义与脚本生成时必须遵守的调用约定。

资产注册表是数据准备里最容易被低估的一项。论文承认资产库依赖是局限，复现时若不把包围盒尺寸纳入注册表，LLM 只能凭语义猜物体大小，比例错误几乎必然出现。把尺寸写进注册表后，场景图规划器可以在生成阶段就做一次粗算：给定「桌子上放三个杯子」，用桌面的包围盒顶面高度与杯子的底面尺寸算出合法放置区间，再把区间作为数值约束写进场景图，而不是留给脚本生成器临场发挥。这一步把「比例错误」从执行期前移到规划期，是复现能否稳定的关键机制。

$$\text{placement}(o_i)=\{\,p \mid p\in \text{top}(o_j),\ \text{dist}(p,\partial \text{top}(o_j)) \ge r_i\,\}$$

上式是一个玩具级的放置约束：物体 o_i 的合法位置集合是支撑面 o_j 顶面上、距离边界不小于其自身半径 r_i 的点集。它不追求物理精确，只保证「不悬空、不出界、不互相穿透」这三条最低验收线。复现时应把这类约束写成场景图 schema 里的可选字段，让 LLM 填数值而非自由文本，这样脚本生成器拿到的就是可直接转成 location 与 rotation 的确定量。

提示词契约同样要落到数据里。脚本生成器的提示词必须包含：合法资产名清单、可用的 library 函数签名、Blender 版本与 API 约定、以及「只输出可执行 Python、不输出解释」的硬约束。把契约做成文件而非硬编码字符串，才能在 library learning 新增函数时自动扩充提示词，避免人工同步遗漏。失败模式很具体：若提示词未声明 Blender 版本，LLM 可能写出已被弃用的 API 调用，脚本在执行期报 AttributeError，而这类错误与场景逻辑无关，却会污染视觉反馈的判断。

四 · 超参配置：迭代、渲染与 library 的三组旋钮

SceneCraft 无需训练，所谓超参全部是编排参数。复现时应把它们分成三组，每组都有明确的代价函数，避免「调大一点看看」式的盲目试错。

组别参数作用代价或失败模式
迭代组最大迭代轮数、单轮视觉反馈是否触发重写、场景图是否允许回退重规划控制「渲染—看图—修正」闭环深度轮数过大时渲染耗时线性增长；反馈解析错误会导致震荡重写
渲染组分辨率、采样数、是否启用降噪、超时阈值决定视觉反馈的可读性与单轮成本分辨率过低时 GPT-V 读不出重叠与比例；过高时单轮超时被杀
库组函数沉淀的最小复用次数、检索注入的 top-k、是否允许库函数被改写控制 library learning 的沉淀与复用沉淀过早会固化错误实现；top-k 过大挤占提示词预算

迭代组的关键判断是「反馈触发条件」。不是每一轮渲染都需要重写脚本：若视觉反馈只报告「光照偏暗」这类与几何无关的问题，重写脚本是浪费；只有当反馈命中几何类断言（重叠、悬空、比例、朝向）时才应触发重写，否则只调整渲染参数或直接接受。这个分流机制能显著压低无效迭代，也是复现时最容易被忽略的一处工程优化。

渲染组的超时阈值必须与分辨率联动设定。论文承认渲染慢，复现时若把超时设得比最坏渲染时间还短，执行器会频繁杀进程，而杀进程留下的半成品图像会让 GPT-V 给出误判，进而触发错误重写，形成「越调越乱」的正反馈。正确做法是先测出目标分辨率下的渲染耗时分布，把超时设为分布的保守上界，并在超时被杀时把该轮标记为「环境失败」而非「脚本失败」，不让它进入反馈回路。

库组的核心是沉淀门槛。library learning 把常用函数沉淀成库，但若一个函数只在一个场景里用过一次就入库，库里会堆满特化实现，跨场景复用时反而误导脚本生成器。复现时应要求函数在至少两个不同场景中被验证可用才入库，并在入库时记录其适用标签；检索注入按标签匹配而非按名字模糊匹配，避免把「摆桌子」的函数注入到「摆吊灯」的场景里。失败模式是库污染：一旦错误函数被沉淀并被反复注入，后续所有场景都会继承同一个几何错误，且难以从最终产物反推源头。

五 · 验收断言：三层断言与最小可跑版本的判定

验收断言是复现的收口。SceneCraft 的产物是脚本加渲染图，因此断言必须同时覆盖「脚本可执行」「场景图合法」「渲染可读」三个层面，任何一层缺失都会让「跑通了」变成主观判断。建议按三层实现，每层都可对 runs/ 历史作业独立重放。

  • 结构断言：场景图通过 JSON Schema 校验；每个物体引用的资产名在注册表中存在；每条空间关系都能映射到至少一个数值约束字段；物体数量与描述中的量词一致。
  • 执行断言：脚本在无头 Blender 中以退出码 0 结束；无未捕获异常；渲染产物文件存在且尺寸非零；执行耗时在超时阈值内；脚本未调用注册表之外的资产。
  • 视觉断言：渲染图中可检测到预期数量的物体实例；无大面积互相穿透；支撑关系成立（物体底面与支撑面顶面的高度差在容差内）；朝向与描述一致。

结构断言里「关系可映射」这一条最容易被跳过，却最能暴露场景图规划器的缺陷。若一条关系写成自然语言而无法落成数值字段，脚本生成器只能猜，猜错就是比例或重叠错误。复现时应把「无法映射的关系」计为硬失败并触发重规划，而不是让脚本生成器带着模糊关系往下走。一个具体例子：描述里的「围绕中心排列」若未转成极坐标角度与半径字段，脚本生成器可能把物体摆成一条直线，视觉断言里的「围绕」检测就会失败，而失败原因其实在规划期而非执行期。

视觉断言的实现要克制。不要试图用视觉模型做精细几何测量，而是让它回答有限几个二值问题：物体是否重叠、是否悬空、数量是否对得上、朝向是否明显错误。把开放式的「这张图好不好」换成封闭式的断言问答，反馈才可解析、可重放、可归因。失败模式是开放式反馈导致的重写震荡：视觉模型每轮给出不同的模糊评价，脚本生成器每轮朝不同方向改，迭代轮数耗尽仍不收敛。封闭式断言把反馈压缩成有限状态，震荡概率大幅下降。

最小可跑版本的判定标准应是：单条描述在迭代上限内产出退出码为 0 的脚本、非零渲染图、且三层断言全部通过。这个标准不追求场景美观，只追求链路闭合与失败可定位。常见崩溃点按出现频率排列：资产名不在注册表、Blender API 版本不匹配、渲染超时被杀、场景图关系无法映射、library 函数签名与调用不一致、视觉反馈解析失败导致空反馈。每一个都应在 asserts/ 里有对应的显式检查，而不是靠人工看日志。

六 · 常见崩溃点的定位手法与工程判断

崩溃点定位的核心是把「智能体失败」与「环境失败」分开。前者是 LLM 输出不合格，后者是 Blender、资产或渲染管线的问题。二者混在一起时，重试策略会失效：对环境失败重试只会重复撞墙，对智能体失败不重试则浪费了反馈回路。工程上应在执行器里对退出原因做分类，把资产缺失、API 弃用、超时、渲染空图归为环境类，把 schema 校验失败、关系不可映射、脚本语法错误归为智能体类，两类走不同的重试与回注路径。

资产缺失的定位最直接：执行器捕获 stderr 后匹配资产名，回注「合法清单」并强制脚本生成器从清单中选择。API 弃用的定位需要版本钉死：在提示词与执行器两侧同时声明 Blender 版本，执行器在启动时打印版本号并写入作业目录，任何 AttributeError 都先怀疑版本漂移而非 LLM 幻觉。渲染超时的定位依赖耗时日志：把每轮渲染耗时写入 runs/，超时阈值据此调整，而不是拍脑袋设一个固定值。

关系不可映射的定位要靠结构断言的前置校验。场景图规划器输出后先跑一遍「关系 → 数值字段」的映射检查，未映射的关系直接打回重规划，不进入脚本生成。这一步把一类隐性错误挡在渲染之前，省掉整轮渲染成本。library 函数签名不一致的定位则靠库的元数据：每个库函数记录签名与调用示例，脚本生成器注入提示词时带上签名，执行器在脚本静态检查阶段比对调用参数个数，不一致即判为智能体失败并回注正确签名。

视觉反馈解析失败的定位最隐蔽。视觉模型返回的自然语言若无法解析成结构化断言结论，反馈回路就断了，表现为「迭代轮数照跑但脚本不变」。复现时应对视觉反馈做严格的输出契约：要求它按固定字段返回二值结论与简短理由，解析失败即视为该轮反馈无效并记录，而不是把整段文本塞给脚本生成器。工程判断是：宁可少一轮有效反馈，也不要让不可解析的反馈污染重写方向，因为后者会让失败原因从「视觉模型输出不合契约」漂移成「脚本越改越差」，归因链条断裂。

最后落在 library learning 的复现判断上。库的价值在于跨场景复用，而复用的前提是函数语义稳定。复现时应把库函数当作有版本的产物：每次沉淀记录其来源场景、验证通过的断言集合、以及被复用的次数；一旦某函数在复用场景中触发视觉断言失败，应将其标记为可疑并暂停注入，而不是继续沉淀新函数掩盖问题。这个机制把 library learning 从「只增不减的缓存」变成「带质量信号的函数库」，是复现能否长期稳定运行的关键工程判断。
