一 · 四模块流水线的数据契约与接口开销

把世界写成 \(\mathcal{W}=\mathrm{Compose}(\mathrm{Layout}_{\mathrm{LLM}}(t),\mathrm{Terrain}_{\mathrm{proc}},\{\mathrm{Gen}(o_i)\})\) 只是数学上的一个复合算子；工程上它是一条四段流水线，每一段之间都存在显式的数据契约。第一段 LLM 输出的是场景图，不是坐标：节点是房间、区域、地标、物件类别，边是“包含”“相邻”“朝向”“可达”这类拓扑与语义关系。第二段程序化模块消费场景图，把它翻译成地形高度场、建筑体块、道路与门洞的几何骨架。第三段扩散模型逐物体生成网格与贴图。第四段 object-aware 组合把生成物按场景图给出的槽位放置，处理朝向、支撑面、碰撞与尺度归一。

接口开销主要不在算力而在“翻译层”。场景图到程序化参数需要一个确定性映射：房间面积区间、层高、走廊宽度、地形坡度上限都必须由工程常量约束，否则 LLM 输出的“宏伟大厅”会被程序化模块解释成任意尺度。物体槽位到扩散提示需要模板化：槽位携带类别、风格标签、尺寸先验与朝向约束，扩散侧据此拼装提示词并选择采样分辨率。组合层则需要一份统一的资产描述，至少包含包围盒、原点约定、朝向轴、材质槽与碰撞代理。任何一处约定不一致，都会在最后一段以穿模、悬空或比例失真的形式暴露。

一个具体例子：LLM 场景图给出“村口有一座石桥跨过小河，桥头有灯笼”。程序化模块据此切出河道与桥面体块，并在桥头预留两个挂件槽位；扩散侧按“石质、风化、低多边形风格”生成桥体与灯笼；组合层把灯笼原点对齐到槽位挂点，而不是包围盒中心。若槽位只写了类别没写挂点语义，组合层只能按包围盒中心放置，灯笼就会陷进桥柱。这类失败不是模型能力问题，而是契约缺字段。

系统代价体现在串行依赖上：第四段必须等前三段全部完成才能开始，流水线无法像纯扩散那样批量并行。缓解手段是把组合层做成增量式——每生成一个物体就尝试落位并写回场景图状态，失败则回退到槽位重新采样，而不是等全量资产生成完再统一摆放。这要求场景图在流水线中途可变，也要求组合层维护一份“已占用体积”的空间索引。

二 · 复杂度分解：谁在承担规模

大世界可穿越的关键是把复杂度从“单次生成”转移到“分层复用”。设世界被划分为 \(N\) 个区块，每区块含 \(M\) 个物体槽位，单物体扩散采样成本为 \(C_g\)，程序化地形单区块成本为 \(C_t\)，LLM 布局一次调用成本为 \(C_l\)。总成本近似为

$$C_{\text{total}} \approx C_l + N\cdot C_t + N\cdot M\cdot C_g + C_{\text{compose}}(N,M)$$

其中组合项 \(C_{\text{compose}}\) 随已放置物体数增长，若用朴素两两碰撞检测则为 \(O((NM)^2)\)，必须用均匀网格或 BVH 把近邻查询压到接近线性。真正的工程杠杆在 \(M\) 与 \(C_g\)：远景物体可以用低分辨率、低面数、甚至程序化代理替代扩散生成，只有玩家可达半径内的槽位才走全分辨率扩散。这相当于给流水线加一个 LOD 调度器，按距离与可见性决定哪些槽位触发第三段。

另一个复杂度来源是地形与建筑的耦合。程序化地形先生成高度场，建筑体块必须贴合地面，否则出现悬空地基或埋入山坡。做法是先在地形上做平整度采样，把建筑 footprint 内的地形抬平或削平，再生成体块；这一步的代价是地形网格的局部重采样，属于 \(C_t\) 内部的额外开销，但避免了组合层去修地形。

失败模式很典型：当 \(N\) 增大而 LLM 只被调用一次时，场景图必须覆盖全部区块，输出长度与一致性压力陡增，容易出现远处区块语义空洞或自相矛盾（同一地标被放在两个区域）。工程上把 LLM 调用改为分层：先出全局骨架（区域划分、主地标、道路连通），再对每个区块单独出细节场景图，父图给子图传递边界条件。代价是多次调用与跨调用的一致性维护，需要一份共享的全局状态表。

具体例子：一个包含村庄、林地与山口的区块群，全局骨架只声明“村庄在河谷、林地在东坡、山口连接两区”，区块级调用再各自展开房屋、树木与隘口物件。若不分层，单次 LLM 输出要在同一段文本里同时保证三区拓扑正确与每区细节，长度一长就丢约束。

三 · 显存与通信：扩散段的真实瓶颈

第三段是显存主战场。物体扩散通常以多视角或三平面表示生成网格，采样步数与分辨率共同决定峰值显存。设单物体在分辨率 \(R\) 下需保存 \(K\) 个中间特征图，每图通道数为 \(C\)，则单物体激活显存近似正比于 \(K\cdot C\cdot R^2\)。批量生成 \(B\) 个物体时，若不共享批次则显存线性增长；共享批次能摊薄权重与调度开销，但要求所有物体分辨率一致，而槽位尺寸差异很大（灯笼与房屋），强行同分辨率会浪费大量显存在空区域上。

工程解法是按尺寸分桶：把槽位按包围盒体积分成若干桶，同桶内物体共享分辨率与批次，桶间串行。这牺牲了部分并行度，换来显存可控。另一个手段是生成与组合解耦到不同设备：扩散卡只负责出资产并写入磁盘或主机内存，组合卡负责落位与碰撞，二者通过资产队列通信。通信量等于资产网格与贴图的字节数，贴图往往是大头，因此资产在传输前应先做量化与压缩，组合层按需解码。

通信瓶颈还出现在 LLM 段与程序化段之间。场景图是文本或结构化 JSON，体积小，但语义解析与校验需要额外一轮模型调用或规则引擎；若把校验放在 GPU 侧做嵌入相似度比对，就产生一次主机到设备的传输。更常见的坑是把场景图直接塞进扩散提示，导致提示过长被截断，槽位约束丢失。正确做法是组合层持有结构化槽位，扩散提示只携带该槽位相关的短描述。

失败模式：显存碎片化。反复以不同分辨率采样会让缓存分配器留下大量不可用块，表现为“明明总算力够却 OOM”。对策是固定一组分辨率档位并在启动时预热，避免运行中动态形状。另一个失败是资产队列积压：扩散段产出速度高于组合段落位速度时，队列膨胀吃满主机内存；需要背压机制，让扩散段在队列满时暂停采样。

具体例子：一个区块含数十个槽位，其中大部分是灌木、石块这类小物件。若全部按房屋分辨率生成，显存与时间都被小物件拖垮；分桶后小物件走低分辨率档，房屋单独走高档，峰值显存回落到可调度范围。

四 · 伪代码思路：调度器与组合循环

系统骨架可以写成三层循环：全局布局、区块展开、槽位落位。伪代码思路如下（以文字描述结构，不展开为代码块）：入口接收文本提示，调用 LLM 得到全局场景图并写入世界状态；对每个区块，调用 LLM 结合父图边界条件展开细节场景图；程序化模块依据区块图生成地形与建筑骨架并注册到空间索引；调度器遍历槽位，按距离与可见性决定分辨率档，提交扩散任务；组合循环从资产队列取回物体，查询空间索引找候选落位，做支撑面贴合、朝向对齐与碰撞检测，成功则写回世界状态并更新索引，失败则把槽位标记为待重采样并附上失败原因。

组合循环的关键是失败原因要可回传。碰撞失败、支撑面缺失、尺度越界是三类不同错误，对应不同修复策略：碰撞失败调整位置或缩小包围盒，支撑面缺失回退到程序化模块补几何，尺度越界回到扩散段换分辨率或改提示。若只返回布尔失败，调度器只能盲目重试，浪费采样预算。

调参顺序在这里体现得很直接：先固定程序化模块的常量（层高、走廊宽度、坡度上限），再固定组合层的容差（贴合距离、碰撞余量、尺度归一区间），最后才调扩散段的采样步数与引导强度。原因是前两层决定了几何合法性，扩散段只负责外观；若先调扩散，外观再好也会被组合层拒绝。一个常见反模式是先追求单物体生成质量，再回头发现所有资产都因尺度不一致而无法落位。

系统代价：组合循环是串行热点。每个物体落位都要查询空间索引并可能触发重采样，循环吞吐受最慢槽位拖累。缓解是把落位做成两阶段：先做快速粗放置（只查包围盒重叠），把明显冲突的槽位批量打回；再对通过粗放置的槽位做精确贴合。粗放置可以向量化，精确贴合才逐个体做。

具体例子：一条街道两侧的房屋槽位，粗放置阶段发现两栋房屋包围盒重叠，直接判定其中一栋需要换槽位或缩尺度，无需进入精确贴合；精确贴合只处理与地形、道路的接触关系。这把大部分冲突挡在便宜阶段。

五 · 工程坑：坐标系、尺度与资产质量

坐标系是第一大坑。LLM 场景图是语义的，程序化模块常用右手系、Y 轴向上，扩散模型训练数据可能来自不同约定，导出到游戏引擎又有自己的轴向与前向定义。工程上必须在组合层设一个唯一的世界坐标系，并在每个模块入口做显式转换，转换矩阵写成常量表而不是散落在代码里。否则表现为物体整体旋转 90 度或镜像，且难以定位是哪一段引入的。

尺度是第二大坑。扩散模型对绝对尺度不敏感，生成的房屋可能相对门洞过大或过小。组合层需要尺度归一：以槽位声明的尺寸先验为准，把生成资产缩放到包围盒匹配，再检查关键比例（门高与层高之比）是否落在合理区间，越界则拒绝。尺度归一不能简单按最长边缩放，否则扁平物体（地毯、路面）会被拉变形；应按体积或按语义主轴缩放。

资产质量参差是系统级问题。扩散生成的网格可能非流形、带自交、法线朝向混乱，直接进引擎会引发光照错误或物理穿透。组合层应挂一个轻量几何校验：检查闭合性、退化面比例、包围盒有效性，不合格资产打回重采样而不是强行修复。修复非流形网格的成本往往高于重新采样。

还有一类坑是“语义正确但玩法错误”：LLM 把门放在不可达的墙后，或把关键路径上的物件生成成不可穿越的障碍。这属于布局与游戏逻辑的耦合失败，纯几何校验查不出来。对策是在场景图里显式标注可达性边，程序化模块据此保证门洞与通道连通，组合层禁止在可达路径的关键宽度内放置大体积物件。

具体例子：程序化地形生成了一条穿过村庄的主路，LLM 细节图在路中央放了一个集市摊位槽位。若组合层不检查通道宽度，摊位会把主路堵死，玩家无法穿越。正确做法是槽位携带“允许占用通道”的布尔标记，默认禁止，只有明确的路障类物件才允许。

六 · 调参顺序与失败定位

推荐的调参顺序是自底向上：先让程序化模块单独产出合法地形与建筑骨架，用固定种子跑通并可视化；再接入组合层，用占位几何（简单立方体）替代扩散资产，验证槽位落位、碰撞与可达性；最后接入扩散段，逐桶替换占位几何，观察显存、吞吐与资产合格率。这个顺序把“几何合法性”与“外观质量”解耦，任何失败都能定位到具体层。

失败定位依赖日志字段。每个槽位应记录：场景图来源、程序化骨架参数、扩散采样配置、组合层落位结果与失败原因、最终资产校验结果。当出现穿模时，先看是骨架错（程序化层）还是落位错（组合层）还是资产包围盒错（扩散层）。三类原因对应三种修复，混在一起调参只会来回震荡。

调参的另一个原则是先定预算再定质量。扩散段的采样步数与分辨率直接决定单物体成本，而槽位数量由布局决定；若不先约束槽位总数与分辨率档位，调参会在“加质量”和“减显存”之间无解。工程判断是：把远景槽位固定为代理几何，把预算集中到玩家可达半径内的少量槽位，质量提升的边际收益最高。

系统复杂度带来的隐性代价是回归困难：改动 LLM 提示模板会改变场景图分布，进而改变槽位数量与尺寸分布，最终影响显存峰值与组合层冲突率。因此每次改动都要跑一遍端到端固定种子用例，记录槽位数、峰值显存、冲突率与导出成功率四个指标，而不是只看单物体生成图。缺标准的评测现状让这件事更难，团队只能自建这套指标作为内部回归基线。

最后一个具体机制落在调度器的准入控制上：扩散任务提交前检查当前显存水位与资产队列长度，超过阈值则降档或暂停；组合循环消费后释放资产并回写水位。这个反馈环让流水线在有限资源下稳定运行，而不是靠人工盯着 OOM 调批次。
