一 · 管线拓扑与端到端复杂度账本

把这条管线当成一条数据流水线来看，它的拓扑是严格分段的：抓取 → 许可过滤 → 格式统一（转 GLB）→ 去重与质量筛 → 多视图渲染 → CLIP 嵌入与标注 → 发布。每一段都是一次全量扫描，中间产物落盘，段与段之间用清单文件（manifest）解耦。这个设计的直接后果是：端到端成本不是各段成本之和的简单相加，而是被最慢的一段和 I/O 带宽共同支配。设原始抓取量为 N₀，各段的留存率为 r₁…r₆（许可过滤、格式转换成功、去重、质量筛、渲染成功、标注成功），则最终数据集规模为

$$N=\prod_{k=1}^{6} r_k \cdot N_0$$

工程上真正要盯的是每一级的绝对吞吐而不是留存率。抓取段是网络密集型，受目标站点限速与并发连接数约束；转 GLB 段是 CPU 密集型，单模型耗时随网格面数与材质贴图数量线性增长；渲染段是 GPU 密集型，成本与视图数成正比；CLIP 段是 GPU 推理密集型，成本与视图数乘以批大小相关。四类资源互不重叠，意味着如果串行执行，任何时刻只有一类硬件在忙，其余三类闲置。因此实现上必须把段与段做成可独立扩缩的作业队列，让抓取、转换、渲染、嵌入四类 worker 各自按队列深度弹性伸缩。代价是中间存储膨胀：一个原始模型加上它的 GLB、多视图 PNG、嵌入向量，落盘体积是原始资产的数倍，千万级规模下中间存储会成为比算力更早触顶的资源。

一个具体的失败模式是清单漂移：如果某段 worker 在写 manifest 之前崩溃，重跑时该段会重复处理同一批资产，而上游段已经推进，导致同一资产在不同段被处理两次、版本不一致。解决办法是每段输出带内容哈希的不可变清单，下游只读上游清单的某个快照，重跑时以清单为幂等边界。这个机制看起来是工程细节，实际上决定了整条管线能否在千万级规模上做增量修复——没有它，任何一次局部重跑都会退化成全量重跑。

二 · 去重的算法结构与它的渐近代价

去重是这条管线里唯一一个全局比较的操作，因此也是复杂度最难看的一段。几何去重不能靠文件名或缩略图，因为同一模型在不同平台上会被改名、重导出、缩放。可行的做法是把网格归一化后提取一个对刚体变换与均匀缩放不变的特征向量，再在特征空间里做近邻搜索。设特征维度为 d，资产数为 N，暴力两两比较是 O(N²d)，在千万级上不可行。工程实现走的是分桶加近邻：先用粗粒度哈希（例如基于面数区间、包围盒长宽比量化、材质数量的组合键）把资产分到桶里，桶内再做精确的近邻检索。

$$h(M)=\big(\lfloor \log_2 F \rfloor,\ \lfloor 8\cdot \tfrac{a}{b} \rfloor,\ \lfloor 8\cdot \tfrac{c}{b} \rfloor,\ m\big)$$

其中 F 是面数，a,b,c 是归一化包围盒的三边长（按降序），m 是材质槽数量。桶内用余弦距离或欧氏距离做阈值判定，阈值取多少直接决定误杀率与漏杀率的平衡：阈值偏松会把不同资产判为重复，造成数据集多样性损失；阈值偏紧会放过重导出副本，造成训练集泄漏——同一模型的多视图同时进入训练集与验证集，评估指标虚高。这是这条管线最隐蔽的失败模式，因为它在数据统计上看不出来，只在模型评估时表现为验证损失异常低。

系统代价方面，去重段的显存需求很低但内存需求高：桶内近邻检索需要把整个桶的特征矩阵驻留内存，如果某个粗哈希桶因为量化过粗而聚集了过多资产，单桶内存会爆。工程上的对策是对桶做二级拆分，或者在桶过大时退化为流式分块检索，用召回率换内存。伪代码思路如下：对每个资产计算归一化特征并写入按哈希分片的临时文件；按分片加载特征矩阵，构建近邻索引；对每个资产查询最近邻，若距离低于阈值则标记为副本并记录指向保留资产的指针；最后按指针做一次并查集归并，输出去重后的清单。并查集这一步不能省，因为副本关系可能传递（A 与 B 近、B 与 C 近但 A 与 C 不近），只做单轮标记会留下链式重复。

三 · 渲染段的显存与批处理调参顺序

多视图渲染是整条管线里唯一必须真正把资产加载进 GPU 的段，因此显存是硬约束。单个资产的显存占用由三部分构成：顶点与索引缓冲、纹理（按分辨率与通道数计）、以及渲染目标（多视图的帧缓冲）。设视图数为 V，单视图分辨率为 R×R，则渲染目标的显存下界是

$$S_{\text{target}} \ge V \cdot R^2 \cdot C \cdot b$$

其中 C 是通道数，b 是每通道字节数。纹理往往是真正的瓶颈：高分辨率 PBR 材质的单模型纹理占用可以轻易超过几何缓冲一个数量级，而长尾资产里存在极端分辨率的贴图，直接把单模型显存推到卡容量之上。工程上的机制是渲染前做纹理降采样预检：读 GLB 的纹理元数据，若单模型纹理总字节超过阈值，则先离线降采样到目标分辨率再进渲染队列。这个预检必须放在渲染段之前而不是之中，因为渲染 worker 里做降采样会让显存峰值不可预测，批处理调度失效。

调参顺序在这里有明确的依赖关系，不能乱序。第一步定视图数与分辨率，因为它们同时决定渲染目标显存和 CLIP 段的输入规模；第二步定单卡并发模型数（batch size），由预检后的最大单模型显存反推；第三步定 worker 数与队列深度，由 GPU 利用率与落盘带宽共同决定；第四步才是调渲染采样数等质量参数。反过来先调质量参数再定批大小，会导致显存预算被质量参数吃掉，批大小被迫降到 1，GPU 利用率塌陷。一个具体例子：同一批资产里既有几十万面的低模也有数百万面的扫描件，若按统一批大小调度，批大小会被最重的模型拖到极小；正确做法是按面数分档排队，轻档大批、重档小批，让显存利用率在时间上更平滑。

失败模式是渲染超时与静默丢帧。某些资产的材质引用了外部未打包的纹理，转 GLB 时未被内嵌，渲染时贴图缺失但不会报错，输出的是灰模多视图。这类样本进入 CLIP 标注后会得到与真实外观不符的嵌入，污染训练集。对策是在渲染段加一道纹理完整性校验，把缺失纹理的资产打回格式统一段重转，而不是让它们带着错误外观流下去。

四 · CLIP 嵌入段的吞吐、批与通信

CLIP 段把多视图图像映射为语义嵌入，是整条管线的语义瓶颈。它的计算量是 N·V 次前向，且每次前向的算力需求与图像分辨率、视觉塔规模相关。吞吐优化的核心是把 N·V 张图当成一个扁平的图像流来批处理，而不是按资产逐个处理——按资产处理会让批大小被单资产的视图数锁死，GPU 利用率低。扁平化之后，批大小只受显存与图像分辨率约束，调度自由度大幅提升。

$$\text{throughput} \approx \frac{B \cdot V}{t_{\text{forward}}(B) + t_{\text{io}}}$$

分母里的 t_{\text{io}} 常被低估：千万级资产乘以视图数，图像总量是海量小文件，随机读的 IOPS 会成为实际瓶颈，而不是 GPU 算力。工程机制是把多视图打成固定大小的分片包（例如每包若干资产的全部视图），顺序读取代随机读，代价是单包内资产的处理必须整包完成才能推进，包越大尾延迟越明显。调参上，包大小与批大小要联合调：包太小则 IOPS 压力回升，包太大则显存峰值与尾延迟上升。

多卡场景下的通信量很小，因为 CLIP 推理是纯前向、无梯度、无跨卡依赖，每张卡独立处理自己的分片，只需在最后把嵌入向量按资产 ID 归并写回。真正的通信代价在归并阶段：嵌入向量维度固定，总量与资产数成正比，写回是顺序写，压力在存储而不在网络。失败模式是视图级标注与资产级标注的错位：CLIP 对每张视图给出嵌入，但数据集条目是资产级的 ℓᵢ，需要把多视图嵌入聚合为单一标签。聚合方式（取首视图、取均值、取与类别原型最近者）会显著改变标签分布，若聚合逻辑在重跑时变更而未版本化，同一资产在不同批次会得到不同标签，造成数据集内部不一致。对策是把聚合规则连同其参数写进 manifest 的元数据，使标签可复现。

五 · 工程坑的排序与调参的依赖图

把这条管线落地时，坑的严重程度不是按出现频率排，而是按“是否静默污染数据”排。第一类是静默污染：去重阈值不当造成的训练集泄漏、纹理缺失造成的灰模嵌入、许可过滤漏判造成的不可商用资产混入。这三类都不会让管线报错，只会让下游模型指标失真或带来法律风险，因此必须在管线里做成硬校验而非软告警。第二类是资源触顶：中间存储膨胀、单桶内存爆、随机读 IOPS 瓶颈。第三类是吞吐塌陷：批大小被最重资产拖死、段间串行导致硬件闲置。调参顺序应当由第一类倒推：先定去重阈值与许可规则这些影响数据正确性的参数，再定渲染与嵌入的资源参数，最后才调吞吐参数。

许可过滤这一段值得单独说机制。公开平台上的 CC 许可有多个变体，允许商用与要求署名、禁止演绎的条款混杂，且许可信息以平台元数据字段形式存在，字段缺失或填写不规范的情况普遍。工程实现不能只做字符串匹配，而要把许可字段解析为结构化枚举，再按目标用途（可商用、可再分发、允许衍生）做布尔判定，判定结果连同原始许可字符串一起写入 manifest。失败模式是把“未标注许可”误当作“允许”，这在规模化抓取里是系统性风险，因为缺失字段的比例会随抓取范围扩大而上升。正确做法是把未知许可默认判为不可用，宁可损失召回也不引入法律风险。

最后是增量与重跑的设计判断。千万级管线的现实是它不会一次跑完就冻结，上游会持续有新资产进入，下游会持续有规则修订。因此每一段都必须以清单快照为输入、以新清单为输出，段内处理对资产 ID 幂等。这样规则修订只需重跑受影响的下游段，而不必回到抓取。这个机制的直接代价是 manifest 数量随重跑次数增长，需要定期做清单压实（把多次增量合并为一次全量快照），压实本身是一次全量扫描，要安排在低峰期并预留存储余量。工程判断上，如果某一类规则修订的频率高于清单压实的频率，说明规则还没稳定，此时不应把管线推进到全量发布，而应先在子集上验证规则再扩大。
