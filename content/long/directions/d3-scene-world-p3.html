一 · 从 Text2Room 到 WonderWorld：表示替换而非功能叠加

Text2Room 与 WonderWorld 常被并列为「单图/文本生成场景」的代表，但二者之间不是功能叠加关系，而是一次表示层的替换。Text2Room 的核心机制是迭代式场景网格补全：从一个已知视角出发，渲染当前网格得到深度与颜色缓冲，定位尚未观测到的区域，用 2D 修补模型（inpainting）生成新视角图像，再反投影为三角网格并融合进全局网格。它的状态是显式网格加纹理，每一步都在已有几何上「补洞」。WonderWorld 则把场景状态换成高斯泼溅：每个高斯携带位置、协方差、不透明度与球谐颜色系数，新视角的生成不是补网格洞，而是在未覆盖区域生长新的高斯集合，并用深度与语义一致性约束其落位。

这个替换带来的第一个后果是几何一致性的来源变了。Text2Room 的一致性依赖网格融合时的深度校验与视角重叠；WonderWorld 的一致性依赖高斯生长的边界约束与多视角光度一致。前者在长距离漫游中会因融合误差累积出现网格缝隙与纹理拉伸，后者会因高斯数量随视角扩张而线性增长，显存成为硬约束。用公式描述高斯生长的代价更直观：若每次外扩新增 N 个高斯，每个高斯存储 d 维属性（位置 3、协方差 6、不透明度 1、球谐系数按阶数展开），则总显存约为

$$M \approx \sum_{k=1}^{K} N_k \cdot d \cdot b$$

其中 K 为外扩轮数，b 为每属性字节数。这条式子说明：漫游距离越远，显存压力不是常数而是随轮数累加，工程上必须在「生长新高斯」与「剪枝低不透明度高斯」之间做取舍。一个具体例子是：在单图输入下向房间外走廊连续外扩数轮后，靠近原始视角的高斯密度远高于远端，若不剪枝，远端视角的渲染会出现稀疏空洞，而剪枝过激又会破坏近端细节——这是表示替换后新出现的失败模式，Text2Room 的网格融合阶段并不存在对应问题。

继承关系也清晰：两者共享「以当前渲染结果为条件、逐步向外生成」的迭代骨架，差异在于条件信号如何落到几何载体上。Text2Room 把 2D 修补结果经深度反投影落到网格；WonderWorld 把 2D 结果经深度与语义约束落到高斯参数。因此读这两篇论文时应关注同一控制流下不同的状态更新算子，而不是把它们当作两条互不相干的路线。

二 · WorldGen：把「可漫游」从渲染问题变成结构问题

WorldGen 的断裂点在于它不再以「视角外扩」为唯一生成驱动，而是直接产出可穿越的地形与世界结构。文本到可穿越世界的关键机制是：先生成具有高度场与可行走区域的世界布局，再在其上放置植被、建筑与路径，最后用程序化或生成式手段填充细节。这使得「能走进去」不再依赖渲染器是否覆盖了某个视角，而依赖世界结构本身是否连通、坡度是否可通行、边界是否闭合。

与 Text2Room、WonderWorld 相比，WorldGen 的继承在于同样以文本为条件、同样追求几何一致；断裂在于它把一致性判据从「多视角光度一致」换成「拓扑与通行性一致」。一个具体机制是通行性判定：对高度场做梯度分析，把坡度超过阈值的格子标记为不可通行，再用连通性检查确保起点与目标区域之间存在路径。伪代码思路可写成：生成高度场 → 计算坡度图 → 阈值化得到通行掩码 → 对掩码做连通分量标记 → 若起点与终点不在同一分量则回退修改布局。这个回路在 Text2Room 中不存在，因为后者根本没有「通行」这一概念，只有「是否被观测到」。

代价随之转移。WorldGen 的失败模式主要不是渲染空洞，而是结构层面的不连通与尺度失真：文本描述「穿过森林到达山顶」时，若高度场生成的山体坡度过陡，通行掩码会把整条路径切断，此时需要回退重生成布局，而回退成本远高于单次视角修补。系统代价体现在生成轮次上：布局生成、通行性校验、细节填充是串行阶段，任一阶段失败都要重跑前序阶段，这与 WonderWorld 的增量式外扩在成本结构上完全不同——后者失败只影响局部高斯，前者失败影响全局布局。

另一个继承线索是 LLM 的角色。WorldGen 用语言模型解析文本中的空间关系与物体清单，这与 SceneCraft 用 LLM 生成 Blender 代码在「把语言结构转成可执行结构」上是同一条思路，但落点不同：SceneCraft 落到脚本化的场景图与材质，WorldGen 落到地形与通行结构。读这两篇时应把 LLM 视为「结构编译器」而非「像素生成器」，这是 2024–2025 年间场景生成在控制流上的共同转向。

三 · SceneCraft：程序化表示作为一致性锚点

SceneCraft 的位置在论文链条中很特殊：它不直接生成像素或高斯，而是让 LLM 智能体合成 Blender 代码，由渲染器执行代码得到场景。其机制是「语言 → 脚本 → 场景图」的三段式：LLM 根据文本拆解物体、空间关系与材质，写出可执行的 Blender Python 脚本，脚本运行后得到带变换矩阵与材质参数的场景。一致性锚点因此从「生成模型的隐空间」转移到「脚本的显式参数」——物体的位置、旋转、缩放都是代码里的数值，可被检查、可被修改。

这与 Text2Room 的迭代补全形成互补而非替代：Text2Room 擅长从单图扩展出连续的房间几何，但对「房间里应该有什么、摆在哪里」缺乏显式控制；SceneCraft 擅长显式布局与材质，但从零生成大尺度连续几何并非其目标。继承关系体现在两者都把「几何」与「外观」分离处理：Text2Room 用网格承载几何、用纹理承载外观；SceneCraft 用变换矩阵承载几何、用材质节点承载外观。断裂在于控制粒度：前者是像素级修补，后者是参数级编辑。

系统代价是执行链路的脆弱性。LLM 生成的代码可能出现 API 误用、坐标单位不一致、物体相互穿插等问题，且错误往往在渲染后才暴露，调试回路长。一个具体失败模式是：文本要求「桌上放一盏灯」，脚本把灯的变换矩阵设在桌面高度之下，渲染结果中灯被桌子遮挡，而脚本本身语法正确——这类错误无法靠语法检查捕获，只能靠渲染后的视觉校验或几何相交检测回退。伪代码思路是：生成脚本 → 沙箱执行 → 渲染多视角 → 用视觉语言模型核对文本与图像的一致性 → 不一致则带错误信息重新生成脚本。这个回路每轮都要跑完整渲染，成本高于纯文本重写。

在年代脉络上，SceneCraft 代表了「程序化表示回归」的一支：当端到端生成模型在长距离一致性上反复失败时，把场景压回可解释的参数空间是一种工程上的退守，但换来了可编辑性与可验证性。它与 WorldGen 的结构化思路同源，区别在于 SceneCraft 的结构是物体级场景图，WorldGen 的结构是地形级通行场。

四 · PhysDreamer：物理属性作为生成目标的后补层

PhysDreamer 补上的是链条中此前缺失的一环：生成物体不仅要有几何与外观，还要有可交互的物理属性。其机制是视频驱动的物理参数估计：用视频生成模型合成物体在外力作用下的形变序列，再通过可微物理仿真反推材质参数（如杨氏模量、泊松比），使仿真结果与生成视频的运动一致。目标函数可写成仿真轨迹与生成视频轨迹之间的差异最小化：

$$\theta^{*} = \arg\min_{\theta} \sum_{t} \left\| \mathcal{S}(x_0, f_t; \theta) - \hat{x}_t \right\|^2$$

其中 \theta 为待估物理参数，\mathcal{S} 为仿真器，f_t 为外力序列，\hat{x}_t 为视频生成的第 t 帧形变。这条式子揭示了继承与断裂：继承的是「用生成模型提供监督信号」这一范式，Text2Room 用 2D 修补提供几何监督，PhysDreamer 用视频生成提供运动监督；断裂在于监督对象从「静态几何」变成「动态响应」，因此需要可微仿真器进入回路。

系统代价在于仿真回路的计算量与参数可辨识性。可微仿真需要在前向仿真后反向传播梯度，每轮优化都要跑完整时间步序列，成本随帧数与网格分辨率上升。失败模式是参数不可辨识：若视频中的形变幅度很小，多组材质参数都能拟合出相近轨迹，反推结果对初始猜测敏感，交互时表现为「看起来软但碰撞响应僵硬」。一个具体例子是：对同一物体分别用小幅挤压与大幅拉伸的视频做估计，前者得到的参数在强外力下会失真，说明监督信号的激励幅度直接决定参数可信区间。

在论文链条上，PhysDreamer 不与 Text2Room、WonderWorld 争夺场景生成的主导权，而是作为后处理层挂在已有资产生成之后：先用场景或物体生成拿到几何与外观，再用 PhysDreamer 赋物理属性。这决定了它的工程位置——它不是替代关系，而是补全关系，且补全的代价是引入仿真器与视频生成两个额外系统，链路长度显著增加。

五 · 年代脉络中的断裂与延续

把五篇论文按控制流排开，可以看到两条并行的延续线。第一条是「迭代外扩」线：Text2Room 用网格补全外扩，WonderWorld 用高斯生长外扩，二者共享「以当前渲染为条件、逐步扩展」的骨架，断裂只在状态表示。第二条是「结构先行」线：WorldGen 先定地形与通行结构，SceneCraft 先定场景图与脚本，二者共享「先结构后细节」的顺序，断裂只在结构粒度。PhysDreamer 不在这两条线上，它挂在两条线的输出之后，作为物理属性的补全层。

论文状态表示一致性判据主要失败模式
Text2Room显式网格+纹理深度校验与视角重叠融合误差累积、缝隙与拉伸
WonderWorld高斯泼溅集合深度与语义约束下的生长高斯数量膨胀、显存受限
WorldGen高度场与通行结构拓扑连通与坡度阈值布局不连通、需全局回退
SceneCraftBlender 脚本与场景图参数显式可查代码语义错误、渲染后才暴露
PhysDreamer几何+材质参数仿真轨迹与视频一致参数不可辨识、激励不足

这张表的意义在于：一致性判据的每一次更换，都对应一次失败模式的转移，而不是失败模式的消失。Text2Room 解决了「单图无法生成连续房间」的问题，代价是融合误差；WonderWorld 解决了「网格融合在长距离漫游中崩坏」的问题，代价是显存；WorldGen 解决了「漫游依赖渲染覆盖」的问题，代价是布局回退成本；SceneCraft 解决了「布局不可控」的问题，代价是执行链路脆弱；PhysDreamer 解决了「有几何无物理」的问题，代价是仿真回路与参数可辨识性。读论文时按这条「问题—判据—代价」的转移链去读，比按功能清单去读更能看清继承与替代的真实边界。

近年 2024–2025 的走向是从「静态房间」走向「可交互世界」：WonderWorld 支持实时漫游与场景外扩，WorldGen 生成可穿越地形，PhysDreamer 补上物理属性。这条走向在论文链条上的体现是控制流变长——从单次生成变成「布局→细节→物理」的多阶段串联，每一阶段的输出都是下一阶段的输入，任一阶段的失败都会向下游传播。评测仍缺统一标准，这意味着上述失败模式目前只能靠各自论文的定性描述与局部演示来判断，跨论文比较缺乏共同度量。

工程判断落在具体机制上：选择哪条链条，取决于你要的是「连续房间的视觉漫游」还是「可通行世界的结构正确」。前者应沿迭代外扩线选表示（网格或高斯），并把预算放在融合校验或高斯剪枝上；后者应沿结构先行线选粒度（地形场或场景图），并把预算放在通行性校验或脚本渲染校验上。物理属性作为后补层，只有在几何与外观已经稳定后才值得引入，否则仿真回路会把上游的几何误差放大成不可辨识的参数估计——这是链条串联带来的具体代价，也是读这五篇论文时最应带走的工程结论。
