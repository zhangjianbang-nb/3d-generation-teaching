一 · 路线分野：把「场景」拆成可交付的四件事

讨论路线对比之前，先要把「生成一个场景」这个目标拆成可分别验收的交付物，否则不同论文之间的比较会退化成「谁的 demo 更炫」。从工程交付角度看，一个可漫游、可交互的场景至少包含四件彼此耦合的东西：几何（可被相机穿越而不穿帮的网格或辐射场）、外观（与几何对齐的纹理或高斯属性）、空间范围（相机能走多远、边界之外是什么）、物理（物体在被推、被拉、被压时的响应）。Text2Room、WonderWorld、WorldGen、SceneCraft、PhysDreamer 这五条路线，本质上是在这四个交付物上做了不同的取舍：有的把几何与外观绑死在一起换取一致性，有的放弃显式几何换取实时性，有的干脆把「场景」降维成一段可执行的程序，还有的只解决物理这一件事而把几何当作已给定的输入。

把交付物拆开之后，一个关键判断浮现出来：几何一致性与实时可漫游性在当前的表示下是互相拉扯的。显式网格（mesh）天然支持碰撞检测、物理仿真、传统渲染管线，但它的生成过程是串行的、逐步扩增的，误差会沿扩增路径累积；辐射场类表示（高斯泼溅）天然支持实时新视角合成与场景外扩，但它的「几何」是概率性的、没有封闭表面，碰撞与物理仿真需要额外的代理几何。这条拉扯线是理解全部路线差异的主轴。

下面用一个统一的抽象来描述所有路线的工作方式：把场景生成视为一个状态序列 $S_0 \to S_1 \to \dots \to S_n$，每一步由一个「扩展算子」$E$ 和一个「观测算子」$O$ 组成。$E$ 决定新区域如何被创造出来（补全、外扩、程序化放置），$O$ 决定已有区域如何被约束住不漂移（重投影、深度对齐、几何正则）。不同路线的差别，几乎全部落在 $E$ 与 $O$ 的具体形式上，以及 $O$ 是否足够强到能压住 $E$ 引入的误差。

$$S_{k+1} = O\big(E(S_k,\ c_k),\ S_k\big),\quad c_k \sim p(\cdot \mid \text{text or image})$$

其中 $c_k$ 是第 $k$ 步的条件信号（文本提示、单图、或上一步渲染出的视图）。这个式子的工程含义是：只要 $O$ 不是恒等映射，它就必然引入计算代价；只要 $E$ 不是确定性的，它就必然引入随机性。路线选型的第一问因此变成——你的应用能容忍多大的 $O$ 代价，以及你能接受多强的 $E$ 随机性。

二 · 迭代式网格补全：Text2Room 的串行扩增与误差累积

Text2Room 的路线是把 2D 文本到图像模型当作「纹理与几何的联合先验」，用一个迭代式的场景网格补全循环把房间一点点长出来。具体机制是：从当前已生成的网格出发，选择一个尚未观测的区域（通常是当前视角的边缘或一个预设的相机轨迹下一站），渲染出该区域的深度与部分颜色，把渲染结果连同文本提示送入 2D 修补（inpainting）模型，得到一张完整的、带新内容的视图；再从这张视图反推深度，把新几何缝合进已有网格，并把新纹理投影回网格表面。循环往复，直到相机轨迹走完。

这条路线最值得学习的是它的「观测算子」设计：每一次缝合之后，都会把已有网格重新投影到新视角下，与修补结果做一致性比对，用深度对齐与颜色一致性把漂移压回去。伪代码层面的思路大致是：

  • 初始化：由文本生成首帧视图，单目深度估计得到初始网格 $S_0$；
  • 循环：沿预设轨迹取下一相机位姿，渲染 $S_k$ 得到部分观测；
  • 修补：以部分观测为条件、以文本为语义约束，生成完整视图 $I_{k+1}$；
  • 反投影：由 $I_{k+1}$ 估计深度，三角化得到新面片，与 $S_k$ 在重叠区做深度与颜色的最小二乘对齐；
  • 缝合：把对齐后的新面片并入网格，更新纹理图集。

它的系统代价非常具体：串行。每一步都要跑一次 2D 扩散修补加一次单目深度估计，步数与轨迹长度成正比，生成一个完整房间的时间是分钟级的，而且不可并行——因为第 $k+1$ 步依赖第 $k$ 步的网格状态。更麻烦的是失败模式：误差沿轨迹累积。单目深度的尺度歧义在每一步都会引入一点尺度漂移，重叠区的对齐只能压住局部，压不住全局；走到轨迹末端时，早期生成的墙面与晚期生成的墙面在接缝处会出现几何错位与纹理拉伸。这是「串行扩增 + 局部对齐」这一组合的结构性缺陷，不是调参能解决的。

一个具体的例子：让模型生成一个带走廊的房间，相机从房间中心出发向走廊推进。前几步生成的墙面纹理清晰、几何平整；走到走廊尽头回头时，入口处的门框往往已经与最初生成的墙体错开，纹理在接缝处被拉成条状。这个现象在工程上意味着：Text2Room 类路线适合「短轨迹、单房间、以观赏为主」的场景，不适合需要长距离往返漫游的环境。

三 · 高斯泼溅场景扩展：WonderWorld 的实时性与几何代价

WonderWorld 走的是另一条路：用高斯泼溅（Gaussian Splatting）作为场景表示，从单张图像出发，支持实时漫游与场景外扩。它的核心机制是把场景表示为一批带位置、协方差、颜色与不透明度的三维高斯椭球，渲染时把这些椭球投影到屏幕并做 alpha 混合。生成过程是：由单图估计初始高斯集合与深度，当相机移动到尚未覆盖的区域时，用 2D 生成模型补出新视图，再把新视图反投影成新的高斯，并入现有集合。

这条路线最大的工程优势是实时性。高斯泼溅的渲染是光栅化式的、可并行的，单帧渲染代价与高斯数量近似线性，因此在消费级 GPU 上可以做到交互帧率。这让「可漫游」从一句口号变成了可交付的体验：用户可以真的按住方向键在场景里走，而不是等一段预渲染视频。它的扩展算子 $E$ 也比网格补全轻——不需要三角化与缝合，只需把新视图的像素反投影成高斯并做属性融合。

但代价同样明确。第一，几何是概率性的：高斯集合没有封闭表面，深度是「期望深度」而非「表面深度」，因此碰撞检测、物理仿真、遮挡关系都需要额外的代理几何或启发式。第二，场景外扩时的几何一致性依赖新视图与已有高斯的对齐，而这个对齐是在二维图像空间做的，缺乏三维约束，长距离外扩后会出现「同一面墙在不同视角下厚度不一致」的现象。第三，显存随高斯数量增长，一个稍大的场景就是数百万级高斯，显存占用与渲染带宽成为规模上限。

$$\mathcal{L}_{\text{align}} = \sum_{p\in\Omega}\big\|D_{\text{new}}(p) - D_{\text{exist}}(p)\big\|^2 + \lambda\sum_{p\in\Omega}\big\|C_{\text{new}}(p) - C_{\text{exist}}(p)\big\|^2$$

上式是外扩时常用的重叠区对齐损失：在重叠像素集合 $\Omega$ 上同时约束深度 $D$ 与颜色 $C$。它的局限在于 $\Omega$ 只覆盖当前视角可见的部分，被遮挡区域没有任何约束，误差会藏进不可见区，等相机绕过去时才暴露。一个具体例子：从一张客厅单图出发向沙发背后外扩，正面视角下一切正常；当相机绕到沙发背后，原本被遮挡的墙面高斯往往出现空洞或颜色突变，因为那部分从未被任何视角约束过。工程判断是：WonderWorld 类路线适合「以第一视角漫游、观赏为主、物理交互弱」的场景，实时性是它不可替代的优势，但不要指望它直接产出可做刚体仿真的几何。

四 · 文本到可穿越世界：WorldGen 与 SceneCraft 的两种「程序化」

WorldGen 与 SceneCraft 代表了两条更激进的路线：不再把场景当作「逐步长出来的资产」，而是当作「一次成型的结构」。WorldGen 的目标是直接从文本生成可穿越、可交互的三维世界，它的机制偏向于先生成宏观的空间布局（地形、路径、区域划分），再在布局约束下填充局部内容，使得「可穿越」成为一等公民——相机路径、通行区域、碰撞边界在生成阶段就被考虑进去，而不是事后补。SceneCraft 则把场景降维成 Blender 代码：用一个 LLM 智能体把文本描述翻译成一段可执行的 Blender 脚本，通过程序化地放置、变换、组合资产来构造场景。

SceneCraft 这条路线的方法论价值在于「把生成问题转成程序合成问题」。它的机制是：LLM 智能体先做场景分解（把文本拆成物体清单与空间关系），再检索或调用资产库取得具体模型，然后生成 Blender Python 代码来实例化、摆放、设置材质与灯光，最后渲染出图并做视觉反馈，若不满足描述则迭代修改代码。伪代码思路是「分解—检索—合成—渲染—反思」的循环。它的优势是结构可控：空间关系是显式写死的，不会出现网格补全路线那种接缝错位；场景可编辑，改一行代码就能挪一个物体；资产是真实的、带封闭表面的，天然支持物理与碰撞。

代价在于「资产依赖」与「语义鸿沟」。程序化路线无法凭空创造资产库里没有的东西，遇到文本里的新奇物体只能退化为近似或失败；LLM 生成代码的可靠性是另一层风险，空间关系描述里的「在……左边」「靠着墙」这类模糊约束，翻译成坐标时容易出错，而错误是离散的、不可微的，无法用梯度修正。WorldGen 的代价则是宏观布局与局部细节的耦合：布局一旦定错，局部填充再精细也救不回来；而布局生成本身缺乏强监督，长距离的地形一致性依赖生成模型的空间推理能力。

路线扩展算子 E观测算子 O几何类型主要代价
Text2Room2D 修补 + 单目深度重投影深度/颜色对齐显式网格串行、误差累积
WonderWorld新视图反投影为高斯重叠区二维对齐高斯泼溅几何概率性、显存
WorldGen布局生成 + 局部填充通行/碰撞约束混合布局错误不可逆
SceneCraftLLM 合成 Blender 代码渲染反馈 + 代码反思显式资产资产依赖、语义鸿沟

一个具体例子：文本要求「一间有落地窗的卧室，窗外是海」。SceneCraft 类路线会去资产库找窗、床、地板，用代码把窗放在墙上、把海做成背景板或天空盒；如果资产库没有「落地窗」，它只能用一个普通窗近似，语义就打折了。WorldGen 类路线则会把「窗外是海」纳入宏观布局，先定出室内与室外的边界，再填充，代价是室内细节的精度往往不如程序化路线。

五 · 物理属性补全：PhysDreamer 的「视频即物理先验」

PhysDreamer 解决的是另一件事：给定一个已生成的、带外观的三维物体，如何让它具备可交互的物理属性（弹性、阻尼、质量分布等），使得用户推它、拉它时响应是真实的。它的机制是把视频生成模型当作物理先验：对一个候选物理参数组，用可微物理仿真在给定外力下算出物体的形变序列，渲染成视频，再与视频生成模型在相同文本/图像条件下的「想象响应」比对，用这个比对误差反传去优化物理参数。

$$\theta^{*} = \arg\min_{\theta}\ \big\| \mathcal{R}\big(\text{Sim}(G,\theta,f)\big) - V_{\text{gen}}(\text{cond}) \big\|^2$$

其中 $G$ 是物体几何，$\theta$ 是待估物理参数，$f$ 是外力，$\text{Sim}$ 是可微仿真器，$\mathcal{R}$ 是渲染，$V_{\text{gen}}$ 是视频生成模型的输出。这条路线的方法论意义在于：它把「物理参数估计」从「手工标注材质」变成了「用生成模型的视觉先验做监督」，绕开了真实物理测量。代价有三层。第一，视频生成模型的「物理直觉」未必正确，它可能生成视觉上合理但动力学上矛盾的响应，优化会把错误先验固化进参数。第二，可微仿真本身的计算代价高，参数优化需要多轮前向与反传，单物体的参数拟合是分钟到小时级。第三，泛化性受限于视频模型见过的材质分布，对罕见材质（比如某种编织物）的估计缺乏约束。

一个具体例子：让 PhysDreamer 处理一个生成的花瓶，外力设为侧向轻推。若视频生成模型对「陶瓷」的想象是刚性晃动，优化出的参数会偏向高刚度；但真实陶瓷在被轻推时几乎不动、在被重击时碎裂，这种「阈值型」响应是连续参数模型难以表达的。工程判断是：PhysDreamer 类路线适合「软体、弹性、有明显视觉形变」的物体，对「脆性、断裂、多体接触」这类离散事件，当前参数化方式覆盖不到。

六 · 选型判据：按交付物反推路线

把五条路线放在一起，选型不该问「哪条最先进」，而该问「我的交付物里哪一件是不可妥协的」。下面给出一组可操作的判据，每条都对应一个具体的工程约束。

  • 若交付物要求实时交互漫游（帧率是硬指标），高斯泼溅路线是唯一能同时满足实时渲染与场景外扩的选择，代价是必须接受概率性几何，并为物理与碰撞单独准备代理。
  • 若交付物要求可做刚体/软体仿真、需要封闭表面与碰撞网格，显式网格或程序化资产路线是前提；此时实时性让位于几何确定性，Text2Room 类串行补全适合短轨迹，SceneCraft 类程序化适合结构明确的室内场景。
  • 若交付物要求长距离往返漫游且几何不能漂移，串行扩增路线的误差累积是结构性障碍，应优先考虑「先布局后填充」的 WorldGen 类路线，或程序化路线，用显式空间约束替代局部对齐。
  • 若交付物要求物理响应的真实性，PhysDreamer 类参数估计是必要组件，但它只解决「已有物体的物理属性」，不解决几何与外观，必须与前述某条几何路线串联。
  • 若交付物要求可编辑性（改布局、换物体、调材质），程序化路线天然胜出，因为场景是一段可读可改的代码而非一堆不可解释的网格或高斯。

还有一个跨路线的工程判断：评测缺失使得选型不能只看论文指标。当前没有统一的场景级评测标准，几何一致性、可漫游性、物理真实性各自有各自的局部指标，但没有任何一个指标能同时覆盖「走进去不穿帮」与「推一下有正确响应」。这意味着选型必须自建验收流程：用固定相机轨迹做往返漫游测几何漂移，用固定外力序列测物理响应，用固定显存预算测规模上限。三条验收线跑下来，路线的真实代价才会暴露，而不是被 demo 视频掩盖。

最后落到一个具体机制上：无论选哪条路线，场景生成的规模上限都由「约束的覆盖密度」决定。高斯泼溅的约束来自已观测视角，网格补全的约束来自重叠区对齐，程序化路线的约束来自显式空间关系，物理路线的约束来自视频先验。约束覆盖不到的区域就是误差的藏身之处，而场景生成的本质困难，正是相机可以走到任何约束稀疏的地方。因此选型的最终判据不是路线的新旧，而是这条路线在你的目标场景里，能否把约束铺到相机可能到达的每一个角落——铺得到，路线成立；铺不到，再实时、再好看也只是演示。
