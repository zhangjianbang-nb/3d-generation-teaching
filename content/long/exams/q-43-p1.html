一 · 三档答案的分层标准：从“答对关键词”到“答出闭环动力学”

这道题在评分上被切成两块：风险占 50%，反馈机制占 50%。三档答案的差别不在于“提到了几个名词”，而在于是否把风险与反馈机制放在同一条因果链上讲清楚。及格档的特征是名词齐、关系散：能说出“LLM 写 bpy 代码”“可能语法错、API 错”“用 GPT-V 看渲染图反馈”，但风险与反馈各自孤立，没有说明为什么反馈必须是“看图”而不是“看代码”，也没有说明为什么“写代码”这件事本身会把空间推理的负担转嫁给一个不擅长空间推理的模型。良好档会补上闭环：写代码—渲染—看图—改代码，并指出渲染结果是模型唯一能“看见”的中间产物，因此 GPT-V 的视觉判断是把不可执行的符号错误转成可执行的自然语言修正建议的枢纽。满分档则进一步给出动力学判断：闭环能纠错，但纠错能力受限于渲染图的信息量与轮数成本，复杂场景下误差不会单调收敛，而会在“改一处、坏一处”的耦合中震荡；同时明确指出“代码精确”与“LLM 对 3D API 与空间推理不稳定”之间的张力——代码要求精确，模型输出的是概率性文本，二者的接口就是那道渲染反馈。

把三档拆成可操作的判分维度，可以用一张表对齐：

维度及格档表现良好档表现满分档表现
风险识别列出语法错、API 错补上空间关系错与死循环指出四类错误同源：概率文本对接精确 API
反馈机制提到 GPT-V 看渲染图讲清“看起来不对→文字反馈→改代码”说明视觉反馈为何不可替代、轮数与成本约束

这张表的作用是防止“名词覆盖式”作答：四个判分点（LLM 写 bpy 代码、GPT-V 看渲染反馈、写-渲-看-改闭环、API/空间推理风险）在及格档里往往只被点名，没有被连成链。评分时，风险 50% 与反馈 50% 是硬切分，任何一档如果只答一半，另一半点数不能靠“闭环”这个词补回来——闭环属于反馈机制那一半，不能拿来充当风险分析的替代品。

二 · 机制解析：为什么“写代码”是风险源，而“看图”是纠错源

SceneCraft 的基本架构是把场景描述交给 LLM，由 LLM 产出 Blender 的 Python 脚本（bpy 代码），在 Blender 里执行并渲染，再把渲染图交给 GPT-V 评估，评估结论以文字形式回灌给 LLM，触发下一轮代码修改。这条链上真正的机制要点是：bpy 是一门精确的命令式接口，每一个函数调用都对应确定的场景图变更；而 LLM 的输出是逐 token 采样的概率文本。二者对接时，错误不是偶发的“手滑”，而是结构性的：模型对 API 名称、参数顺序、单位、坐标系朝向的记忆是统计性的，对“两个物体之间的相对位置”的推理也没有内建的几何约束。于是四类风险各自有明确的生成机制。

语法错来自 Python 层面的 token 级失误，例如括号不匹配、缩进错位、变量未定义；这类错误在渲染前就会抛出异常，属于最容易被发现的一类，但它的存在说明模型并没有在执行前“编译”自己的输出。API 错更深一层：函数名拼错、参数名与版本不匹配、把只读属性当可写属性赋值。这类错误有时不抛异常而是静默失效，例如设置了不存在的属性，Blender 可能忽略它，场景看起来“没报错但也没变化”。空间关系错是最隐蔽的：旋转的欧拉角顺序、局部坐标与全局坐标的混用、物体原点位置，都会让渲染图“看起来不对”却说不出哪一行代码错。死循环则来自循环条件写错或递归无终止，表现为渲染进程挂死，属于系统代价最高的一类失败。

$$\text{Err}_{\text{total}} = \text{Err}_{\text{syntax}} + \text{Err}_{\text{API}} + \text{Err}_{\text{spatial}} + \text{Err}_{\text{loop}}$$

这个加性分解不是严格可加的，因为空间错往往由 API 误用诱发，但它给出了纠错资源的分配依据：语法错与 API 错可以由静态检查或执行异常捕获，成本低；空间错必须靠渲染图才能暴露，成本高；死循环必须靠超时与沙箱隔离，成本体现在算力占用上。SceneCraft 的反馈闭环之所以以“渲染图”为核心，正是因为前三类里最难的那一类——空间关系——没有别的观测通道。代码本身是精确的，但“精确的代码”不等于“正确的场景”，渲染图是唯一把代码语义投影到可视域的算子。

GPT-V 的角色因此不是“另一个评审员”，而是“把视觉异常翻译成文字修正指令”的转导器。它的输入是像素，输出是自然语言，中间没有符号级的调试信息。这意味着反馈的粒度受限于视觉可辨识度：一个偏移几厘米的物体在低分辨率渲染里可能看不出来，一个材质颜色偏差却可能被过度强调。反馈文本回到 LLM 后，模型需要把“看起来不对”映射回具体的 bpy 语句，这一步又是一次概率推理，可能改对，也可能改错位置。闭环的纠错能力就卡在这个“视觉→文字→代码”的两级转导上。

一个具体例子可以说明这条链的脆弱点：让 LLM 生成“桌面上放一个杯子，杯子在桌子左侧”的场景。模型可能写出正确的立方体与圆柱体创建代码，但把杯子的平移量写在了全局坐标里，而桌子的原点不在世界原点，于是渲染图里杯子悬空或穿模。GPT-V 看到“杯子没有放在桌面上”，回灌一句“杯子应接触桌面表面”。LLM 下一轮可能去改杯子的 z 坐标，却仍然用全局坐标，结果只是把悬空高度改小，没有解决原点错位。这就是“改一处、坏一处”的耦合震荡：反馈命中了现象，但没有命中根因，因为视觉反馈不携带坐标系信息。

三 · 数字底账：把“轮数多、成本高”拆成可核算的量

解析里给出的定性判断是“轮数多、成本高，复杂场景仍会失败”。在没有实验数字的前提下，仍然可以把成本结构写成可核算的账本，让评分者看到答者理解“贵在哪里”。账本至少有三栏：每轮渲染的算力开销、每轮 GPT-V 调用的推理开销、以及轮数随场景复杂度增长的趋势。三者相乘构成总成本，而总成本的瓶颈通常不在单轮，而在轮数的尾部——少数难场景会吃掉大部分轮数。

$$C_{\text{total}} = N_{\text{round}} \cdot (C_{\text{render}} + C_{\text{vision}} + C_{\text{llm}})$$

其中 N_round 是闭环轮数，C_render 是单次渲染的 GPU 时间，C_vision 是视觉模型一次前向的成本，C_llm 是代码生成与修改的 token 成本。这个式子解释了两件事。第一，闭环的边际成本是常数级的，但轮数是变量，所以成本对难场景高度敏感。第二，任何减少无效轮数的机制——比如在渲染前做静态语法检查、在提示里固定坐标系约定——都能直接压缩 N_round，这比优化单轮渲染更有效。工程上常见的失败模式是把预算花在“多跑几轮”上，而没有花在“减少需要跑的轮数”上。

死循环是账本里最刺眼的一项：它不增加有效轮数，却持续占用渲染进程与沙箱资源，直到超时被杀死。这类失败在成本上表现为“零产出但全额计费”，在评分上则应被明确归入风险一栏——答者若只提“语法错、API 错”而漏掉死循环，风险覆盖就不完整。另一个失败模式是“静默失效”：API 错不抛异常，渲染图看起来“差不多”，GPT-V 给出模糊的“看起来还行”，闭环提前终止，错误被固化在最终场景里。这种失败比死循环更危险，因为它不产生任何告警信号，成本账本上甚至显得“便宜”。

复杂场景仍会失败，机制上的理由是误差耦合随物体数量超线性增长。每个物体都带来位置、朝向、尺度三组参数，物体间的相对约束（接触、遮挡、对齐）数量随物体数呈组合增长，而 GPT-V 的视觉判断是全局的、低分辨率的，无法逐约束核对。于是当场景从“桌上一只杯”扩展到“餐桌周围一圈椅子、桌上餐具、吊灯”时，反馈文本只能覆盖最显眼的几处异常，剩余约束在轮数耗尽后仍未被修正。这就是“轮数多、成本高”与“仍会失败”并存的根源：不是闭环不工作，而是闭环的观测带宽小于场景的约束数量。

四 · 评分演练：同一道题的三份作答如何落点

演练一（及格档）：作答写道“最大风险是 LLM 生成的 bpy 代码可能有语法错误和 API 错误，SceneCraft 用 GPT-V 看渲染结果并给出反馈让 LLM 修改”。这份作答命中了两个判分点（LLM 写 bpy 代码、GPT-V 看渲染反馈），但风险只覆盖语法与 API，漏掉空间关系错与死循环；反馈只提到“看渲染结果”，没有写出“写-渲-看-改”的闭环结构，也没有说明文字反馈如何转成代码修改。按 50/50 切分，风险项因覆盖不全只能拿到部分分，反馈项因缺少闭环结构同样打折。它的典型缺陷是把“反馈”当成一个动作而不是一条链。

演练二（良好档）：作答写出“风险包括语法错、API 错、空间关系错、死循环；SceneCraft 的闭环是 LLM 写代码→Blender 渲染→GPT-V 看图→把‘看起来不对’转成文字→LLM 改代码”。这份作答四个判分点齐全，风险四类覆盖完整，闭环四步明确，且点出了“看起来不对转文字”这一转导环节。它距离满分差的是动力学：没有说明为什么视觉反馈不可替代、没有给出轮数与成本的约束、没有指出复杂场景下误差耦合导致闭环仍会失败。评分上，风险项与反馈项都能拿到大部分分，但在“机制解析”与“工程判断”上留了缺口。

演练三（满分档）：在良好档基础上补三段。其一，指出代码的精确性与 LLM 概率文本输出的结构性张力，四类错误同源于此，因此静态检查只能拦住前两类，空间错必须靠渲染图暴露。其二，给出成本式 C_total = N_round·(C_render+C_vision+C_llm)，说明瓶颈在轮数尾部，死循环是“零产出全额计费”，静默失效是“便宜但固化错误”。其三，给出复杂场景失败的机制：约束数量组合增长而视觉观测带宽有限，反馈只能覆盖显眼异常，剩余约束在轮数耗尽后残留。这份作答把风险与反馈放在同一条因果链上，且给出了闭环的收敛条件与失败模式，两个 50% 都能拿满。

演练的价值在于暴露一个常见错误：答者以为“提到闭环”就等于答完了反馈机制。实际上闭环只是骨架，评分要看的是骨架上的两个转导点——渲染图如何把代码语义投影为可视异常，文字反馈如何把可视异常映射回代码行。前者决定反馈的观测带宽，后者决定反馈的命中率。只写“写-渲-看-改”四个字，等于只交了骨架图，没有交动力学。

五 · 判分点的权重落地：风险与反馈为何必须各占一半

评分标准写死“风险 50%，反馈机制 50%”，这个切分有工程依据：只答风险不答反馈，等于说“这方法很危险”却不说“它怎么自救”，是半份诊断；只答反馈不答风险，等于说“它有闭环”却不说“闭环在对抗什么”，是半份方案。二者互为条件——反馈机制的设计（用渲染图而非代码日志）恰恰是由风险的类型（空间错无法从代码静态发现）决定的。因此评分时不能允许“闭环”一词跨栏计分：闭环属于反馈那一半，风险那一半必须独立看到四类错误与“概率文本对接精确 API”的机制表述。

在风险半边，四类错误的权重不是均等的。语法错与 API 错是显性的、可被工具拦截的，答者提到即得分但不足以拿满；空间关系错是本题的核心风险，因为它直接对应“LLM 不懂 3D 空间”这一常见错误的纠正点；死循环是系统代价的代表，漏掉它意味着答者没有考虑闭环的运行成本。在反馈半边，判分点依次是：GPT-V 看渲染结果（观测通道）、把视觉异常转成文字（转导）、文字回灌触发代码修改（闭环闭合）、以及轮数与成本的约束（工程判断）。前三项构成机制，第四项构成动力学，缺第四项则反馈半边停在良好档。

一个具体的评分动作是要求答者给出“反事实”：如果去掉 GPT-V 只看代码日志，闭环会怎样？正确答案是空间错无法被发现，因为代码日志只报告异常与打印，不报告“杯子悬空”。这个反事实能快速检验答者是否真的理解渲染图的不可替代性，而不是把 GPT-V 当成一个可替换的“另一个 LLM”。同理，如果去掉渲染只做静态检查，语法错与 API 错能被拦住，空间错与死循环拦不住——这正好对应风险四类中后两类的特殊性。

六 · 从机制到工程判断：闭环的收敛边界在哪里

把闭环看成一个迭代修正过程，可以写出一个粗略的收敛判据：每一轮修正带来的场景误差下降量，必须大于该轮引入的新误差量，否则迭代不收敛。视觉反馈的粒度决定了下降量的上限，而代码修改的耦合性决定了新误差的量级。当场景约束数量超过视觉可辨识的异常数量时，下降量趋近于零而新误差仍在产生，闭环进入震荡。这不是“轮数不够”的问题，增加轮数只会让成本线性上升而不改变收敛性。工程判断因此落在“何时停止闭环、改用人工介入或分解场景”上，而不是“再多跑几轮”。

SceneCraft 的设计选择——用 GPT-V 看渲染图而不是让 LLM 读自己的代码——正是对上述边界的回应：代码是精确的，但精确的代码不携带“看起来对不对”的信息；渲染图携带该信息，却丢失了符号级的定位能力。闭环的每一次迭代都是在这两种信息之间做翻译，翻译的保真度就是系统的上限。复杂场景仍会失败，不是因为模型不够强，而是因为这条翻译链的带宽被视觉分辨率与文字粒度共同限制。答者若能在满分档写出这一层，说明其理解已经从“知道有这个闭环”推进到“知道这个闭环的收敛条件”。

落到具体机制上，最值得在作答里点明的是“反馈的观测通道决定了纠错的能力边界”：语法与 API 错可以由执行异常捕获，属于低成本通道；空间错只能由渲染图暴露，属于高成本通道；死循环只能由超时机制兜底，属于资源通道。三条通道对应三种纠错手段，混为一谈就会得出“有闭环就万事大吉”的错误结论。评分演练中反复出现的失分点，正是答者把三条通道压成一句“GPT-V 看渲染图反馈”，既没有区分风险类型，也没有说明为何空间错必须走视觉通道。
