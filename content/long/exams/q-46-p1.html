一 · 三档答案的分层标准与判分权重

这道题表面上是一个事实回忆题，实质是一个工程判断题。参考答案给出的信息点可以拆成两组：来源组（多来源抓取、去重、格式转换、许可过滤、元数据对齐、1000 万+）与风险组（许可/版权混杂、重复与低质资产、类别长尾、分布偏导致评测虚高）。评分标准明确写了来源 40%、风险 60%，这个权重分配本身就是判分的第一道筛子：只答来源不答风险的答案，上限被压在及格线附近；风险答得深但来源含糊的答案，反而更容易进入良好档。

及格档的形态是“点齐但浅”。考生能说出 GitHub、Thingiverse、Sketchfab 三个来源名，能提到去重和格式转换，能说出 1000 万+ 这个量级，风险部分能列出“版权”“质量”“长尾”三个词，但每个词后面没有机制。这种答案在来源 40% 里能拿到大部分分，在风险 60% 里只能拿到词面分，因为判分点要求的是“风险如何作用于训练与评测”，而不是风险名词的罗列。

良好档的形态是“有机制但缺数字底账”。考生能解释去重为什么必须做（近重复资产会让模型记住而非泛化）、许可过滤为什么是硬约束（许可混杂使数据集不能整体以单一许可发布，下游商用链路被切断）、长尾为什么伤害评测（类别分布偏斜使高频类指标掩盖低频类崩溃）。但良好档往往说不清“1000 万+”这个数字是怎么被支撑起来的：多来源抓取的原始量、去重后的留存率、格式转换的失败率、许可过滤的剔除率，这四个环节各自吃掉多少，决定了最终规模是不是“有效规模”。

满分档的形态是“机制 + 底账 + 评测判断”三层闭合。它会把规模拆成一条流水线：抓取 → 去重 → 格式转换 → 许可过滤 → 元数据对齐 → 质量分级，并指出每一环都是规模的分母而不是分子；它会指出 1000 万+ 是清洗后的口径而非抓取口径；它会把“评测虚高”落到具体机制上——分布偏使测试集与训练集共享同一批高频来源，指标上升反映的是来源覆盖而不是生成能力。满分档不追求把每个环节都给出精确比例（题目没有给这些数字），而是明确区分“已知事实”与“工程上必须核算但题目未给的量”，这种区分本身就是工程判断力的体现。

二 · 来源机制：多源抓取为什么不是“多开几个爬虫”

参考答案里的“从 GitHub、Thingiverse、Sketchfab 等多个来源抓取”在工程上对应三种完全不同的资产形态。GitHub 上的 3D 资产多以仓库形式存在，资产与代码、配置文件、README 混在一起，抓取单位是仓库而不是单个模型，抽取时需要遍历目录、识别模型扩展名、处理 Git LFS 指针文件。Thingiverse 以社区分享的打印模型为主，资产附带打印参数、材料说明、衍生关系（remix），抓取单位是“帖子 + 附件”，衍生链本身构成一张图。Sketchfab 是托管平台，资产带作者、许可、标签、面数等结构化元数据，抓取走 API 或页面解析，元数据质量最高但许可字段最复杂。

三种形态意味着“抓取”不是统一动作，而是一组适配器。工程上的典型结构是：每个来源一个 collector，输出统一的中间记录，字段至少包括资产字节、来源标识、原始许可字符串、作者、抓取时间、父级关系。中间记录进入下一环之前必须做 schema 校验，否则后续去重和许可过滤会在异构字段上失效。伪代码思路如下：

$$\text{record} = \{\,\text{bytes},\ \text{source},\ \text{license\_raw},\ \text{author},\ \text{parent},\ \text{ts}\,\}$$

这里的关键判断是：来源多样性带来的不是简单的数量叠加，而是分布叠加。GitHub 偏向代码伴生的技术型资产，Thingiverse 偏向可打印的实体物件，Sketchfab 偏向视觉展示型资产。三者的类别分布、面数分布、许可分布都不同。把它们混在一起，规模上去了，但混合后的分布是三个偏斜分布的并集，而不是自然分布。这正是后文“分布偏”风险的源头，也是满分档必须点出的因果链：多来源抓取 → 分布并集 → 评测集若按同一并集采样 → 指标虚高。

系统代价方面，多来源抓取的第一大失败模式是“来源漂移”：平台改版、API 限流、许可字段改名，都会让某个 collector 静默产出空记录或错字段。若没有按来源的产出监控（每个来源的抓取量、字段完整率、许可解析成功率），规模数字会在某个来源失效后仍然“看起来正常”，因为其他来源补上了总量。第二个失败模式是元数据对齐失败：同一资产在不同来源有不同 ID、不同作者拼写、不同许可表述，对齐不上就会在去重环节被当成两个资产，直接抬高重复率。

具体例子：一个在 Thingiverse 上以 CC-BY 发布的模型被用户 remix 后在 Sketchfab 以 CC-BY-NC 重新上传，两者几何高度相似但许可不同。若抓取阶段只记录 license_raw 而不做许可归一化，去重阶段按几何相似度合并时就会面临“合并后许可取哪个”的问题；取交集则资产不可用，取并集则违反 NC 条款。这个例子说明许可过滤不能放在去重之后当独立步骤，而必须与去重联动，这是良好档与满分档的分界线之一。

三 · 清洗流水线与数字底账：1000 万+ 是分子还是分母

参考答案的“做去重、格式转换、许可过滤与元数据对齐，规模到 1000 万+”这句话里，最容易被误读的是“规模到”。及格档会把 1000 万+ 理解为抓取量，满分档必须把它理解为清洗后的有效量。工程上正确的记账方式是：抓取原始量是分母，去重留存率、格式转换成功率、许可过滤通过率、元数据对齐完整率四个乘子决定分子。用公式表达：

$$N_{\text{eff}} = N_{\text{raw}} \times r_{\text{dedup}} \times r_{\text{format}} \times r_{\text{license}} \times r_{\text{meta}}$$

题目没有给出这四个比率的具体数值，因此不能编造。但工程判断要求考生指出：1000 万+ 若已经是清洗后口径，则原始抓取量必然显著大于它；若 1000 万+ 是抓取口径，则有效量会明显缩水，训练价值被高估。这两种口径在论文与工程文档里经常混用，是“规模等于质量”这一常见错误的温床。满分档的写法是明确声明口径，并指出口径不明时规模数字不可比。

去重环节的机制值得单独展开。3D 资产去重不是文本去重，几何相似度计算代价高。常见做法是先做粗筛（包围盒尺寸、面数、顶点数、缩略图感知哈希），再做精筛（几何特征或渲染视图比对）。粗筛用低成本特征把候选对压到可承受规模，精筛只在小候选集上跑。系统代价在于：粗筛阈值过松会让精筛的候选对数量爆炸，计算预算被吃光；粗筛阈值过紧会漏掉缩放/旋转后的近重复，重复率被低估。失败模式是“去重不彻底导致训练集泄漏”：近重复资产同时出现在训练与测试划分中，评测指标虚高，这与“分布偏导致评测虚高”是两条独立的虚高路径，满分档应把两者并列。

格式转换的机制是统一到可训练的表示。不同来源的资产格式各异，转换到统一格式时会出现拓扑损坏、材质丢失、单位不一致（米/毫米）、坐标系手性差异。转换成功率不是 100%，失败资产要么丢弃要么修复，两者都影响有效量。元数据对齐则是把作者、许可、标签、类别映射到统一词表，对齐失败会导致许可过滤无法执行——许可字段为空或无法解析的资产，在合规严格的流水线里只能被剔除，这是一条隐性的规模损失。

具体例子：假设某来源的一批资产许可字段是自由文本，写着“free for personal use”。许可归一化器无法把它映射到标准许可集合，合规策略只能将其归入“不可商用/不可再分发”，于是这批资产在训练可用集里被剔除，但在“抓取量”统计里仍然计数。若规模数字取自抓取量，就会高估可用数据；若取自过滤后集合，则必须披露这类剔除的比例。这个例子不需要具体数字，就能说明底账口径为何是满分档的硬要求。

四 · 风险机制：许可、重复、长尾、分布偏如何各自传导

许可/版权混杂是第一风险，因为它是硬约束而非质量约束。机制上，多来源抓取使数据集内并存多种许可：允许商用的、禁止商用的、要求署名的、要求相同方式共享的、许可未知的。数据集整体发布时，若不能按许可分层，就只能取最严格的交集，导致大量资产不可用；若按许可分层发布，则下游使用者必须按层过滤，工程复杂度转移给用户。失败模式是“许可传染”：一个 NC 资产混入商用子集，整批子集的商用声明失效。系统代价是许可过滤必须在流水线早期执行，且必须与去重联动（见第二节例子），否则后期返工成本极高。

重复与低质资产是第二风险，传导路径是训练效率与评测泄漏。重复资产让模型在近重复样本上过拟合，泛化被高估；低质资产（破面、非流形、无材质、尺度异常）让训练信号带噪，生成结果的几何合理性下降。机制上，质量分级是必要的第三道筛：按几何完整性、材质完整性、尺度合理性、渲染可用性打分，把资产分为可用/修复/丢弃三档。系统代价是分级本身需要渲染与几何检查，计算开销与存储开销都不小；失败模式是分级标准与训练目标不一致——为渲染优化的质量分不一定适合几何生成训练。

类别长尾是第三风险，传导路径是评测均值掩盖低频崩溃。3D 资产的类别分布高度偏斜：常见物件（家具、餐具、玩具）占据多数，专业物件（机械零件、生物结构、建筑构件）稀少。若评测集按自然分布采样，高频类指标主导总分，低频类的失败不可见。机制上，正确做法是按类别分层报告指标，或对低频类过采样评测。失败模式是“长尾类生成崩溃但总分好看”，这在工程部署时表现为特定类别请求的失败率远高于均值。

“数据多但分布偏”导致评测虚高是第四风险，也是最隐蔽的一条。机制上，多来源抓取使训练分布成为多个平台分布的并集，而评测集若从同一并集采样，则测试样本与训练样本共享来源特征（同样的作者群、同样的标签体系、同样的几何风格）。模型学到的可能是来源特征而非生成能力，指标上升反映的是来源覆盖。失败模式是跨来源泛化崩溃：在留出来源上评测时指标显著下降。系统代价是必须做来源级划分（source-wise split），这会减少可用训练量并让评测更严格，工程上常被牺牲掉，正是虚高的制度性原因。

五 · 评分演练：同一道题的三份答卷如何落档

演练一（及格档）：答卷写“Objaverse-XL 从 GitHub、Thingiverse、Sketchfab 抓取，做了去重、格式转换、许可过滤，规模 1000 万+。风险是版权、重复、长尾、分布偏。”这份答卷命中全部判分点的词面，来源组得分接近满额，风险组只拿到名词分。失分点在于没有机制：去重为什么重要、许可过滤为什么是硬约束、分布偏如何导致评测虚高，全部缺失。按 40/60 权重，落在及格档上沿。常见错误“以为规模等于质量”在这份答卷里没有暴露，但也没有被反驳，判分时应视为未证明。

演练二（良好档）：答卷在上述基础上补充了“去重防止近重复导致训练测试泄漏”“许可混杂使数据集不能整体单一许可发布”“长尾使均值指标掩盖低频类失败”。这份答卷在风险组拿到机制分，来源组仍停留在词面。失分点在于数字底账：没有区分抓取量与有效量，没有指出 1000 万+ 的口径问题，也没有把四个清洗环节理解为规模的乘子。此外，它把“分布偏导致评测虚高”与“重复导致泄漏”混为一谈，未识别这是两条独立路径。按权重，落在良好档中部。

演练三（满分档）：答卷以流水线视角组织：抓取适配器 → 统一中间记录 → 粗筛精筛两级去重 → 格式转换与元数据对齐 → 许可归一化与过滤（与去重联动） → 质量分级。明确声明 1000 万+ 的口径必须是清洗后有效量，并给出乘子公式，指出题目未给各比率因此不能编造具体留存率。风险部分四条各自落到传导机制：许可的硬约束性与传染性、重复的两级去重代价与泄漏路径、长尾的分层评测、分布偏的来源级划分与跨来源泛化崩溃。最后给出工程判断：规模数字必须与口径、清洗乘子、评测划分一起报告，否则不可比。这份答卷不编造数字，但把“必须核算什么”说清楚，落在满分档。

演练的判分操作建议：先看风险组是否给出至少两条传导机制，没有则封顶及格档上沿；再看是否区分抓取量与有效量，没有则封顶良好档；最后看是否把评测虚高的两条路径（泄漏与分布偏）分开，未分开则不能进满分档。这个顺序与 40/60 权重一致：风险组是主筛，来源组是辅筛，底账与评测判断是满分档的加锁条件。

还有一个容易被忽略的判分细节：常见错误“忽略许可”在答卷里的表现形式往往不是完全不提许可，而是把许可过滤当成一个普通清洗步骤，与格式转换并列，不指出它的硬约束属性。判分时应识别这种“并列式降级”：许可被写成“也做了许可过滤”，而不是“许可决定了数据集能否整体发布、决定了去重合并策略”。前者是及格档特征，后者才是良好档以上。同理，“以为去重不重要”的表现形式是把去重写成“去掉了重复文件”，而不是“近重复会破坏训练测试划分的独立性”。判分演练的价值就在于把这些词面与机制的差别固定成可操作的落档规则，而不是凭印象给分。
